## Reported, not fixed

- **Reasoning effort is `high` for every request** (`model-config.ts:3`, `plan.ts:4019`). A greeting pays the same reasoning latency as a multi-artifact plan. S11 forbids a keyword greeting classifier, so lowering it needs a product decision. One option is a model-chosen or surface-based profile. Streaming (fix 3) hides much of this but not the time to the first token.
- **Focused edits build context twice** (`runtime.ts:679` and `:689`). An explicit focused edit re-runs `buildContext` with `hydrateTargets`. The first pass could hydrate directly when the edit signal is already known. This design is owned by CONTEXT, so I did not change it.
- **`updateStatus(retrieving)` and `setContextSnapshot` run serially** (`runtime.ts:765-783`, `:791`). Both patch the same run row, so running them in parallel would only trade latency for OCC retries. Merging them into one mutation is the real fix, which is a Convex contract change.
- **`finish_reason: "length"` on a text-only turn is returned as the final answer** (`agent-loop.ts:252`). No `max_tokens` is sent, so this only happens at the model's own output cap. That is rare, but the result is a silently truncated answer. The fix would treat `length` like the trailing error in fix 1 and let the loop continue or repair.
- **Streamed deltas are the model's raw text.** Owned IDs and long tokens are stripped by `sanitizeArtifactUserFacingContent` only in the final `text_replace`, which arrives seconds later. IDs are not secrets, but a student may briefly see one.
- **The chat reply's native sentence is a snapshot.** When the Bridge verifies later, the Live Dock updates, but the saved chat message still says the file "hasn't confirmed this change yet". The wording ("yet") is true when written. Live re-rendering would need the chat message to follow `run.outcome`.
- **There is no claim check on the answer path.** A no-operation answer that says "I saved it" is not contradicted by anything. The prompt forbids such claims (`workspace-assistant-prompt.ts:12`), and operate paths are receipt-backed.
- **Academic integrity (product decision).** The prompt says "When asked to create or change something, do it" (`workspace-assistant-prompt.ts:8`). A "write my essay" request is completed as written. Whether to coach instead, disclose AI authorship to teachers, or offer a teacher-side policy needs a product decision, so I did not invent a policy.
- **`appendEvents` collects all of a run's events on every batch** (`convex/spectraRuns.ts:1646`). Streaming adds a flush every 1.5 s while an answer is written, so a long answer's read cost grows with its length. Coalescing (fix 3) bounds the number of rows but not this read. This belongs to ops/performance.

## Traced and not a defect

- **Compaction** (`agent-context.ts`, `agent-loop.ts:153-235`) runs at 80% of 256k, targets 50%, and keeps system and user messages verbatim. It keeps the latest exchange and the exact task state (staged graph and receipts), and digests older tool results into IDs and statuses with a re-read note. The token estimate is provider `promptTokens` plus appended characters ÷ 3.5. If an over-window turn cannot be reduced, the loop pauses instead of truncating the task.
- **Tool results** are bounded by `boundedToolData` (24k characters, 4k per string) before entering the loop. Tool and source content are framed as evidence, not instructions, in the system prompt, the tool prompt, and the attached-draft labels.
- **Loop limits** (`agent-loop.ts:140-187`): 24 turns, 60 tool calls, 4 minutes. After that the loop has two finalization turns. A no-progress nudge comes at 2 idle turns and forced finalization at 4. Cumulative tokens are capped at 4× the window. Partial failure is reported through `interruptedEffectSummary` from receipts.
- **Clarification**: `ask_user_choice` takes 2–6 titled options with descriptions. `request_context_target` accepts only permissioned candidates and disambiguates duplicate titles by workspace. The prompt asks for one question only when the answer materially changes the result.
- **Model configuration**: `openai/gpt-5.6` with a Luna fallback, OpenAI-only routing, and an idle timeout of 25 s (60 s for complex requests) that treats keep-alives and reasoning as activity. The recovery sequence is repair, then encouragement, then the fallback provider, then primary retries at 1.5 s and 5 s. On a mid-stream failure the user now sees any streamed text taken back while recovery runs, then either the recovered answer or a receipt-based error.

## Needs live verification

1. Ask a plain question in chat on the deployed (scheduled) path. Text should appear in chunks roughly every 1.5 s through durable events, and the final message should replace it without a flicker or a duplicate.
2. Ask for an edit whose model turn opens with prose before calling a tool. The preamble may appear briefly, should disappear when work is staged, and the "Done" text should appear only after the save.
3. Force a provider error mid-answer (for example by blocking the route). The partial text should be cleared and the retried answer should stream fresh, with no truncated reply saved.
4. Make an AI edit to a Bridge-backed `.docx`. The chat reply should end with "The file on your computer hasn't confirmed this change yet.", and after Bridge read-back the Live Dock should show verified.
5. Check that the first-token time on a simple question improves by one Convex round trip (the removed planning write).
6. Spot-check tone with 14-year-old style prompts: no flattery, age-appropriate content, uncertainty admitted, and no refusal of ordinary topics such as reproduction in biology or wars in history.
