# W1-01 — Spectra prelaunch cost and hosting audit

Audit date: 2026-09-08  
Baseline inspected: `43c45cc557942ccfb4f806092a61b6950dcdf2f3` (`main`, clean)  
Scope: production composition, Convex function/cost paths, realtime gateway, AI callbacks, cron/scheduled work, and hosting scenarios. Landing-page work is excluded.

## Result

This is a cost/hosting evidence packet, not a deployment or a hosting decision.

The codebase has a coherent composition for the intended school launch: Next web/API, Convex functions and scheduler, a signed AI callback path, a Hocuspocus collaboration gateway, and a local-device Bridge/replica path. The main launch gap is operational proof: the repository contains a production Fly manifest for the gateway, but no checked-in deployment contract proving where the web app and Convex production deployment run, which plan/region they use, or which exact build is live. The gateway manifest is also deliberately single-instance and stateful.

Historical measurements explain Pablo's cost concern, but they are not a current production verdict. The older evidence contains large improvements already reflected in source—projection tables, indexed stale-run recovery, scheduled reminder delivery, and reduced idle polling—while also showing two items that must be remeasured before being called safe:

1. `replicas:sweepReplicaTruth` was observed at 510 documents and 463,634 DB-I/O bytes in one scheduled execution in an existing P8 capture, even though the current source exposes a 100-document budget.
2. The live UI still has multiple independent refresh paths: durable run-event polling, run-tab refresh, a 180-second idle dock refresh, and a 10-second active conversation recovery refresh. During an active AI run, the one-second server-side heartbeat and event/artifact writes add a separate write path.

No deployment, plan change, data migration, query-source fix, or hosting recommendation was made in this wave.

## Cron and scheduled-job map

Current `convex/crons.ts` schedules:

- every 1 minute: legacy replica-truth migration and private-memory maintenance;
- every 2 minutes: stale Spectra runs, stale Bridge work, replica-truth sweep, school lifecycle jobs/exports;
- every 1 minute: scheduled school announcements;
- hourly: planner/timetable reminder safety sweeps;
- daily: artifact-snapshot maintenance and memory safety evaluation.

Reminder delivery has been changed from broad minute scans to schedule-at-write plus hourly indexed safety sweeps. `plannerReminders.ts` and `timetableReminders.ts` store scheduled-function handles and reconcile bounded overdue/missing handles.

The legacy migration is cursor-paginated over `spectraArtifacts` in batches of 25 and becomes cheap after its migration row reaches `complete`. It still runs every minute until that state is proven. The next live check should record whether `replicaTruthMigrations.key = replica-truth-v1` is complete in the actual production deployment; no source change was made here.

## Findings

### W1-01-F01 — Production composition and live cost identity are unproved (P0 launch evidence gap)

The repository proves a Fly collaboration gateway shape, not the complete production topology. There is no source-controlled answer here for the web host, Convex deployment URL, Convex plan/class, data region, deploy command/commit binding, or whether the gateway is actually running in `mad` with one machine. Without those values, a dashboard spike cannot be joined reliably to a commit or user journey, and the managed-vs-self-hosted comparison cannot be priced honestly.

Required next evidence: exact production web URL, Convex deployment/region/plan, gateway app/machine/region, current build IDs, and the deployment mechanism for each. This is a hosting question, not permission to deploy.

### W1-01-F02 — Replica sweep needs a current populated-state measurement (P1 cost risk)

The current `sweepReplicaTruth` implementation uses a shared document-budget helper intended to cap work at 100 documents and uses indexed state/time ranges. It then performs nested lookups for requests, work replicas, payloads, transitions, and conflicts. The existing scheduled capture nevertheless saw 510 documents and 463,634 bytes in one execution. This could be old-build evidence, instrumentation semantics, or a path whose nested reads are not represented by the intended cap; the audit does not assume which.

Measure on the current production-like build with 0, 100, 250, and 1,000 stale records. Record `databaseReadDocuments`, DB read/write bytes, writes, execution time, and returned bytes per invocation. Do not call this fixed until the observed and intended budgets agree.

### W1-01-F03 — Refresh paths can amplify active-run reads (P1 bandwidth/read risk)

The run surface has several legitimate but overlapping recovery mechanisms:

- `useSpectraRun` consumes durable run events and has fallback run-tab refreshes;
- `live-dock.tsx` refreshes run tabs every 180 seconds when visible/consumed and has a faster active-run path;
- `conversation-surface.tsx` refreshes the full thread/workspace state every 10 seconds during an active run;
- run creation, streaming, and stop/retry paths also force refreshes through the shared API cache.

The current design is materially better than the historical 750ms/full-row `listTabs` path: `spectraRuns.listTabs` now uses `spectraRunTabs.by_account_updated`, a bounded limit, stored run summaries, canonical-thread deduplication, and one result-card projection per canonical tab. The remaining question is whether active runs receive both event deltas and repeated full snapshots at the same time. W1-02 should measure requests and Convex function calls per active run, not just idle screens.

### W1-01-F04 — Collaboration gateway has a periodic policy/exchange floor (P1 realtime cost risk)

The Fly gateway keeps rooms in memory and runs `enforceActivePolicyVersions()` every 5 seconds. Each active room/group can trigger policy checks through the signed Convex bridge. Accepted messages are merged and persisted after a short debounce; checkpoint/snapshot work is another write/read path. Historical evidence found 113K `collaborationGatewayBridge.exchange` calls and 343.11MB egress.

Measure one idle room, one active room, 10 rooms, and a classroom-sized room set with two browser peers per room. Separate policy-sweep exchanges, authorization, canonical update appends, checkpoints, snapshot loads, health probes, and client-visible egress. The single-instance room model also needs restart/recovery evidence before horizontal scaling is considered.

### W1-01-F05 — Artifact list is projection-first, but detail and access enrichment remain fan-out candidates (P1 DB-I/O risk)

`spectraArtifacts.list` now reads `spectraArtifactSummaries`, bounded grants/principal/workspace/invitation indexes, and returns projected metadata without full content, text indexes, protected bases, or AI previews. That is the correct direction and addresses the historical 12.51GB class.

It still enriches candidate summaries with per-summary overrides, workspace/placement information, and latest agent release/owner lookups. `spectraArtifacts.get` intentionally reads the full artifact plus placement/invitation data for detail/open. W1-02 should measure the ratio of list bytes to detail bytes at 10, 100, and 500 artifacts, with and without school/workspace filters, and count the query calls per response.

### W1-01-F06 — Content and sync state have several intentional duplicate representations (P1 storage/backup risk)

The schema can hold, depending on artifact/workflow state: full `spectraArtifacts.content`, `textIndex`, protected base content/text, `aiPreview.content`, projection summaries, `workReplicas.projectionBaseContent`, `bridgeWriteRequests` projection bases, `payloadObjects` metadata pointing to `_storage`, version `before`/`after` payloads, `artifactSnapshotObjects.payload`, and collaboration update/snapshot bytes. These are defensible for fidelity, conflict recovery, and offline sync, but they are not the same billing category:

- Convex DB storage/I/O covers rows, indexes, and document/index data transferred inside functions;
- Convex file storage/egress covers `_storage` payloads and delivery;
- Fly volume storage/backups would be a separate self-hosted concern;
- external model/provider charges are outside all of these.

The next measurement should sample representative row sizes and write amplification for a small text artifact, a rich artifact, a versioned artifact, and a collaboration room. Do not infer persisted storage from a DB-I/O dashboard number.

### W1-01-F07 — AI callback path has high call frequency while a run is live (P1 active-run cost risk)

The scheduled chain is bounded at the dispatch boundary: `spectraRuns.scheduleExecution` schedules one internal action, `executionScheduler` posts one signed callback, and the callback re-enters the runtime only after HMAC/timestamp verification. Inside a live attempt, however, the runtime heartbeats every second, queues/batches events, and performs progressive artifact/operation/status writes. Retries, resumes, confirmation, and stop paths add alternate chains.

Measure a no-op run, a text-only run, a one-artifact run, and a retry/resume. Capture calls, DB reads/writes, event count, write bytes, action compute, callback count, and elapsed time. The useful unit is “per run and per minute while live,” not just “per user session.”

## Cost model

The following is an auditable model, not a quote. It uses Convex Professional's published US rates as checked on 2026-09-08: $25/developer/month; 25M function calls, 250 action GB-hours, 50GB DB storage, 100GB file storage, 50GB DB I/O, and 50GB egress included; then $2/M calls, $0.30/action GB-hour, $0.20/extra DB-storage GB, $0.03/extra file-storage GB, $0.20/extra DB-I/O GB, and $0.12/extra egress GB. Convex notes EU-region pricing at 1.3x on its limits page. Query/mutation compute is free on Professional; Node/action compute is not. See [Convex pricing](https://www.convex.dev/pricing) and [Convex limits and metering definitions](https://docs.convex.dev/production/state/limits).

Use decimal GB consistently in the worksheet:

```text
monthly_DB_IO = users × active_days ×
  (list_actions × list_MB + detail_actions × detail_MB + live_actions × live_MB)
  + scheduled/system_DB_IO

metered_cost =
  max(0, calls_M - 25) × $2
  + max(0, action_GBh - 250) × $0.30
  + max(0, db_storage_GB - 50) × $0.20
  + max(0, file_storage_GB - 100) × $0.03
  + max(0, db_IO_GB - 50) × $0.20
  + max(0, egress_GB - 50) × $0.12
```

Illustrative monthly scenarios, before tax and external AI/model charges:

| Scenario | Explicit workload assumptions | Modeled usage | Convex Professional illustration |
| --- | --- | --- | ---: |
| Small pilot | 200 students + 20 teachers; 20 active days; 40 peak concurrent; per user-day: 4 brief/list actions × 0.25MB, 1 detail open × 2MB, 0.25 live AI/collaboration action × 3MB; +5GB system/scheduled | 21.5GB DB I/O; 2M calls; 20GB egress; 20GB DB storage; 40GB files; 100 action GB-hours; 2 developers | **$50/month base**, no modeled overage |
| Larger school | 1,000 students + 200 teachers; 20 active days; 250 peak concurrent; per user-day: 5 list actions × 0.5MB, 1.5 detail opens × 3MB, 0.3 live action × 5MB; +40GB system/scheduled | 244GB DB I/O; 35M calls; 150GB egress; 60GB DB storage; 150GB files; 500 action GB-hours; 2 developers | **about $199.30/month**: $50 base + $20 calls + $75 action compute + $38.80 DB I/O + $2 DB storage + $1.50 files + $12 egress |

The model shows why the historical “about 60GB DB I/O over two weeks” must not be read as “60GB of stored data.” If representative, it annualizes to roughly 120–130GB/month of transferred DB/index data and would be around $14–$16/month above a US Professional plan's 50GB DB-I/O inclusion before other meters; it says nothing by itself about persisted row/file storage. The actual bill still depends on calls, egress, action compute, region, and whether the capture was representative.

## Hosting comparison (no winner selected)

| Option | What it removes/keeps | Cost shape | Operational questions |
| --- | --- | --- | --- |
| Managed Convex | Keeps current Convex queries, realtime, scheduler, backups, dashboard, and function metering | Predictable team base plus usage meters; Professional has the inclusions above; EU region multiplier applies where relevant | Confirm plan/class, region, build/deploy binding, backup/export access, and whether current school traffic fits S256 concurrency/session limits. |
| Supported Convex self-hosted on Fly | Keeps the Convex backend model but moves backend runtime, persistent state, upgrades, backup, auth/config, and observability ownership to the operator | Fly compute + persistent volume + snapshot/backup + egress + engineering/incident time; it does not make DB reads/writes logically disappear | Convex says self-hosting is hands-on and recommends hosted Convex for a more hands-off solution. The official Fly guide separates deploying the backend from deploying application functions. A Fly volume is single-server/local to a machine and is not automatically replicated. |
| Convex metadata + cheaper object storage | Could reduce Convex file/payload storage or delivery cost for suitable large immutable objects | Adds object-store storage/egress/request charges and signed URL, hash/refcount/GC, retry, restore, and access-control work | Current code already has payload refs and metadata, but semantic projections, summaries, collaboration updates, cron reads, and Convex DB I/O remain. This is not a fix for list/subscription amplification. |

For scale context, the checked-in gateway's always-on `shared-cpu-1x` 512MB Fly shape is listed at $3.32/month before volumes, network, and operations. A self-hosted Convex backend would be a separate Fly deployment and persistent storage problem, not a free replacement for that gateway. Fly lists volumes at $0.15/GB-month and volume snapshots at $0.08/GB-month after the first 10GB; daily snapshots default to five days, and Fly says important data still needs its own backup plan. See [Fly resource pricing](https://fly.io/docs/about/pricing/), [Fly volume considerations](https://fly.io/docs/volumes/overview/), [Convex self-hosting](https://docs.convex.dev/self-hosting), and the [official Convex Fly deployment guide](https://github.com/get-convex/convex-backend/blob/main/self-hosted/advanced/fly/README.md).

Convex's supported export path can include file storage (`npx convex export --include-file-storage --prod`); this is relevant to any self-hosting or object-storage comparison, but no export or migration was run in this audit. See the [Convex export reference](https://docs.convex.dev/cli/reference/export).

## W1-02 measurement handoff

Run on one named current build and record deployment, region, plan/class, timestamps, and the Convex usage-stat window:

1. **Idle Library:** 15 minutes with one student profile, one teacher profile, and a second tab; count requests, function calls, subscription updates, DB read/write bytes, egress, and writes.
2. **Active AI:** no-op, text-only, one-artifact, retry/resume; produce a caller → query/mutation/action chain and per-run totals, including the 1-second heartbeat.
3. **Run-tab/thread fan-out:** compare event-only, active conversation, dock-visible, dock-hidden, and hard-refresh cases; report calls and bytes per minute.
4. **Artifacts:** list at 10/100/500 rows, then open representative detail rows; separate summary, placement/access, content, and file payload bytes.
5. **Replica sweep:** empty, 100, 250, and 1,000 stale rows; verify the intended 100-document/128KB-style scheduled budget against actual `usageStats` and nested reads.
6. **Collaboration:** one/10/50 rooms, two peers per room, idle and active; split policy sweep, authorize, append, checkpoint, snapshot load, and egress.
7. **Storage/backup sample:** record row sizes, index count, `_storage` payload bytes, snapshot/version bytes, and export duration without mutating production data.
