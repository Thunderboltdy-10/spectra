# W1-02 — Storage and unnecessary data access

## Result

The launch path already has a useful summary/detail split for Library and tree navigation, but several AI/workspace, history, asset, bridge, and deletion paths still cross that boundary. The strongest immediate defect was the collaboration gateway returning full `spectraArtifacts.content` on every room load even when a durable native Yjs snapshot/log was available. That is fixed in the isolated source worktree and covered by a focused Convex test. Permanent deletion also leaves cross-domain replica, payload, collaboration, and bridge rows behind; this remains report-only because it crosses the replica/collaboration lifecycle owners.

## Scope and current architecture

Source was audited at baseline `43c45cc557942ccfb4f806092a61b6950dcdf2f3` in the isolated worktree `<local-workspace>`. No live runtime, browser session, Windows bridge, or macOS runtime was changed or used; therefore the platform/runtime conclusions below are source-level only.

## Findings grouped by root cause

### W1-02-F01 — Permanent artifact deletion does not close the full payload/collaboration lifecycle

Severity: important. Confidence: high. Proven source defect.

`convex/spectraArtifacts.ts:3191-3421` permanently deletes the artifact, tree placements, versions/snapshot references, runtime builds, import originals, assets, links, runs, and some memory rows. It does not delete or retire rows in `workReplicas`, `payloadObjects`, `bridgeWriteRequests`, `syncOperations`, `syncConflicts`, `collaborationRooms`, `collaborationUpdates`, `collaborationSnapshots`, or `regionClaims`. The tree purge path separately drains collaboration updates/snapshots (`convex/orgTree.ts:654-713`), but direct `spectraArtifacts.permanentlyDelete` does not. `payloadObjects` remain discoverable through `workReplicas` reference probes (`convex/replicas.ts:1648-1743`), so a payload can remain active indefinitely after its artifact is gone. Rooms and logs become orphaned because the artifact lookup in gateway load then fails.

User consequence: “permanently delete” can leave database rows, native bytes, signed-URL-capable account payloads, bridge metadata, collaboration history, and local-replica state behind. It also makes deletion cost grow with orphan accumulation. The exact local-file behavior is a product choice—deleting an artifact may intentionally leave the user’s source file on disk—but the cloud metadata/payload lifecycle still needs an explicit terminal state.

Bounded remedy: add a capability-checked, resumable artifact-deletion job owned jointly by artifact/replica/collaboration owners. It should delete or tombstone all artifact-keyed rows, release payload refs, drain room logs in pages, and record whether the local file is intentionally retained. Do not attempt a broad schema redesign in this wave.

### W1-02-F02 — Version history and exceptional collaboration paths scan unbounded history

Severity: important. Confidence: high. Proven source defect.

`convex/spectraArtifacts.ts:listVersions` reads every version with `.collect()` (`:3084-3147`) and only then slices the requested maximum of 100. It also computes each version number by searching the full in-memory array. A user asking for 30 versions therefore still pays for the complete artifact history scan.

The collaboration recovery path similarly collects every snapshot and update for a room (`convex/collaborationGatewayStore.ts:390-405`), and verified snapshot compaction collects all prior snapshots and all updates through the snapshot boundary (`convex/collaboration.ts:344-415`). Normal compaction keeps these sets small in healthy operation, but a failed/stalled compaction or long-lived room turns recovery/verification into a transaction and memory risk.

Bounded remedy: add cursor/sequence windows for user history and page cleanup/recovery by sequence/status. Preserve capability checks, snapshot integrity, ordering, and the current “unsafe recovery fails closed” behavior. A next-wave test should seed 1,000+ versions/updates and assert fixed-size reads for a small requested window.

### W1-02-F03 — Workspace context is an unbounded full-content N+1 read

Severity: important at large workspaces. Confidence: high. Proven source defect; authorization is present.

`convex/orgTreeShared.ts:458-476` collects every live node for a workspace. `convex/orgTree.ts:929-985` then loops serially: each work node loads the full artifact through `evaluateAccess`, spreads `projectArtifactForAccess`, collects all invitations for that artifact, and adds the full projected artifact to the result. There is no item limit or pagination in `listWorkspaceContents`/`listWorkspaceContentsPublic` (`:987-1005`).

The path is called from AI gather for the requested workspace and up to three explicit workspace details (`src/app/api/spectra/run/loop/gather.ts:195-214,355-389`), from the `read_workspace` AI tool (`src/app/api/spectra/run/loop/plan.ts:3007-3016`), and from the public workspace/overview API (`src/app/api/spectra/route.ts:372-382,620-658`). A large workspace therefore loads every artifact body before the caller later summarizes many of them. This is not an authorization bypass—the access decision still gates each artifact—but it defeats the summary-first architecture and can amplify Convex reads, response bytes, and AI context cost.

Bounded remedy: make workspace listing return bounded node + artifact-summary projections, with explicit selected-ID detail reads for AI/editor actions. Keep the same `evaluateAccess` decision and quiz/timetable redaction when detail is requested; do not silently cap an existing full-content contract without updating the callers.

### W1-02-F04 — Asset gallery listing issues URLs for every asset and is not paginated

Severity: small for current 20 MiB/artifact budget, important if the limit/count grows. Confidence: high. Proven source defect.

`convex/artifactAssets.ts:listForArtifact` collects all assets by artifact/path and calls `ctx.storage.getUrl` for every active asset (`:252-280`). The API uses this path whenever no `assetId` is supplied (`src/app/api/spectra/assets/route.ts:95-117`). The safer `getReferenced` path is capped at 100 IDs and is used when callers know the references, but the gallery/list path has no count/page bound and eagerly creates signed URLs that may never be opened.

Bounded remedy: paginate metadata and issue URLs only for visible/referenced IDs, or provide an explicit “include download URLs” request. Keep read capability checks and the current integrity metadata.

### W1-02-F05 — Native download performs a redundant full artifact query

Severity: small. Confidence: high. Proven source defect.

`src/app/api/spectra/native/route.ts:52-75` calls `ensurePortablePayload` and independently calls `spectraArtifacts:get` in parallel. When a verified cloud payload already exists, the latter full artifact read is needed only for the title used in the filename. When no payload exists, `ensurePortablePayload` itself calls `spectraArtifacts:get` (`:55-60`), so the fallback can read the full artifact twice before packaging it. The POST path has the same outer full-artifact read (`:81-99`).

Bounded remedy: expose/use a capability-checked metadata-only title query or return the artifact title from the payload truth path, while retaining the full detail read only for fallback packaging. Verify native authorization and filename behavior in the route tests before changing the caller contract.

### W1-02-F06 — Direct payload/import finalizers are weaker than their HTTP wrappers

Severity: important for integrity hardening. Confidence: high. Proven source defect with fail-closed downstream verification.

The public import PUT route hashes the complete request body and compares it with the declared digest before upload (`src/app/api/spectra/imports/route.ts:118-147`), but `convex/artifactImports.ts:93-135` finalizes based only on storage size; it does not compare storage SHA-256 or content type with the job declaration. Likewise `convex/payloads.ts:25-62` checks payload size but not storage metadata SHA-256 before registering the payload under the caller-provided hash. Native retrieval later verifies bytes, so a bad record usually fails closed at read time, but the system can still retain and meter a mismatched object and direct mutation callers do not receive the same integrity guarantee as the HTTP route.

Bounded remedy: make each Convex finalizer self-contained—compare storage metadata size, digest, and expected media type; delete/quarantine the storage object on mismatch. Preserve modify capability and account ownership. This is a small validation fix, but it overlaps launch-safety ownership and should be coordinated with W1-17 before integration.

### W1-02-F07 — Abandoned import uploads have no storage cleanup path

Severity: future/important for storage retention. Confidence: medium-high. Proven source gap.

`artifactImports:abortUpload` marks the job failed but accepts no storage ID and does not delete an already-uploaded original (`convex/artifactImports.ts:215-238`). The HTTP PUT uploads directly to storage before finalization (`src/app/api/spectra/imports/route.ts:131-156`); a client disconnect after storage accepts the bytes but before finalization has no job-level cleanup. The cron inventory (`convex/crons.ts:6-77`) contains no stale import-job/storage janitor. Completed permanent deletion does delete known `originalStorageId`, but cannot clean an upload that was never finalized.

Bounded remedy: accept and validate the upload storage ID on abort, and add a bounded internal sweep for stale `uploading` jobs that deletes only their owned, expired storage objects. Define the retention window and audit/meter reversal before implementing.

### W1-02-F08 — Runtime publishing duplicates asset bytes in memory and base64 payloads

Severity: future/cost/performance. Confidence: high. Proven source behavior, bounded by 8 MiB.

`src/app/api/spectra/runtime/publish/route.ts:99-155` obtains signed URLs for referenced assets, downloads each asset into a server `Buffer`, verifies it, then embeds it as a base64 `data:` URL. The published build consequently carries an additional encoded copy (with base64 overhead) and the route holds the complete asset set in memory. The 8 MiB asset limit is a useful safety bound, but repeated publishes multiply storage/egress/compute work.

Bounded remedy: retain the current integrity checks and limit; for scale, consider immutable object references/CDN delivery or a build-time object manifest. Do not choose hosting or storage migration in this wave.

### W1-02-F09 — Scheduled maintenance runs without active-user gating

Severity: future/cost hypothesis. Confidence: high for scheduling, low for production impact.

`convex/crons.ts:6-29` runs stale-run, bridge-work, replica-truth, and legacy-replica migration jobs every 1–2 minutes regardless of active users; hourly/daily safety and snapshot jobs also run (`:30-77`). The individual replica sweeper is deliberately bounded (`convex/replicas.ts:1764-1789`) and the gateway’s policy sweep does gate on active connections, so this is not itself a correctness bug. It is a production IO/compute measurement item for W1-01: quantify empty-school and idle-account cost before changing cadence, and ensure migrations are finite rather than re-scanning completed data.

## Small fixes completed

### Native collaboration load projection split

Commit: `e424d7ce57444236eea8151b85a33f8ae9b7f2aa` (`Avoid full artifact projection on native room reload`).

- Before: `convex/collaborationGatewayStore:load` always returned `initialProjection.content` when `afterSequence === 0`, even if a verified snapshot or durable update log was available. `scripts/collaboration-gateway.mjs:onLoadDocument` therefore received full canonical artifact content on every reload; native Yjs state then made that field unnecessary.
- After: `load` accepts an optional internal `includeInitialProjection` flag and omits the full projection by default (`convex/collaborationGatewayStore.ts:271-343`). `convex/collaborationGatewayBridge.ts` forwards the validated flag. The gateway first loads durable state without content, returns native Yjs state immediately when available, and only requests the full projection in the non-native/legacy bootstrap branch (`scripts/collaboration-gateway.mjs:1141-1220`).
- Caller/authorization impact: none. The bridge operation remains internal and signed; the gateway still reauthorizes before loading. The second opt-in load preserves legacy-room migration, which is why the change is not a simple “snapshot exists => omit content” condition.
- Focused validation: `npm run test:run -- convex/collaboration-checkpoint.test.ts` passed, 8/8 tests. The new test verifies content is present for an explicitly requested empty-room bootstrap, absent on the normal load after a durable update, and still available for explicit legacy bootstrap. Targeted ESLint over all four touched files passed; `git diff --check` passed.
- Remaining limit: the second legacy/bootstrap load re-reads the bounded state envelope as well as the projection. It is rare and necessary for compatibility; a future dedicated bootstrap query could reduce that duplicate metadata read.

## Next-wave tests and implementation implications

1. Native reload/read-shape: create a large document/sheet with a verified native snapshot and tail updates; connect two sessions; capture bridge response sizes and Convex reads. Expect no `initialProjection` on native reload, identical editor state, correct policy revocation behavior, and one projection only on legacy/empty bootstrap.
2. Workspace/AI scale: seed 500 and 2,000 work nodes with mixed document, quiz, timetable, shared, and teacher-created artifacts. Compare Library, overview, `read_workspace`, and AI gather response bytes/query duration. Expect summaries first, selected content only, and no quiz-answer leakage to a student.
3. History pressure: seed 1,000 versions and 1,000 collaboration updates; request 20 versions, recover a room, and verify a snapshot. Expect bounded pages, stable version numbering, and no transaction-size failure.
4. Delete lifecycle: seed one artifact with import original, asset, version snapshot, cloud/local replicas, payload, pending bridge request, room, updates, snapshot, conflict, and region claim. Permanently delete, then assert the chosen local-file behavior, no active orphan payload/room rows, released storage accounting, and idempotent cleanup retries.
5. Upload integrity/abandonment: exercise both HTTP and direct Convex finalizers with wrong digest, wrong MIME, exact size, client disconnect after upload, explicit abort, and stale-job expiry. Expect identical rejection/cleanup semantics.
6. Asset/download/publish fanout: list an artifact with many assets with and without IDs; test native download with an existing payload and fallback packaging; publish the 8 MiB boundary. Count signed URLs, full artifact reads, server memory, and response bytes.
7. Idle workload: observe an empty account/school for at least 15 minutes, then one active editor and one Bridge mount. Attribute scheduled Convex reads/writes and gateway timers separately; do not infer production cost from local development.
8. Bridge platform windows: W1-13/W1-05 should run the same native payload lifecycle on Windows and macOS (pair, mount, edit, external save, delete/restore, reconnect) with safe disposable files. This task provides no runtime proof for either platform.

Scalable direction: keep small, capability-safe summaries, hashes, refcounts, policy state, and indexes in Convex; consider moving large immutable native payloads, import originals, assets, and cold version/snapshot bodies behind object storage with signed URLs and lifecycle rules. Preserve canonical content and Yjs durability semantics during any change, and decide managed Convex versus self-hosting separately from the storage boundary.

## Decisions for parent/Pablo

- Treat summary-first navigation as the intended contract and make workspace/AI context explicit about summary versus selected detail. Do not broaden full-content workspace reads to solve targeting ambiguity.
- Make “permanently delete” a real cross-domain lifecycle operation, while explicitly deciding whether an on-disk Bridge source is retained. The cloud payload/replica/collaboration rows should not depend on a later incidental sweep.
- Keep the completed two-phase gateway load fix; it removes a repeated full-content transfer without breaking legacy migration or changing authorization.
- Require direct Convex upload finalizers to enforce the same digest/MIME integrity as HTTP wrappers, coordinated with W1-17.
- Use production IO/egress/compute measurements to decide whether scheduled sweeps need cadence changes. Do not infer a hosting winner from the source scan.
