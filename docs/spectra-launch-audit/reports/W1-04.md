# W1-04 — Spectra universal action/search and AI viewport audit

Audit date: 2026-09-08  
Baseline inspected: `43c45cc557942ccfb4f806092a61b6950dcdf2f3` (`main`, clean)  
Scope: application action/capability convergence, human/AI command parity, route and thread opening, preference/settings paths, AI viewport/follow choreography, and the smallest safe wiring fixes needed before a universal action/search surface. Landing-page work, live dock layout (W1-11), and the AI execution loop (W1-03) are excluded.

## Result

**PASS WITH P1/P2 FOLLOW-UPS.** The repository has a credible foundation for a universal action/search surface: a capability IR, an application command projection, a shared client dispatcher, typed bus commands, permission/authority metadata, and a server tool registry. It does not yet have a universal K-bar. The installed `kbar` package is unused; the current `CommandBar` is the AI composer and `GlobalSearch` searches only work/workspaces.

The most important parity risks are not visual. The application capability map overstates the set of AI tools and server handlers that actually exist, application params are still `z.null()` in the IR while concrete schemas live separately in the AI tool registry and dispatcher, and artifact workbars mounted from `/chat` or route-side panels do not receive the application dispatcher. A palette built directly on the current records would therefore show actions whose params, host, or server execution path may be unavailable.

Three contained fixes were completed in this wave:

1. `/workspace` is now derived as the `workspace` choreography surface rather than `library`.
2. `/chat` now handles `run.openConversation` in the main ChatShell, resolving a run id to its thread when necessary. This preserves the intended rule that `/chat` owns the primary conversation and must not mount a duplicate right-side chat.
3. `app.settings.manage-account` is now readable in both the capability spec and the command presentation, so read-only students can navigate to account settings without being incorrectly disabled.

No full K-bar was built. The proposed extension and next-wave tests are below.

## Scope and current architecture

### Capability and command layers

`CapabilityDefinition` is the intended semantic source: it carries a typed Zod params schema, availability, execution refs, AI exposure/risk, and choreography (`src/features/spectra/capabilities/types.ts:58-82`). The catalog combines office, application, and studio capabilities (`src/features/spectra/capabilities/catalog.ts:1-58`). `commandBindingFromCapability` copies IR-owned fields into existing workbar bindings (`src/features/spectra/capabilities/derivations.ts:45-83`), while the ghost/conformance checks validate missing ids, execution refs, AI descriptions, and native deltas.

Application capabilities are declared in `src/features/spectra/capabilities/application.ts:12-250` and projected onto the human-facing application presentation in `src/features/spectra/commands/app-registry.ts:58-404`. The projection correctly makes the capability definition authoritative for availability, risk, choreography, and AI authority. The separate `APPLICATION_TOOL_COMMAND_MAP` (`app-registry.ts:412-465`) is a useful convergence inventory, but its current audit status means “an app command exists,” not “an AI tool and server handler exist.”

The client dispatcher (`src/features/spectra/commands/application-dispatcher.ts:36-219`) is the right seam for user-facing application actions. It validates selected params, calls the typed bus when a mounted surface owns the action, and falls back to its host for navigation/organization where available. The typed bus awaits all listeners through `commandAsync` (`src/features/spectra/events/bus.ts:23-83`). Artifact commands remain in the workbar/office registries; application commands cross the dispatcher boundary.

### Thread and route ownership

`GlobalRouteWorkbench` is mounted only on non-workbench routes; it explicitly treats `/chat`, `/workspace`, `/library`, and `/agents` as routes with their own workbench (`src/features/spectra/components/global-route-workbench.tsx:20-45`). `RouteSidePanelHost` is explicitly limited to `/school`, `/analytics`, `/settings`, `/managebac`, `/admin`, and `/superadmin` (`src/features/spectra/components/route-side-panel-host.tsx:24-49`). This is the correct structural guard against a duplicate right-side chat on `/chat`.

Before this wave, only the side-panel host handled `run.openConversation`. The new ChatShell handler (`src/features/spectra/pages/chat-shell.tsx:378-398`) resolves either a supplied thread id or `getSpectraRunDetail(runId).run.threadId`, then calls the existing URL/thread selection path. The dispatcher already awaits `commandAsync`, so a missing or inaccessible run can return an action error instead of silently opening a second surface.

The remaining side-panel asymmetry is real: its handler only calls `loadThread` when `command.threadId` exists (`route-side-panel-host.tsx:127-148`). A universal action that knows a run id but not its canonical thread id will be a no-op there. The same resolver used in ChatShell should be shared by the route-side host or the command contract should require a canonical thread id before dispatch.

### Preferences and current search controls

The preference schema already provides a plausible product choice for the future palette: `general.globalCommandBehaviour` can be `search_and_commands`, `commands_first`, or `search_first` (`src/features/spectra/settings/schema/preferences.ts:12-20`). It currently has no consumer, so it does not alter the UI.

`GlobalSearch` is a modal with focus trapping and an 180ms search debounce, but its result model is only artifacts and workspaces (`src/features/spectra/components/context-controls.tsx:708-...`). `CommandBar` is a composer with attachments, context, stop, steer, and a small composer menu (`src/features/spectra/components/command-bar.tsx:220-...`). Neither is a universal search/action surface. The package includes `kbar` (`package.json:127`), but there are no `KBarProvider`, `useKBar`, or `from "kbar"` usages in `src`.

## Findings grouped by root cause

### Root cause A — The semantic action contract is not yet the only schema source

#### W1-04-F01 — Application capability params are placeholders, so inline palette params cannot be derived (P1)

`CapabilityDefinition` promises typed params, but every application capability currently uses the shared `z.null()` schema (`src/features/spectra/capabilities/application.ts:5,232-245`). Concrete params are hand-written in `application-dispatcher.ts` and separately in `application-tools.ts`. That is enough for today’s fixed UI buttons and server tools, but not enough for a universal action surface that must render inline target pickers, enum choices, folder destinations, setting patches, or run/thread selectors from one contract.

Next implementation should give each exposed application capability its real Zod schema and derive at least: provider JSON schema, palette field descriptors, required-context predicates, and a safe display label for invalid/missing params. Target ids should be selected from permissioned search results rather than typed freehand. Keep prohibited security actions in the catalog with an explicit disabled reason, as the current code does.

#### W1-04-F02 — Tool-to-command audit reports command existence, not executable AI parity (P1)

The convergence map includes `reveal_work_anchor`, `open_run_conversation`, `begin_reference_picking`, `begin_context_picking`, `manage_account`, and other ids, but the current `APPLICATION_AGENT_TOOL_IDS` does not include those tools. `insert_reference` is registered in the tool registry (`application-tools.ts:139`) and mapped to `app.reference.insert`, yet `executeApplicationCommand` has no corresponding server handler and reaches `APP_COMMAND_NOT_REGISTERED` (`act.ts:392-395`). The same loop implements only the explicitly coded handlers between `act.ts:94-390`.

This is a registry/handler conformance defect, not a reason to broaden W1-03. The next gate should classify each map entry as one of: client-only action, AI tool + client dispatcher + server handler, prohibited, or deferred. It should assert tool presence, provider schema, command record, authority policy, and handler presence where AI exposure is true. The current test only proves map → app-command presence (`ai-command-registry.test.ts:32-46`).

### Root cause B — The dispatcher is not mounted at every surface that renders application actions

#### W1-04-F03 — Chat and route-side artifact studios lack the application dispatcher (P1)

`ArtifactStudio` accepts optional `executeApplicationCommand` (`artifact-studio.tsx:2543-2586`) and `ArtifactWorkbar` forwards it into the command context (`artifact-workbar.tsx:192-216`). The main `SpectraShell` constructs the dispatcher and passes it to its studio/tile surfaces. The `/chat` studio (`chat-shell.tsx:755-785`) and route-side studio (`route-side-panel-host.tsx:159-173`) do not pass one. Any application workbar action mounted in those contexts therefore reaches `APPLICATION_COMMAND_DISPATCHER_UNAVAILABLE` instead of the shared product path.

Next implementation should provide one shell-level `ApplicationCommandHost`/dispatcher context, with route-aware `openArtifact`, navigation, preference replacement, and library handlers. Do not duplicate a dispatcher per panel; the existing design already warns against multiple studios and stale callbacks. Add route-matrix tests for `/chat`, `/workspace`, `/library`, `/settings`, `/managebac`, and `/school`.

#### W1-04-F04 — Non-chat side-panel thread open requires a thread id even though the command contract permits only a run id (P1)

`app.run.open-conversation` validates `runId` and makes `threadId` optional (`application-dispatcher.ts:84-91`). ChatShell now resolves the optional value. `RouteSidePanelHost` currently ignores the command when `threadId` is absent (`route-side-panel-host.ts:137-140`). This will surface as a palette action that appears available but does nothing on school/settings/admin routes when selected from a run-only result.

Use a shared `resolveRunThread` helper, or require the palette resolver to enrich run results with their canonical thread id before enabling the action. The action result must report “conversation unavailable” if the run has no thread, rather than silently closing the palette.

### Root cause C — The universal surface is not implemented and the current controls have different responsibilities

#### W1-04-F05 — There is no universal search/action UI yet (P1 design/implementation gap)

The dormant `kbar` dependency and semantic-index purpose suggest an intended direction, but the current UI has three separate concerns: sidebar focus search, work/workspace `GlobalSearch`, and AI `CommandBar`. There is no global result union for artifacts, folders, workspaces, chats, settings, and commands; no command-vs-search preference behavior; no availability display; and no structured action result panel.

Proposed extension of the existing protocol:

1. **One palette record model.** Build records from permissioned library/chat search plus `APP_COMMANDS`/capability definitions. Each record has `kind` (`target`, `action`, `setting`), stable id, title/subtitle, icon, route/context, `availability`, risk, required params, and an execution target. Do not make the palette a second action registry.
2. **Rank without hiding valid domains.** Score text match first, then current surface/context, recency, permission availability, and risk. On `/settings`, boost settings and settings actions but continue showing matching library/artifact/chat targets. In `search_and_commands`, interleave; in the other two modes, bias the first group without excluding the other group.
3. **Thread ranking.** Treat an active run and a continued thread as different states. Rank an active run first when the same thread has one; rank the explicitly continued thread next; then rank the latest completed/recent thread. Preserve the current Live Dock rule that active status wins for a duplicate thread (`live-dock.tsx:553-570`), but expose “active”, “continue”, and “open” labels so the user knows why one result won.
4. **`/chat` ownership.** Selecting a chat/thread on `/chat` must call ChatShell’s main `selectThread` path. It must never send the result to `RouteSidePanelHost`; that host intentionally excludes `/chat`. On non-workbench routes, the same action may open the route side panel, but it must resolve run → thread and keep only one side conversation.
5. **Inline params.** Once application capabilities carry real schemas, render only known field types: permissioned target search, enum select, setting section, folder destination, and confirmation summary. Preserve the action record while a target is being resolved; invalid params should keep focus on the invalid field and show the schema message.
6. **Execution and result.** Navigation actions may close immediately after an awaited dispatcher acknowledgment. Mutations should show `pending`, then `success`/`error`, with a stable operation id, human-readable consequence, and a retry/undo affordance only where the underlying action supports it. Errors must return to the palette state rather than disappear into a toast-only path.
7. **Keyboard/accessibility.** Use the existing global shortcut registrar as the single entry point, avoid competing `/chat` and sidebar search shortcuts, trap focus within the dialog, keep `aria-activedescendant`/selected-result state correct, support Escape, Arrow keys, Enter, Tab/Shift+Tab, and announce loading, unavailable reason, pending, and failure through a live region. Respect reduced motion in the existing choreography layer.

The first implementation should be a thin palette resolver and dialog over existing records; it should not replace the workbar, composer, or live dock.

### Root cause D — Human and AI action vocabularies do not cover the same semantic lifecycle

#### W1-04-F06 — Close, restore, comments, continue, stop, and admin/Bridge actions are not one shared command vocabulary (P1/P2 by action)

The typed bus contains library organization/delete, work open/reveal/close request, run open-conversation, references, settings, sharing, sync, memory, and ManageBac sync (`events/contracts.ts:5-65`). It does not contain thread select/continue/stop, library restore/purge, comment lifecycle, or Bridge setup/permissions. Some omissions are good policy choices—Bridge/security must remain human-only—but the current split is not explicit enough for a universal action surface to distinguish “not a palette action” from “missing implementation.”

Before adding records, publish an action eligibility table with owner (`human`, `AI`, `both`, `never`), target requirements, authority/risk, undo/recovery, and surface behavior. Continue/stop should likely remain run-engine controls with a dedicated result contract, while comment and restore actions need target/version/concurrency semantics first.

#### W1-04-F07 — Application execution returns success before async command completion (P1)

`executeCommand` in `src/features/spectra/commands/registry.ts:301-310` returns `true` immediately after `void command.execute(...)`. This is acceptable for existing fire-and-forget workbar clicks only if their errors are handled elsewhere; it is not an adequate palette acknowledgment contract. The typed bus has an awaitable path, but the generic command helper does not expose it.

The palette should call an awaitable action executor and receive structured status. A future compatibility wrapper can preserve the boolean helper for existing workbars while adding `executeCommandAsync` or an equivalent action-result protocol. This is adjacent to W1-03 but does not require changing its run loop.

### Root cause E — Choreography is thoughtfully constrained but under-tested at route and concurrent-run boundaries

#### W1-04-F08 — Workspace route identity was wrong; fixed and regression-tested (P2, fixed)

`appSurfaceFromPathname` previously returned `library` for both `/workspace` and `/library`. That could give an AI app action the wrong visible target, causing a body to be assigned to the wrong surface or a Follow AI navigation decision to be suppressed. It now distinguishes `/workspace` and `/library` and has focused tests for both root and nested workspace paths.

#### W1-04-F09 — Follow AI input disengagement and timing need live route coverage (P2)

The choreography contract is otherwise sound: Follow AI is opt-in; direct pointer, keyboard, and wheel input disengages it; programmatic opens are marked for roughly 1.2s; repeated semantic locations are deduplicated; and app choreography settles after 280ms unless reduced motion is active (`follow-ai.ts:4-17,71-88,138-206`; `app-choreography-host.ts:72-201`). The remaining risks are boundary behaviors not proven here: a user input event during the programmatic-open window, two AI actors publishing within that window, a followed actor returning to the same route/target, and precise studio path updates after a coarse run-feed update.

Add browser-level tests for those cases. Keep navigation and viewport movement separate from the semantic mutation: choreography may decide whether to show a body, but it must never perform the write.

#### W1-04-F10 — Active-vs-continued run ranking is deterministic but needs a product acceptance rule (P2)

Live Dock filters active runs first, then explicitly continued/open threads, then retained completed tabs, deduplicates by run, prefers active over continuation for the same thread, and sorts by updated time (`live-dock.tsx:532-580`). This is a reasonable default and matches the requirement that an active run remains visible. It needs explicit acceptance tests for: active run + continued thread in the same thread, active runs in two threads, a completed continued thread past retention, and a run waiting for required input. These tests belong to behavior, not dock layout (W1-11).

### Root cause F — Read-only/account and school-boundary metadata needed one small correction

#### W1-04-F11 — Account navigation was incorrectly edit-gated; fixed and regression-tested (P2, fixed)

`app.settings.manage-account` is navigation-only, but its application capability and pre-projection command presentation used the editable availability. It was changed to `readable` in `capabilities/application.ts:151-155` and `commands/app-registry.ts:260-270`. The registry test now asserts it is enabled in a read-only context. Destructive/security commands remain prohibited, and ManageBac mapping remains human-admin-only.

## Next-wave tests and implementation implications

1. **Capability/tool conformance:** for every `APPLICATION_TOOL_COMMAND_MAP` entry, assert command record, tool registry presence when AI-exposed, provider schema, server handler, authority target, and a declared reason for client-only/prohibited/deferred entries. Include negative tests for `insert_reference`-style missing handlers.
2. **Palette resolver unit tests:** interleaved search/action modes; settings-context boost without library exclusion; read-only action visibility; hidden/prohibited action reasons; active vs continued thread ranking; target resolution and stale target removal.
3. **Dispatcher host matrix:** invoke representative actions from `/chat`, `/workspace`, `/library`, `/settings`, `/managebac`, and `/school`; assert one mounted host, one open panel, correct route, and no `APPLICATION_COMMAND_DISPATCHER_UNAVAILABLE`.
4. **Thread routing E2E:** run-only result and thread result on `/chat`; run-only result on side-panel routes; missing/deleted thread; active run required-input state; `/chat` must never render the route side panel.
5. **Async result grammar:** pending/success/error for navigation, library move/delete, settings change, ManageBac sync request, and unavailable handler. Verify action failure retains params and keyboard focus.
6. **Choreography:** route mapping, reduced motion, programmatic-open suppression, direct-input disengagement, two AI actors, repeated route targets, and one-body-per-actor serialization.
7. **School/Bridge acceptance:** Windows and macOS discovery, pair challenge expiry, permission loss, queued offline state, revoke, and reconnect. Test student and teacher peer roles separately; keep school setup, invitations, and ManageBac mapping in admin scopes.
8. **ManageBac acceptance:** verified identity and freshness status, personal sync for permitted users, admin-only mapping, stale/error copy, and palette availability. Do not expose mapping as an AI action.

## Decisions for parent/Pablo

- Treat W1-04 as an audit and contained-wiring wave, not authorization to ship a complete K-bar.
- Use the existing capability IR and application dispatcher as the future palette’s action source. Do not create a second command catalog inside `kbar` or a new action-specific registry.
- Make the application capability schemas real before rendering inline params. The current `z.null()` placeholders are the main protocol debt.
- Require the AI/tool/handler conformance gate before advertising mapped actions as executable. In particular, resolve `insert_reference`, run/thread opening, reveal/picking, and settings/account tool coverage explicitly.
- Keep `/chat` as the primary conversation owner. Route-side conversation is for non-workbench routes only; it must not duplicate ChatShell.
- Keep Bridge/security, account deletion, credential changes, AI authority-mode changes, and provider connections human-only/prohibited. Keep ManageBac mapping admin-only.
- Prefer showing unavailable actions with a concise reason in an explicit action search, while filtering them from default result ranking when they cannot be useful in the current context. Do not let settings context suppress matching library/artifact/chat search.
- Decide whether close, restore, purge, comments, continue, and stop should ever be universal actions only after each has a target, authority, concurrency, and result contract. The current omission is safer than inventing a weak adapter.
