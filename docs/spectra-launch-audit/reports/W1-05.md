# W1-05 — Spectra launch audit: bridge, setup, packaging, and native-file truth

## Result

**Result: NOT READY for the required cross-platform launch.**

The bridge has a credible Windows-oriented core for local-file truth, journaling, claims, conflict handling, recoverable deletion, and policy-controlled structure sync. The browser setup path also has a clear user-facing device/pairing flow. However, the launch bar includes Windows **and macOS**, and the current source/configuration does not yet provide a shippable macOS bundle, signing/notarization/updater path, or runtime proof for macOS writer stability and provider hydration. Hosted production pairing also has a release-configuration gap: the cloud accepts the hosted HTTPS origin, while the bridge defaults to a localhost-only allow-list unless the release environment injects `SPECTRA_ORIGINS`.

Two contained source fixes were made in the assigned bridge/client scope and committed at `9815617f3abb53ed8d3d3b2af47d2880e55fef49`:

- Unix/macOS resource identity now uses device/inode metadata instead of file length, preventing same-sized files from collapsing to one logical resource.
- Named provider roots such as `OneDrive - School` receive the wider stability window used for provider-backed folders.
- Pairing, pairing-status, and bridge-update browser requests now have the same bounded timeout behavior as the rest of the bridge client.

These fixes reduce known risk but do not substitute for the required Mac runtime and release validation.

## Scope and architecture

This audit covers the local bridge, browser setup/client, local journal and filesystem authority, replica/truth policy, watcher/provider behavior, cloud claims, native-file preservation, and desktop packaging. Landing-page behavior is out of scope. Students and teachers are treated as peers; no elevated teacher/admin trust model was assumed.

The effective ownership boundaries are:

1. **Local bridge truth:** `bridge/bridge-core` and `bridge/bridge-app` own the selected grant root, journal, OS file identity, stable-byte reads, local writes, rename/move/delete operations, and startup/watchers.
2. **Cloud replica and claims:** `convex/bridge.ts`, `convex/bridgeSync.ts`, and `convex/replicas.ts` own device/mount registration, cloud resource continuity, missing-resource reconciliation, write/structure claims, stale-claim handling, and policy enforcement.
3. **Browser setup/control plane:** `src/features/spectra/bridge/*` discovers the loopback bridge, pairs a browser origin, selects/removes/retries mounts, exposes storage-policy choices, and shows native-resource/lens state.
4. **Policy layer:** `shared/sync-policy.ts` and `shared/storage-strategy.ts` separate local/cloud materialization from structure mirroring and deletion behavior. The default independent mode preserves local organization; mirroring is explicit.

The important write path is intentionally conservative: the bridge resolves a cloud claim through the journaled grant and relative path, checks the current target identity/hash, refuses stale or externally deleted targets, writes to a temporary file, atomically replaces the target, reads back and verifies the resulting hash, and only then completes the cloud request. Structure operations use collision-safe names and recycle/trash for local deletion rather than silently removing bytes.

### Native preservation and lens boundary

The resource surface explicitly distinguishes the editable Spectra lens from the retained native package and says unsupported Word/Excel/PowerPoint features remain in the original package. The bridge can preserve native OOXML payloads and perform byte/hash-verified writes, but this audit does **not** prove native Office GUI rendering, feature-complete editing, or round-trip fidelity. Those are separate Office-lens acceptance tests. The correct launch claim is preservation and safe synchronization, not full native-app parity.

### Packaging and startup evidence

`bridge/bridge-app/tauri.conf.json` currently declares an active `nsis` bundle and updater artifacts only. The source has Tauri autostart wiring and Windows scheduled-task repair; the bundled autostart dependency has a Mac LaunchAgent implementation in its source, but no signed/notarized Mac app was built or exercised. There is no evidence here for Mac bundle identifiers, entitlements, filesystem permission prompts, notarization, updater artifacts/signatures, uninstall cleanup, or provider behavior inside a packaged app.

The normal bridge UI is hidden/tray-oriented and the browser settings page is the main setup surface. The tray `logs` and `pause` menu branches are currently no-ops, and the embedded “Open logs” button has no handler. This is not a data-integrity failure, but it weakens recovery/support UX during launch.

## Findings

### W1-05-F01 — Unix/macOS resource identity collision — resolved in assigned commit

**Severity:** Launch blocker before fix; residual validation required. **Confidence:** High.

The previous non-Windows implementation used `metadata.len()` as `file_index`. Two same-sized files could therefore share a logical identity and corrupt continuity/adoption decisions. Commit `9815617f3abb53ed8d3d3b2af47d2880e55fef49` scopes Unix hosts separately and uses `MetadataExt::dev()` plus `ino()`. A regression test creates two same-sized files and asserts distinct identities.

The test could not execute on this Windows host because it is `cfg(unix)`. Run it on macOS, including an APFS rename/temp-replace sequence and a provider-backed file, before calling the fix verified for launch.

### W1-05-F02 — macOS stable-byte and arbitrary-writer proof is incomplete

**Severity:** Launch blocker. **Confidence:** High from source; runtime behavior unverified.

Windows uses share-mode behavior to prevent writers during the stable read. The Unix implementation opens read-only and returns `false` from `is_locked`; it does not prove that an arbitrary native writer has stopped or that the file cannot change during hashing. Office owner-lock suppression (`~$`) helps Word/Excel/PowerPoint but does not cover LibreOffice, Preview, image editors, sync clients, or arbitrary native writers.

Required decision/test: either implement a documented Mac-safe writer exclusion/coordination strategy or explicitly fail closed/advisory for unsupported writers. Exercise Word, Excel, PowerPoint, LibreOffice/another writer, a mid-save kill, temp-file replacement, and a save during cloud-to-local write. A stable-byte hash must never be published from a changing file.

### W1-05-F03 — Hosted production pairing depends on unreconciled release environment configuration

**Severity:** Launch blocker for hosted setup. **Confidence:** High.

The bridge server defaults `SPECTRA_ORIGINS` to `http://localhost:3000,http://127.0.0.1:3000`. The cloud pairing path accepts HTTPS or localhost browser origins and returns the actual hosted origin, but the local bridge process still checks its allow-list. The app also requires `SPECTRA_CONVEX_URL` at startup/pair completion. No packaged release configuration, installer injection, signed config, or first-run configuration path was found that guarantees these values are present and correct.

Add a release-owned configuration path and test the real hosted browser origin: install, start, pair, resume, reload, revoke, and re-pair. Do not broaden origins with a wildcard.

### W1-05-F04 — macOS desktop packaging/distribution is not launch-complete

**Severity:** Launch blocker. **Confidence:** High.

Tauri is configured with an `nsis` target only. There is no Mac `.app`/DMG target, signing/notarization configuration, CI build, signed updater artifact, or uninstall/upgrade evidence in the inspected source. Mac is a stated launch requirement, so this is a current missing capability, not a post-launch enhancement.

Add the Mac target and release pipeline, codesign/notarize it, verify keychain access, filesystem prompts, LaunchAgent behavior, updater signatures, install/upgrade/uninstall cleanup, and run the packaged app against hosted pairing and a real provider-backed folder.

### W1-05-F05 — Provider detection is improved, but OneDrive/Files On-Demand hydration is unproven

**Severity:** High. **Confidence:** High for the test gap; medium for provider-specific runtime behavior.

The source now recognizes `OneDrive - School`, `Dropbox - ...`, and `Google Drive - ...` folder names and applies the wider stability window. That is only a path heuristic. It does not prove Windows Files On-Demand placeholder hydration, reparse behavior, offline availability, partial hydration, or the equivalent Mac provider behavior.

Run real provider tests for an online-only placeholder, hydration during scan, hydration during read/hash, provider temp-file replacement, offline disappearance, reconnect/remount, and a cloud update targeting a placeholder. The bridge must preserve logical work and retry/await rather than silently deleting or publishing incomplete bytes.

### W1-05-F06 — Replica/claim policy is conservative in source, but clone and external-organization acceptance is missing

**Severity:** High for launch confidence. **Confidence:** High on source behavior; low on cross-device runtime evidence.

The source preserves missing resources as unavailable/awaiting/restore-to-disk according to policy, does not automatically delete local bytes on ordinary disappearance, requires approval for spectra-to-disk deletion, uses collision-safe names, and keeps default structure independent unless an explicit mirror mode is selected. Claims are resource/mount/device scoped, stale target hashes conflict, and device revocation fails queued claims/replicas.

Still required: two devices with the same grant; local copies renamed/moved/deleted outside Spectra; cloud-side rename/move/delete; offline edits on both sides; reconnect/remount; clone-like folder copies; and collision cases. Verify that local organization remains independent by default, that explicit mirror modes do exactly their selected direction, and that a vanished/reappearing mount never turns into an unintended delete or duplicate logical resource.

### W1-05-F07 — Fixed-port bind failures are not surfaced as a reliable “port taken” state

**Severity:** Important. **Confidence:** High from source inspection.

The browser schema accepts `health.bindError`, but health interpretation treats a valid JSON health response as a running bridge and does not map `bindError` to the “port taken/connection blocked” state. Since the bridge binds fixed `127.0.0.1:47615`, another process can make startup fail while the setup UI reports a less actionable running/not-connected condition.

Add a deterministic port-conflict test and surface the bind error with a remediation path. Keep the loopback binding and origin checks; do not silently switch ports without a discovery/authorization design.

### W1-05-F08 — Setup/update requests now have bounded timeouts; browser integration tests remain unavailable

**Severity:** Important for setup resilience; contained fix complete. **Confidence:** High.

`/v1/update`, `/v1/pair`, and `/v1/pair/status` now use the bridge client timeout signal in the assigned commit. This closes a hang risk in first-run setup and update flows. The intended Vitest bridge-contract/sync-toggle run could not start because the worktree’s JS dependency environment lacks `vite`; no browser test pass is claimed. Restore the supported dependency environment and add assertions for timeout, port conflict, origin rejection, pairing expiry, resume, and update-unavailable states.

### W1-05-F09 — Recovery/support affordances are incomplete

**Severity:** Small but user-facing. **Confidence:** High.

The tray exposes Logs and Pause entries, and the embedded bridge page exposes “Open logs”, but both code paths are no-ops in the inspected source. This makes failures harder to diagnose during school setup. Wire these actions to a real log view/export and pause/resume state, or remove the affordances until implemented.

### W1-05-F10 — Mac folder-picker copy is inaccurate

**Severity:** Small. **Confidence:** High.

The browser setup text says Windows is the platform that shows the native folder picker when adding a folder, while the Tauri dialog path is intended to be cross-platform. Correct the copy and test the Mac permission prompt plus selected-root persistence. Do not change the actual user autostart configuration as part of this audit.

### W1-05-F11 — Notion is a future adapter, not a current bridge capability

**Severity:** Future scope. **Confidence:** High.

No Notion connector or live Notion API/auth path is present. The current abstraction could host a later provider adapter if it maps provider object identity, capabilities, claims, revisions, and conflict semantics without pretending a remote page is a native filesystem byte stream. Notion should remain deferred; do not rewrite the bridge protocol for it during this launch pass.

## Decisions

- **Cross-platform bar:** Windows and macOS are both required for launch; Mac packaging, signing, updater, permissions, provider behavior, and writer stability are launch gates.
- **Truth boundary:** local file identity, journal, safe writer, and claim-target verification remain authoritative locally; cloud is a replica/coordination layer with explicit claims and policy.
- **Clone/organization policy:** keep local organization independent by default; only explicit mirror modes may mirror structure. Preserve missing logical resources and require approval for destructive spectra-to-disk deletion.
- **Native files:** retain native bytes and surface a lens where supported; do not promise Office GUI parity from bridge evidence.
- **Notion:** defer until a real connector/adapter can define identity and claim semantics; no bridge-protocol rewrite now.
- **Release configuration:** make hosted origin and deployment URL explicit, validated release inputs; never rely on localhost defaults for production pairing.
