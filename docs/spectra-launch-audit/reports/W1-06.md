# W1-06 — DOCX native projection, merge, and fidelity audit

## Result

The linked DOCX path has a sound preservation-first boundary, but it is not a full Word editor. docxLens can safely write existing ordinary body paragraphs, existing safe table-cell text, existing style IDs, and a bounded set of run/paragraph properties. It preserves the rest of the package as carry data and refuses operations whose native OOXML writer is not modeled.

One destructive gap was found and fixed: native Word comment anchors were omitted from the paragraph/table read-only guards. A replacement could therefore move the first writable run across comment range markers and change the semantic span of comments while leaving the comments part and marker counts intact. The fix is in commit aabf214e (Protect native DOCX comment ranges).

The major launch limitation is architectural rather than an accidental data-loss bug: DOCX import and DOCX export in document-studio.tsx are separate, lossy copy workflows. They do not constitute linked native-package round-trip support. “Preserved” below means untouched package XML/parts, not editable or fully rendered parity.

## Scope and current architecture

- Baseline: 43c45cc557942ccfb4f806092a61b6950dcdf2f3 (primary main, detached worktree).
- docxLens.open() opens the package, adds stable paragraph identifiers where safe, projects body paragraphs/tables/rich OMML/images, and returns the original payload in preservedCarry.
- docxLens.materialize() emits only lens-valid operations. The modeled writer changes /word/document.xml; unrelated package parts are preserved and external diffs report them as preserved-part replacements.
- Strict-native fidelity is deliberately pessimistic for images, equations, footnotes/endnotes, headers/footers, sections, fields, hyperlinks, comments, lists, and tracked changes. The command registry and AI operation gate share the same refusal sentence and region map.
- Spectra-native equations/images/citations are represented in the shared projection/ProseMirror model, but those nodes are not a promise that linked Word OMML/drawingML/field structures can be authored.
- DOCX import uses Mammoth to create an independent editable Spectra copy and retains the original import. DOCX export uses the docx package to generate a new simple package from editor text/headings/quotes and reference fallbacks; it is not a native merge back into the source package.

## Findings grouped by root cause

### W1-06-F01 — Comment anchors were not part of the native safety boundary — fixed

Severity: P1 before fix. Confidence: high. Status: fixed in aabf214e.

projectDocument() checked revisions, fields, content controls, hyperlinks, rich objects, and OMML, but omitted commentRangeStart, commentRangeEnd, and commentReference in both paragraph and table-cell checks. In the macro-enabled fixture, the first paragraph containing “On the Insert tab” was therefore editable. The existing replacement algorithm consolidates writable text into a run; when the paragraph contained comment markers, this changed the ranges’ semantic coverage without changing the comments part or marker count.

The fix adds all three comment-anchor elements to both guards and updates the refusal explanation. The new regression asserts projection as nativeReadOnly and refusal with DOCX_REGION_READ_ONLY. The direct probe reproduces the fixed result; the full harness remains green.

### W1-06-F02 — Linked native DOCX and import/export copies are different contracts

Severity: P1 launch clarity/coverage. Confidence: high.

The linked lens preserves native package structure and has a bounded native writer. The regular document import path uses Mammoth HTML conversion, and the export path constructs a fresh DOCX from TextRun(block.text) plus a small heading/quote mapping and reference PNG/URL fallback. The code does not round-trip Word run marks, OMML, linked ranges, comments, tracked-change authorship, fields, headers/footers, sections, theme/style provenance, drawing placement, or complex table structure through that copy path.

The UI copy is honest (“separate editable copy” and retained original), but acceptance criteria must not call this a DOCX round trip. A launch test should label linked-open preservation and copy import/export as separate flows.

### W1-06-F03 — Preserved XML parts are not functional parity

Severity: P1 expectation/UX risk. Confidence: high.

The region map deliberately reports PRESERVED for equations, images, lists, hyperlinks, fields, comments, tracked changes, notes, headers/footers, sections, and table structure. This is the correct safety result, but it means “visible in the package” does not imply “editable in Spectra,” “re-rendered identically in the browser,” or “writeable by native commands.” Equations are a concrete example: KaTeX projection is useful display evidence, but there is no reverse OMML writer. OLE/SmartArt/macros are preserved payloads, not editable objects.

The command registry and AI operation gate use the same actionable refusal: “Spectra preserves <region> in this file but cannot edit it yet. Open the original file in its native app to make this change.” That preserves truth and gives a next action. The remaining UX risk is accumulation: a feature-rich Word file can show many disabled commands. The next UI pass should group/summary the preserved regions and keep supported body controls prominent; it must not hide the reason or silently enable a destructive fallback.

### W1-06-F04 — Font-family write coverage is incomplete for East Asian/custom names

Severity: P2. Confidence: high from source inspection; not yet proven by a fixture mutation.

applyRunFormat() writes ascii, hAnsi, and cs, and clears their theme counterparts, but leaves eastAsia/eastAsiaTheme untouched. A CJK paragraph can therefore retain its prior East Asian font after a user selects a different family. safeFontName() also accepts only the ASCII-oriented ^[\w .+&'-]{1,64}$ form, rejecting valid Unicode font-family names. Existing ordinary font tests cover literal Latin family/size/toggle behavior, not this East Asian/theme case.

Remedy: add a fixture with w:eastAsia/w:eastAsiaTheme, test effective projection and mutation across CJK text, define whether the family command intentionally controls all script slots, and safely support/validate Unicode family names. Keep this as a contained lens fix; do not redesign shared projection IR in this wave.

2. Add East Asian/theme-font fixtures, mixed direct/style/theme formatting, custom Unicode family names, explicit w:szCs, and script-specific runs. Assert effective display data and exact writer deltas.
3. Add browser tests against linked files for read-only badges/placeholders, disabled command language, safe body edits beside equations/comments/fields, and two-session collision behavior. Verify that disabled controls do not obscure supported body editing.
4. Windows native-package scenario: on a copied fixture, open/save in Microsoft Word on Windows, compare package parts before/after, inspect equations/comments/fields/headers/sections/revisions, then edit one safe paragraph in Spectra and reopen in Word. Test accept/reject revisions and update fields in Word as the native handoff.
5. macOS native-package scenario: repeat the same copied-fixture matrix in Word for Mac, including a file created/saved on Windows, and compare comment anchors, OMML, theme fonts, section properties, and tracked-change metadata. The bridge must exercise open/edit/save, not merely package unzip checks.
6. Add rendered visual QA in environments with Word or LibreOffice available. This worktree could not render because soffice.exe was unavailable; no visual parity claim is made here.
7. Treat regular Mammoth import and fresh docx export as a separately documented “adapted copy” contract. Add fixture assertions for the features intentionally reported as adapted/unsupported so future export changes cannot be mistaken for native merge support.
