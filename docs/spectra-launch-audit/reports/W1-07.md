# W1-07 — Spreadsheet and Excel fidelity

## Result

Spectra has a credible sparse-sheet editor and a deliberately conservative native XLSX lens. Cell values, supported formulas, cell styles/number formats, merges, and freeze panes have native write paths; unsupported Excel formulas are represented as cached-only rather than silently recalculated. The model also has on-demand calculation and bounded sparse storage that are appropriate starting points for student workbooks.

The launch risk is the boundary between those two modes. Clean `.xlsx` import through the in-app ExcelJS reader currently drops Excel's cached formula result and does not classify unknown formulas as cached-only. Native mounted workbooks preserve a broad set of Excel package features, but charts, tables, validation, conditional formats, names, pivots, comments, worksheet dimensions/visibility, filtering, and sheet lifecycle are preservation-only. Some model formula semantics and virtualized-grid edge cases still need adversarial coverage. These are material for student trust, especially when a workbook looks intact but a value or native feature is not editable in Spectra.

Small source fixes completed in this wave:

- `INDEX(range, row, column)` now uses both coordinates for two-dimensional ranges.
- Formula-support classification is shared by the native lens and content-to-projection path, so replacing a cached-only native formula with `SUM` or vice versa updates its support class.
- Freeze-row and freeze-column changes merge independently in three-way native projection merges.
- Added regression tests for all three fixes.

The source fixes are committed in the isolated worktree as `c7d91db0` (`fix sheets formula support and native merges`).

## Scope and current architecture

The inspected flow is:

| Layer | Path | Role |
| --- | --- | --- |
| editor/grid | `<local-workspace>` | selection, viewport virtualization, editing, clipboard, import/export, native-mode UI |
| model/engine | `<local-workspace>` | workbook schema, normalization, formula parser/evaluator, cached-only behavior, formatting, structural mutation |
| pure operations | `<local-workspace>` | paste/fill/sort/validation/value parsing/staleness and formula-safe cell operations |
| reference rewriting | `<local-workspace>` | row/column insertion/deletion and sheet rename reference updates |
| sparse storage | `<local-workspace>` | 256-entry chunks at storage boundaries; legacy maps remain readable |
| XLSX lens | `<local-workspace>` | native OOXML projection, fidelity map, native operations, package-part preservation |
| content bridge | `<local-workspace>` | projection/content conversion and native delta generation |
| native merge | `<local-workspace>` | three-way merge for cell/style/merge/freeze/name projection data |
| commands | `<local-workspace>` | spreadsheet command registry, formula catalog, view commands |

The editor model carries cell values, formulas, formula support (`recognized`/`cached-only`), cached-stale state, font/fill/border/alignment/number formats, notes, validations, tables, charts, hidden rows/columns, dimensions, merged ranges, conditional formats, freeze panes, tab visibility, protection, identities, workbook date system, locale/timezone, and named ranges. The native projection is intentionally narrower: cells/formulas/styles/number formats/merges/freeze panes are native; the rest is either preserved or rejected as a native edit.

Calculation is split correctly for scale: `sheetsCalculation()` evaluates on demand when the grid asks for a cell, while `calculateWorkbook()` is eager for export and tests. The model supports a useful but finite Excel-like function set. A formula outside the native recognized set can remain visible from Excel's cached value and is marked stale when its precedents change; it is not silently re-evaluated by Spectra.

## Findings

### W1-07-F01 — Clean `.xlsx` import drops cached formula results

- Severity: Important
- Confidence: High
- Code chain: `<local-workspace>`
- Evidence: ExcelJS formula values arrive as an object containing `formula` and `result`. The importer reads `valueRecord.formula`, sets `value = undefined`, and never reads `valueRecord.result` or sets `nativeFormulaSupport: "cached-only"`. The native lens fixture probe independently confirms the same class of workbook can carry a cached XLOOKUP result.
- User impact: importing a normal clean `.xlsx` containing `XLOOKUP`, `FILTER`, or another unrecognized formula can show `#NAME?` instead of the value Excel last calculated. The user is warned about charts/conditional formats, but not about this loss of cached formula output.
- Recommended remedy: preserve `valueRecord.result` when present; classify imported formula text with the shared `xlsxFormulaSupport`; set `nativeFormulaSupport: "recognized"` only for the supported native set and `cached-only` otherwise; preserve the result as the displayed value. Add an ExcelJS fixture test for an unsupported formula and a stale-precedent edit test. Do not invent a recalculation result in the browser.

### W1-07-F02 — Native XLSX feature map is broad preservation, not edit parity

- Severity: Important
- Confidence: High
- Code chain: `<local-workspace>` and native operation generation in `<local-workspace>`.
- Evidence: the lens marks cells, formulas, styles, number formats, merges, and freeze panes `NATIVE`. Charts, tables, validation, conditional formats, named ranges, pivots, comments, sheet structure, dimensions, sheet views/metadata, calculation settings, and sort/filter are marked `PRESERVED`/read-only. `xlsxOperationsBetween()` emits operations only for cells, formats, merges, and freeze panes.
- User impact: a student can see a workbook's native chart/table/comment/pivot and assume edits in Spectra will update it. Cell edits remain safe, but changing a table range, named range, sheet name/order/visibility, row/column dimensions, filter, or chart source is not a supported native write. A model/content change can therefore be silently outside the saved native delta unless the UI blocks it or reports the preserve-only boundary.
- Recommended remedy: keep the preservation boundary, but make it explicit at the command surface. Disable or clearly label native-incompatible commands for names, sheet topology/rename, dimensions/visibility, filters, table structure, and chart source changes; add a native round-trip status panel showing preserved-only regions. If edit parity is needed, add explicit operation kinds and package-level tests rather than relying on projection diffs that currently ignore these fields.

### W1-07-F03 — Formula semantics are intentionally partial but several lookup modes are misleading

- Severity: Important
- Confidence: High
- Code chain: `<local-workspace>`; formula catalog in `<local-workspace>`.
- Evidence: `XLOOKUP` handles a basic exact lookup and optional not-found value but ignores search/match modes. `MATCH` uses exact `findIndex` and ignores `match_type`. `VLOOKUP`/`HLOOKUP` find exact rows/columns, then return `#N/A` for both approximate and missing cases instead of implementing Excel approximate matching. The command catalog advertises these names, while the native lens deliberately treats them as cached-only when imported from Excel.
- User impact: formulas created or edited in Spectra can look valid while producing a different result from Excel for common optional arguments or approximate lookup behavior. This is especially risky in student gradebooks and lookup tables where a formula result drives a visible score.
- Recommended remedy: either implement the documented mode semantics or reject/mark unsupported argument combinations as cached-only. Add adversarial tests for sorted approximate VLOOKUP/HLOOKUP, MATCH `-1/0/1`, XLOOKUP `if_not_found`, `match_mode`, and `search_mode`, plus Excel expected-value fixtures. Keep error values visible and stable.

### W1-07-F04 — Native named-range and sheet-structure edits are not represented in the XLSX delta

- Severity: Important
- Confidence: High
- Code chain: projection includes names at `<local-workspace>`; native delta is `<local-workspace>`.
- Evidence: names are projected and the three-way merge can conflict on `xlsx:defined-names`, but `xlsxOperationsBetween()` never emits defined-name operations. It also iterates existing sheet IDs only and emits no sheet rename/reorder/visibility or worksheet lifecycle operation. The lens fidelity map calls those regions preserved/read-only, yet the editor model and commands expose named ranges and sheet view/topology concepts.
- User impact: a user can make a content-level named-range or sheet-identity change in the editor model that does not become a native package operation. On save, the native workbook may retain the old name or sheet metadata while nearby cell edits succeed, creating a confusing partial save.
- Recommended remedy: gate these commands when `nativeBinding` is present until native operation kinds exist, or implement explicit atomic operations with package tests. Add a test that attempts rename/name changes on a mounted workbook and asserts a stable refusal rather than a silent no-op.

### W1-07-F05 — Virtualization is good for sparse content but still scales some arrays with declared dimensions

- Severity: Important
- Confidence: Medium
- Code chain: `<local-workspace>` and `2420` in `model.ts` for structural data; `<local-workspace>` for bounded storage.
- Evidence: visible rows, row offsets, column offsets, hidden-row filtering, and viewport mapping are computed from the declared bounds. Sparse cells are stored efficiently and calculation is lazy, but a workbook with inflated row/column dimensions can still produce large visible-index/offset arrays. Selection walks are bounded by `RANGE_WALK_LIMIT = 200,000`; oversized ranges intentionally collapse to a safe start address rather than attempting an unbounded bulk operation.
- User impact: a malicious or merely messy workbook with a huge used range can make the browser allocate or iterate much more than its occupied cell count. A very large selection may also appear to succeed while operating only on the start cell when the limit is exceeded.
- Recommended remedy: benchmark real 100k/200k sparse and dense files in Chromium on Windows and Safari/Chromium on macOS. Use occupied-cell/viewport windowing for extreme declared dimensions, show an explicit “selection too large” state instead of silently reducing the operation, and measure paste/fill/sort latency separately from open latency.

### W1-07-F06 — Merged-cell height can be wrong when hidden rows are inside the merge

- Severity: Important
- Confidence: High
- Code chain: `<local-workspace>`.
- Evidence: the grid maps raw row numbers through `visibleRowIndices`, but merged height uses `rowOffsets[position + (end.row - start.row) + 1]`. If a hidden row lies inside the merged range, raw span and visible-position span differ; if the end offset is beyond the visible array the result can be undefined.
- User impact: merged headers that span hidden rows can render with incorrect height, overlapping cells, or a clipped body. This affects common report layouts and is a visual fidelity issue even when the underlying OOXML merge is preserved correctly.
- Recommended remedy: resolve the merged range to the last visible row at or before its raw end, then use that visible position for the height. Add a render regression for `A1:A4` with row 2 hidden, plus a frozen-row variant.

### W1-07-F07 — System clipboard is values-only across Excel boundaries

- Severity: Important
- Confidence: High
- Code chain: internal rich clipboard in `<local-workspace>`; system clipboard helpers and paste flow are in the same component around the keyboard/clipboard handlers.
- Evidence: internal `ClipboardBlock` retains formulas and formats for copy/paste within Spectra. The system clipboard path calls the text copy/paste helpers, which exchange delimited text. External Excel paste therefore cannot carry formula text, cell formats, validation, merged ranges, tables, or charts into the rich editor path.
- User impact: copying a formula block from Excel into Spectra can paste displayed text or values rather than formulas, and copying styled cells loses formatting. Copying from Spectra to Excel is likewise a text interchange, which is surprising for an Office-facing surface.
- Recommended remedy: support an explicit tabular interchange mode with formula text and a warning, or add a browser clipboard MIME payload where available. At minimum, label external paste as values-only and keep internal rich paste visibly distinct.

### W1-07-F08 — Native visual features are preserved in the package but not represented in the editor canvas

- Severity: Important
- Confidence: High
- Code chain: native fidelity entries in `<local-workspace>`; clean import initializes `tables`, `charts`, and `conditionalFormats` empty at `<local-workspace>`.
- Evidence: fixture parts exist for charts, tables, comments, diagrams, images, ActiveX/VML, and conditional-formatting parts. The native lens preserves those unknown/native parts, while the clean import path explicitly imports no charts/tables/conditional-format rules and reports those caveats.
- User impact: a workbook may round-trip safely at the package level while the Spectra surface cannot show or edit the native object. Conversely, clean import can produce a visually much simpler workbook than the source even though the cell values look correct.
- Recommended remedy: distinguish “preserved but not rendered” from “not imported” in the import notice and native status UI. Add a package-to-canvas acceptance matrix for charts/images/comments/tables and never claim visual parity from package-part preservation alone.

### W1-07-F09 — Date and locale fidelity needs an explicit policy

- Severity: Small
- Confidence: Medium
- Code chain: native date serial handling in `<local-workspace>`; editor content conversion in `<local-workspace>`; import number-format inference in `<local-workspace>`.
- Evidence: the native lens honors workbook `date1904` when converting dates to serials, and the model carries locale/timezone metadata. Clean import maps dates to JavaScript millisecond values and reduces number formats to `date`, `percent`, `currency`, or `general`; it does not preserve the source format code or workbook locale. The content bridge defaults editor projection locale to `en-US` in the current path.
- User impact: dates can display differently from Excel for locale-specific formats, ambiguous day/month input, or custom formats, even if the underlying serial is correct. This is a likely cross-platform discrepancy between Windows regional settings and macOS/browser locale.
- Recommended remedy: preserve the OOXML format code and date system on import, define whether display follows workbook locale or browser locale, and add fixtures for 1900/1904 systems, serial 0/60 edge cases, custom date formats, and `dd/mm` versus `mm/dd` display on both launch platforms.

## Next-wave tests and implementation implications

1. Add a real ExcelJS import fixture with an unsupported formula and cached result; assert that the displayed value survives import, the formula is marked cached-only, and a precedent edit marks it stale without inventing a result.
2. Add native package round trips for named-range edits, sheet rename/order/visibility, row/column dimensions, filters, table ranges, comments, and chart source changes. Each should either emit a native operation or return a stable refusal.
3. Add formula adversarial tests against Excel expected values for lookup modes, date serials, error propagation, absolute/mixed references, whole-row/whole-column ranges, and cross-sheet names.
4. Add render tests for merged ranges containing hidden rows/columns, frozen panes intersecting merges, wrapped text, row-height overrides, and hidden rows near the viewport boundary.
5. Run a browser performance matrix with sparse 200k-cell, dense 200k-cell, and inflated-dimension workbooks. Capture open, first paint, scroll, edit, paste, fill, sort, and export timings on Windows and macOS.
6. Exercise the system clipboard against Excel/LibreOffice/browser text sources and document the rich-versus-values-only contract in the UI.
7. Add visual acceptance for the fixture matrix. Native package preservation must be paired with a canvas/preview statement: preserved-only objects should be visible as such, not presented as fully editable.

## Decisions for parent/Pablo

- Treat native XLSX support as “safe cell editing plus package preservation,” not general Excel editing, until the preserve-only commands are gated and surfaced.
- Prioritize F01 before student-facing clean `.xlsx` import; losing a cached result is a direct trust failure.
- Prioritize F04 alongside any native workbook editing UI; silent no-op deltas for names or sheet identity are more dangerous than an explicit refusal.
- Do not make launch claims about charts, tables, pivots, comments, ActiveX, conditional formatting, or images based only on preserved package parts. They need preview/render evidence.
- The current source fixes are low-risk and independently tested, but the full TypeScript check and live browser/Excel/macOS acceptance remain open.
