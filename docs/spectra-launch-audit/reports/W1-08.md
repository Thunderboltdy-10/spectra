# W1-08 — Presentation and PowerPoint fidelity

## Result

The native PPTX lane is strong for its deliberately narrow contract: the current Open XML harness passes, native title/text/notes/geometry/slide-order operations read back, and unrelated transition, timing, master, media, chart, notes, and OLE parts survive the tested writes. The strict-native command surface is unusually honest about what it cannot author.

The browser presentation lane is not yet a PowerPoint-fidelity editor. It has three different representations—native OOXML, a flattened browser scene model, and a separate export renderer—and they do not share enough of the same typography, layout, shape, chart, or inheritance semantics. A user can safely edit a bounded native subset and create a good Spectra-native deck, but “import PPTX → edit → export with visual/editability parity” is not a launch-safe promise.

I made three small, contained fixes in commit `f9cccf7e`:

- imported PPTX slides now follow `p:sldIdLst` relationship order instead of lexicographic/numeric slide-part order;
- copy-on-write presentation mutations clone nested theme/style/source/animation records, so theme styling no longer mutates the prior deck/undo snapshot;
- PPTX and canvas export resolve the known Spectra CSS color tokens instead of slicing `var(--token)` into invalid color strings.

These fixes reduce correctness hazards but do not close the larger renderer and feature-model gaps below.

## Scope and current architecture

The presentation feature has two materially different lanes:

1. `src/features/spectra/presentation/model.ts` defines a logical 1000-unit canvas, 750-unit 4:3 height or 562.5-unit 16:9 height, scene objects, theme tokens, notes, citations, source bindings, transitions, animations, and accessibility metadata. `presentation-studio.tsx` renders this as editable DOM/CSS.
2. `src/features/spectra/presentation/io.ts` imports PPTX/ODP into the scene model and separately writes PPTX/ODP/PDF/PNG. Its canvas renderer is an independent hand-written renderer, not the DOM layout engine.
3. `src/features/spectra/lenses/pptx-lens.ts` opens native OOXML through `@ariadng/office`, projects only a semantic subset, and materializes a small set of native XML writes while raw-copying preserved parts. `office-content.ts` translates editor content into that subset.
4. `presentation-commands.ts` gates operations by compatibility profile. The strict-native surface permits title/text, basic text-box insertion, notes, hidden slides, alt text, geometry, slide add/delete/reorder; theme/layout/background/shape style/chart data/table/media/embed/equation/transition/animation operations are refused or deferred for linked files.

That split is appropriate for preservation, but the UI needs to make the lane boundary as prominent as the command gating. The native projection is not the same thing as a fully editable PowerPoint document.

## Findings grouped by root cause

### W1-08-F01 — The browser PPTX import is a lossy scene conversion, while the native lens is a preservation projection

- Consequence: imported decks can look materially different and unsupported native objects become replacement placeholders. A chart, SmartArt graphic, or complex table that was editable in PowerPoint is not editable after browser import; its original package is retained only as a separate preservation concern. Rich runs, paragraph formatting, theme fonts/colors, master inheritance, per-slide transitions, and native shape semantics are largely absent from the browser scene model.
- Severity / confidence: High / High.
- Repro: `parsePptx()` in `src/features/spectra/presentation/io.ts:249-366` creates text from concatenated `a:t`, applies one default style, creates pictures, and turns every `p:graphicFrame` into a `type: "shape"` placeholder. It assigns `layoutId: "imported"` and `transition: { kind: "none" }`. The focused test proves the slide-order part of the issue with a real PPTX package; the feature flattening is directly visible in the importer.
- Code chain: `importPresentationFile()` → `parsePptx()` → `normalizePresentationContent()` → `PresentationObjectView`. The native path instead classifies `sp`/`pic`/`graphicFrame` in `pptx-lens.ts:76-99`, retains the source payload, and reports chart/table/SmartArt/equation regions as preserved/read-only.
- Evidence: the chart/notes fixture passes native preservation in the harness, but the browser importer advertises `PowerPoint charts, SmartArt, and complex tables` as unsupported. This is the correct disclosure; it must not be described as editable PPTX import.
- Neighbors: the model has no `equation` object type; groups are represented by IDs but the native projector flattens descendants; ODP import also uses a simpler frame model. Media bytes are collected, but browser conversion is still a scene substitution.
- Remedy: keep the native lane and browser lane explicit. If browser import is promoted, add a feature-by-feature conversion contract for rich text/runs, placeholder inheritance, groups, crop/mask, hyperlinks, charts, tables, equations, audio/video, and transitions. Otherwise label it “editable Spectra copy; original PowerPoint features preserved in source” and require an explicit lossy-import decision.

The slide-order subcase is fixed in `io.ts:126-157`: relationship IDs in `ppt/presentation.xml` are resolved through `presentation.xml.rels`, with a safe numeric fallback and append of any unlisted valid slide parts.

### W1-08-F02 — Editor, static renderer, and PPTX exporter use different layout and paint semantics

- Consequence: the authoring canvas, PDF/PNG output, and PPTX output can disagree on background, color, font, wrapping, shape geometry, tables, groups, and unsupported objects. Before the fix, a token such as `var(--accent-mint)` was sliced to `var(--`, and a token background was invalid for both PptxGenJS color fields and the canvas 2D context.
- Severity / confidence: High / High.
- Repro: `buildPresentationPptx()` at `src/features/spectra/presentation/io.ts:644-717` and `renderPresentationSlide()` at `io.ts:780-880` are independent renderers. The canvas path hardcodes `Georgia`, uses `fillText(..., maxWidth)` rather than wrapping, and falls back to `[type]` for non-text/shape/image/chart objects. The PPTX path uses PptxGenJS defaults and `fit: "shrink"`; it does not consume the DOM’s actual text metrics. The export regression test catches token color emission.
- Code chain: `PresentationObjectView` uses CSS custom properties and browser layout (`presentation-studio.tsx:549-850`), while PDF/PNG call `renderPresentationSlide()` and PPTX calls `buildPresentationPptx()`. There is no shared line-break, font-resolution, shape, crop, or layout measurement service.
- Evidence: the token export assertion now passes after the isolated normalization fix. The native harness proves package preservation only and cannot prove the three visual paths are equivalent.
- Neighbors: `buildPresentationOdp()` serializes every object as a text frame (`io.ts:721-778`), so ODP is intentionally far below PPTX fidelity. PDF is a rasterized JPEG of the independent canvas renderer, so accessibility and native object editability are not retained.
- Remedy: establish one presentation layout/paint contract and reuse it for editor preview, raster output, and native export. At minimum resolve theme tokens from a canonical palette, use the selected heading/body fonts, implement the same wrapping/fit rules, and add golden slide renders for text, shape, image, chart, table, group, 4:3, 16:9, dark mode, and long-script cases.

The known Spectra token path is now safe in the commit: `PRESENTATION_EXPORT_COLORS`/`presentationPaint()` at `io.ts:544-592` normalize hex, RGB-like canvas paints, and the shipped CSS tokens. Arbitrary or `color-mix()` values still fall back rather than being evaluated, so this is a correctness guard, not full CSS paint fidelity.

### W1-08-F03 — Charts and rich objects are visually approximated, not consistently native/editable

- Consequence: a user can see a chart-like bar graphic in Spectra, but the PPTX export does not contain a PowerPoint chart object with series, categories, axes, labels, source binding, or an embedded workbook. A subsequent PowerPoint user cannot edit the data as a chart. Tables are basic `addTable()` output in export and browser HTML display; imported native tables/charts are preserved rather than edited. Requested shape types and group transforms also do not survive all paths.
- Severity / confidence: High / High.
- Repro: `buildPresentationPptx()` at `io.ts:703-716` loops over values and emits `pptx.ShapeType.rect`; `PresentationObjectView` at `presentation-studio.tsx:735-778` renders bars as spans without axes/labels. `pptx-lens.ts:89-99` classifies native graphic frames but only stores flattened text/native identity, and `office-content.ts:834-971` emits no chart-data, table-cell, group, or shape-style operations.
- Code chain: `createPresentationObject("chart")` creates `{ labels, values, chartType }` in `model.ts:292-301`; `realizeGeneratedPresentation()` can place it and audit it, but the export branch reduces it to rectangles. `insert.chart` is correctly refused in strict-native mode at `presentation-commands.ts:818-829`, and `PRESENTATION_STRICT_REASONS.newChart` states the limitation.
- Evidence: native chart/embedded-workbook parts are structurally identical in the current chart/notes harness fixture. That proves preservation, not chart editability. The presentation skill promises chart binding, but the PPTX writer currently has no native chart writer.
- Neighbors: `table` is a scene object and browser HTML table but has no cell-edit command in the native lens; `embed` is a Spectra-only linked artifact and is correctly blocked in strict native; video/audio/media are constrained by the browser asset conversion path.
- Remedy: choose one of two explicit contracts: (a) implement real PptxGenJS/native chart/table writers with source lineage and readback assertions, or (b) call these “visual chart/table snapshots” in exports and never imply native editability. Add chart series/labels/axis/alt-text tests and a PowerPoint readback test before promoting chart creation.

### W1-08-F04 — Theme, font, master, and layout inheritance is preserved natively but not projected semantically

- Consequence: the linked file can preserve its branded masters/layouts, yet the Spectra canvas may not render the same inherited font, fill, placeholder style, alignment, or title/body hierarchy. New browser-exported text uses the body font for every text object; the browser view does not apply `fontFamily` from object style. Imported slides receive a synthetic `pptx-import` theme with no extracted font/color tokens.
- Severity / confidence: High / High.
- Repro: `parsePptx()` returns `theme: { id: "pptx-import", name: "Imported PowerPoint" }` and per-shape defaults at `io.ts:347-366`. `pptxArtifactContent()` returns only `theme: { id: "native-pptx", name: "PowerPoint theme" }` in `office-content.ts:462-471`. `pptx-lens.ts:29-55` resolves a shape transform or one layout placeholder but does not read theme font/color mappings or master fallback. `PresentationObjectView` at `presentation-studio.tsx:651-674` applies size/weight/italic/alignment but not `fontFamily`.
- Code chain: native `deck.slides()` → `slide.layoutPartName` → one-level placeholder lookup → flattened `PresentationObject`; browser DOM and PPTX exporter then apply their own defaults (`Manrope`/`Aptos`/`Georgia`). `addTextBox()` in `pptx-lens.ts:429-436` writes an empty run property element rather than a semantic style operation.
- Evidence: masters and layouts remain byte-identical in the native harness; this is a preservation win. No current evidence proves that the same deck looks identical in Spectra or that newly inserted native text inherits the intended master theme in every PowerPoint layout.
- Neighbors: strict-native commands correctly refuse theme/layout/background/slide-size changes (`office-reasons.ts:68-120`); native slide add deliberately reuses an existing layout, which is the right preservation choice.
- Remedy: expose a read-only semantic theme snapshot for linked decks—resolved heading/body fonts, palette, master/layout/placeholder provenance—and render it in Spectra. For generated decks, pass heading/body font choices through DOM, canvas, PPTX, and ODP. Add inherited-placeholder fixtures with non-default fonts, fills, title styles, 4:3 geometry, and a newly inserted text box.

### W1-08-F05 — Text fit is heuristic in generation and non-wrapping in static export

- Consequence: a generated deck can pass the quality machinery while differing from browser/PowerPoint output, and overflow content can be moved silently into speaker notes. In the raster renderer, long lines are horizontally compressed/clipped rather than wrapped by the same rules used by the editor textarea.
- Severity / confidence: High / High.
- Repro: `estimateTextOverflow()` in `presentation/audit.ts:56-81` uses a fixed average glyph ratio (`0.52`) and line-height ratio. `fitGeneratedSlide()` in `layouts.ts:578-603` expands frames and then `parkOverflowingText()` at `layouts.ts:560-575` pops words into `speakerNotes` until only a fit remains. `renderPresentationSlide()` at `io.ts:811-823` calls `fillText` once per newline with a `maxWidth`; canvas `maxWidth` scales text and does not perform word wrapping.
- Code chain: AI/content normalization → `realizeGeneratedPresentation()` → inferred layout/hydration → heuristic fit/parking → DOM authoring or independent canvas/PPTX export. The editor itself measures `scrollHeight`/`scrollWidth` in `PresentationObjectView`, so the three fit decisions are not identical.
- Evidence: quality-machine tests verify layout variety, reading order, contrast, and successful fit/parking for long copy. They do not compare the final rendered pixels or preserved visible text against a PowerPoint render.
- Neighbors: the presentation skill explicitly asks for rendered-slide inspection and no generic placeholders; the code fulfils that intent at the model/audit level but lacks a render oracle. Text on shapes, tables, and chart labels has separate paths.
- Remedy: make fit a first-class render service with actual font metrics and deterministic line breaking. Treat parking as a visible, user-confirmed lossy action (or keep overflow and block export), and assert that visible text is conserved across editor, PDF/PNG, and PPTX readback.

### W1-08-F06 — Native materialization silently ignores unsupported/deleted scene changes unless command gating prevents them

- Consequence: a direct content projection can appear changed in the browser while native materialization returns the old payload or leaves deleted native objects in place. Style, transition, animation, layout, theme, chart data, table cells, image crop/media, group structure, and object deletion are not represented by native operations.
- Severity / confidence: High / High.
- Repro: `pptxProjectionFromContent()` in `office-content.ts:758-832` starts from the base slide and maps every base object back into the result when its incoming ID is absent; it only appends new incoming objects. `pptxOperationsBetween()` at `office-content.ts:834-971` emits title, notes, hidden, native text, alt text, geometry, add-slide/add-text, remove-slide, and reorder operations. It has no object-delete, style, chart, table-cell, group, media, transition, or animation branch. `pptxLens.materialize()` at `pptx-lens.ts:545-547` applies only that operation list and returns the original payload if it is empty.
- Code chain: editor content → `pptxProjectionUpdateFromContent()` → `pptxOperationsBetween()` → `applyDelta()` in `pptx-lens.ts:470-543`. The strict command registry prevents many of these operations on linked decks, which is good; the projection boundary is still unsafe if reached by AI/content mutation, stale commands, or future UI code.
- Evidence: 20 command fixtures pass for the operations they declare. This validates dispatch and exact touched parts, not completeness of the content-to-native diff.
- Neighbors: the native lens deliberately preserves transitions/timing/master/media/chart/table/SmartArt/equation parts and marks them read-only; `insert.equation` is disabled at `presentation-commands.ts:857-862`. The `presentationStubHandlers()` no-op object is a test/audit fixture, not a production executor, but command-fixture coverage must not be mistaken for mounted UI coverage.
- Remedy: make unsupported diffs fail closed with a structured `PPTX_NATIVE_OPERATION_UNSUPPORTED` result that names the region, or gate materialization on a validated native capability set. Add negative tests for deleting a native object, changing style/transition/chart data, and replacing a group; assert no-op versus refusal is surfaced to the user.

### W1-08-F07 — Merge conflict semantics are conservative but coarse for unsupported presentation regions

- Consequence: concurrent text/geometry edits to one native object conflict as a whole object even when fields are independent; external changes inside a preserved transition/timing/theme/chart/master part may only appear as a preserved-part change, not a semantic conflict with a user-readable field-level preview. Reconciliation is safer than last-write-wins, but it is not yet a complete presentation merge UX.
- Severity / confidence: Medium / Medium-high.
- Repro: `mergeSlide()` in `office-projection-merge.ts:250-302` merges objects through `mergeThreeWay` keyed by object ID, with no per-field merge. `pptxLens.diffExternal()` compares the flattened projection and separately returns `preservedPartChanges` for parts outside the modeled semantic set (`pptx-lens.ts:547`). A change from one PowerPoint transition to another can retain `hasTransition: true` while its raw part changes, so users need the preserved-part disclosure to understand it.
- Code chain: native open projection → external diff/package comparison → `mergePptxProjections()` → `NativeConflictPreview` using truncated JSON/text. Unsupported raw parts remain in the external payload, but are not projected with transition kind, timing tree, chart series, master style, or run-level provenance.
- Evidence: the current transition/timing fixtures and collaboration tests pass; no runtime conflict dialog or three-way PowerPoint GUI session was run here.
- Neighbors: `presentation-lane.ts` timers and join-late route cleanup are explicit; presentation auto-advance/import timers in `presentation-studio.tsx` also return cleanup functions. The remaining gap is semantic conflict coverage, not a confirmed timer leak.
- Remedy: show preserved-part changes beside semantic conflicts, including the exact feature and affected slide/object. Add field-level merges for geometry/text/alt/notes where native identity is stable, and retain whole-object conflict for rich unsupported objects. Add concurrent native fixture tests for transition kind, timing, theme/master, chart workbook, and notes.

### W1-08-F08 — Theme restyling could mutate the prior deck and corrupt undo history

- Consequence: `applyTheme()` mutated `object.style` and the nested theme token object in place while `producePresentationContent()` only shallow-copied objects/theme. Since `emit()` snapshots the current deck for undo around the mutation, the previous style could already contain the new theme, making undo unable to restore the old appearance.
- Severity / confidence: High / High (fixed in this task).
- Repro before fix: `presentation-studio.tsx:2057-2087` assigns `object.style.color/fill/stroke`; the old `producePresentationContent()` at `model.ts:122-170` copied only object/theme shells. The new regression test mutates nested tokens and style and asserts the original remains unchanged.
- Code chain: theme command → `mutate()` → `producePresentationContent()` → `emit()` undo stack. The fix clones `theme.tokens`, `theme.fonts`, `object.style`, `sourceBinding`, and `animation`, compares their shallow values for identity reuse, and includes theme name/tokens/fonts in no-op detection (`model.ts:96-205`).
- Evidence: focused model test passes; the 81-test presentation suite remains green after the change.
- Neighbors: `content` remains intentionally shallow because the current editor recipes replace content records rather than mutating them; any new recipe that mutates nested chart/table content directly should either clone it or use a replacement helper.
- Remedy: keep the regression test. If nested content editing is added, introduce typed copy helpers for chart/table/group content and assert undo/redo identity/durability around each inspector action.

## Decisions for parent/Pablo

- Treat native preservation and native editability as separate product claims. The current native lane is safe for the supported operation list, not for arbitrary PowerPoint scene edits.
- Keep strict-native refusal reasons for theme/layout/shape/chart/table/media/equation/transition/animation features; they are more trustworthy than exposing a control that cannot be written natively.
- Do not advertise browser PPTX import as preserving native editability until the feature model and export writer grow the missing semantics.
- Integrate commit `f9cccf7e` as a small correctness patch. The most valuable next implementation is a shared renderer/metric contract, followed by a real native chart/table decision.
- Use the current harness JSON as preservation evidence only; pair it with real render/readback evidence before claiming Office visual parity.
