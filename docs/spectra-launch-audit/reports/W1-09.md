# W1-09 — onboarding, invitations and roles

## Result

The source flow is coherent for invitation-based school entry: a verified account previews a token, accepts it into one active school membership, resumes through sign-in/sign-up, and reaches a workspace that explains how a membershipless user can join. Student and teacher ordinary capabilities are intentionally peer-level in the inspected UI and authorization paths. Two contained fixes are in the audit worktree: configured school domains are now enforced when creating invitations, and a known wrong-account preview cannot submit a futile accept action.

The live browser/runtime journey was not run because the shared local runtime was unavailable and this worktree has no installed dependencies. This report therefore separates source-supported behavior from unverified live behavior.

## Findings grouped by root cause

### W1-09-F01 — configured school domains were not enforced for member invitations

Severity: important. Confidence: high (source and UI contract; live delivery untested). Status: fixed in the audit worktree, not integrated into the primary runtime.

When a school had non-empty `verifiedDomains`, `convex/memberships.ts:292-329` previously validated only that the target contained `@`; the admin copy simultaneously promised “Invite a verified school email” and “domain checked” (`src/features/spectra/pages/school-admin-shell.tsx:1026-1107`). An admin could therefore generate an invite for an outside domain. This weakens the school onboarding boundary and can send an invite to an unintended identity.

The worktree now loads the target active school and rejects a non-matching domain with `INVITATION_EMAIL_DOMAIN_MISMATCH`. Exact domains and subdomains are accepted; an empty domain list remains permissive, matching the existing school policy and local seed convention. The initial-admin creation path already applied the analogous domain check (`convex/schools.ts:87-99`).

### W1-09-F02 — “Request school access” is not a first-person request flow

Severity: future/product decision. Confidence: high. A user who follows “Request school access” cannot submit anything; the page gives three instructions and links to sign-in/sign-up. This is consistent with a deliberate invitation-only policy, but the page title and sign-up copy can imply that a request is being submitted. If self-service access requests are required for launch, the product needs a request lifecycle, school routing, privacy/spam controls, status/readback and admin handling; that is larger than a contained W1-09 fix.

### W1-09-F03 — wrong-account join submission was offered after a known mismatch

Severity: small. Confidence: high. Before the worktree change, `/join` displayed “Sign in with the invited email” when `preview.emailMatches === false` but left “Join school” enabled (`src/app/join/page.tsx:108-116,147-153`). The backend was secure, but the user could click a guaranteed failure and receive an avoidable error. The submit button is now disabled for this known mismatch; the sign-in link remains available for switching to the invited email.

### W1-09-F04 — class candidate period filtering needs a W1-10 contract

Severity: important if historical records are present; confidence: medium until a provider-shaped fixture/live read is available. The candidate query enforces school, mapping and user/class membership, but its visible filter removes archived records rather than selecting the current academic period (`convex/managebac.ts:3331-3449`). A stale class could therefore be presented during onboarding if the upstream dataset contains multiple non-archived periods. W1-10 owns the integration semantics; W1-09 intentionally made no shared ManageBac change.

## Decisions for parent/Pablo

- Keep the new invitation domain guard if `verifiedDomains` is the intended school boundary. It is the narrowest consistent remedy because the schema, initial-admin creation path and UI copy already establish the policy. If schools intentionally invite personal addresses despite configured domains, the alternative is to change the copy and policy explicitly rather than remove the guard silently.
- Treat `/request-access` as a product decision, not a missing one-line fix. The current source is internally consistent with invitation-only onboarding, but the route name and copy should be renamed or implemented before promising self-service access requests.
- Ask W1-10 to settle current academic-period semantics with a fixture or live read. The existing user/account/class authorization checks are strong; the unresolved issue is temporal candidate selection, not role policy.
- Keep the idempotent accepted-token replay behavior unless strict single-use invalidation is required. It does not duplicate membership and makes reload/retry safe, but the “single-use” copy should be interpreted as single membership effect rather than single HTTP attempt.
