# W1-10 — ManageBac and schoolwork integration

## Result

The source audit finds a real prelaunch isolation risk in the ManageBac cache/projection identity model, plus important gaps in timetable refresh, historical-class selection, edit preservation, semantic idempotency, attachment materialization, and scheduled-sync recovery. Three bounded fixes are implemented in the isolated worktree: account-scoped personal record keys and projections, tombstone-aware membership access derivation, and school-wide conflict authorization. They are not integrated into the primary runtime.

The historical manual-connect path is strong, but it is not evidence for current two-person isolation, current-vs-historical filtering, attachment parity, or scheduled ManageBac behavior. Those require the targeted next-wave scenarios below.

## Scope and current architecture

Source baseline: `43c45cc557942ccfb4f806092a61b6950dcdf2f3` (the charter baseline). Audited source is the W1-10 worktree; the running app remains the primary checkout at `<local-workspace>`.

| Concern | Current path | Authority boundary |
| --- | --- | --- |
| School connection | `POST /api/spectra/managebac` → `managebac:configure` / `replaceCapabilityManifest` / `disconnect` | `school_admin` only; the read-only token is stored through the server secret store |
| Identity | `resolveIdentity` uses a verified Spectra email against one narrow provider route, then `commitIdentityResolution` | One exact match is accepted; provider ID is not presented as a user choice |
| Personal reads | `GET /api/spectra/managebac` → `managebac:myOverview`; AI `get_school_data` → `managebac:recordsForPurpose` | Active school member plus verified account mapping |
| Class choice | `listMyClassCandidates` → `ClassShelfOnboarding` / `ClassShelfEditor` → `materializeClassWorkspaces` | User chooses owned class shelves; source class records are stored before materialization |
| Source projection | `commitNormalizedPage` → `externalRecords` → planner task, Calendar item, or resource projection | Provider writes are read-only; local source-owned fields are intended to remain authoritative |
| Scheduled refresh | Convex scheduler → `executionScheduler.dispatchManageBacSync` → signed internal HTTP callback | Scheduled runs use an active school admin service subject and only non-personal verified capabilities |

The route exposes `/managebac` to ordinary members, but its read view is `myOverview`; admin controls are gated in the POST path and the UI. `/school` is also ordinary-member accessible. `school_admin` is the only school role in the source model; platform superadmin is a separate operator context and is not a normal ManageBac data path. Teachers and students use the same personal scope and class-shelf actions. The AI can read personal data through `get_school_data`, request a bounded refresh, and create/update the user’s own planner/calendar work through the normal `propose_operation` / `submit_plan` authority path. It cannot change ManageBac mapping or credentials (`change_managebac_mapping` is prohibited for AI).

## Findings grouped by root cause

### Identity and durable source identity

#### W1-10-F01 — Personal provider IDs were globally keyed before this worktree fix

- **Consequence:** two students with the same provider class/task/resource ID could overwrite one `externalRecords` row. The later sync changes `mappedAccountId` and normalized content, so the first student can lose or see the second student’s cached source. Global projection keys could also reuse the first owner’s workspace/planner/Calendar projection.
- **Severity:** launch blocker before the fix; **confidence:** high (source-supported).
- **Code chain:** baseline `normalizeProviderPage` built `providerRecordKey` directly from the provider template (`src/app/api/spectra/managebac/route.ts:722-866`); `commitNormalizedPage` upserted by `externalRecords.by_integration_key` (`convex/managebac.ts:2342-2525`); class/planner/timetable/resource helpers used provider-only keys (`convex/managebac.ts:1697-2075`).
- **Fix:** commit `3c905bccae21b52df5f1c9829bc4221611960a4f` scopes mapped-user record keys by account and scopes all account-owned projections/workspace lookups by account. Source relations now select a class target in the same account/shared scope. Existing unscoped rows need a deliberate migration/reconciliation; the fix is not yet in primary.

#### W1-10-F02 — Capability presence was treated as capability usability

- **Consequence:** if the official personal paths existed in a tenant manifest but had become `unverified` after a connection-contract change, the route could skip manifest repair and proceed with no verified identity capabilities. The result is an opaque identity/sync failure rather than a repairable admin validation state.
- **Severity:** important; **confidence:** high.
- **Code chain:** `ensureOfficialPersonalCapabilityManifest` previously checked only `path` presence (`route.ts:508-550`), while `connectorContext` and `beginSync` expose/use only `read_only` + `verified` capabilities (`managebac.ts:1324-1510`).
- **Fix:** the same commit now requires both permission and verification state when deciding whether the official manifest is usable. Admins get the existing repair/merge path; ordinary members still receive an identity-required state.

### Membership and conflict authority

#### W1-10-F03 — Tombstoned memberships could continue to grant class access

- **Consequence:** after a membership was removed, its `providerClassId` still entered `accessibleClassIds`; class-member records could remain visible to AI and could be offered for class selection/materialization.
- **Severity:** important; **confidence:** high.
- **Code chain:** `recordsForPurpose`, `listMyClassCandidates`, and `materializeClassWorkspaces` queried account membership rows without excluding `tombstone` (`managebac.ts` baseline around `3196-3630`).
- **Fix/test:** `3c905bcc` filters membership rows by integration and `!tombstone`. `convex/managebac-isolation.test.ts:14-231` passes for resources and candidates, including a tombstoned old membership.

#### W1-10-F04 — Any school member could resolve an integration-wide conflict

- **Consequence:** a conflict with `accountId` absent represents shared/school-scoped data, but the old `resolveConflict` check allowed any active school member to resolve it. The mutation then iterated every projection for the record, so a student could detach/rebase shared projections or set an arbitrary link target.
- **Severity:** important; **confidence:** high.
- **Fix:** `3c905bcc` requires `school_admin` for accountless conflicts, restricts account-scoped resolution to the conflict account’s projections, and validates `link_existing` targets by type, school, and account scope. The focused test asserts a student is rejected.

### Source projection and edit semantics

#### W1-10-F05 — Timetable refresh uses the wrong projection model

- **Consequence:** new ManageBac timetable/assignment projections store a `calendarItems` ID (`ensureTimetableProjection`, `managebac.ts:1977-2029`). On source change, `safelyRefreshProjection` treats that ID as `artifactId#eventId` for a legacy timetable artifact (`managebac.ts:2131-2225`), returns `false`, marks the projection conflicted, and creates a customization-overlap conflict even when the user did not edit it.
- **Severity:** important; **confidence:** high.
- **Status:** not fixed in this wave. Bounded remedy is to refresh the source-owned `calendarItems` record directly, preserving the separately movable task’s local scheduling fields, while retaining a legacy-artifact fallback for old projections.

#### W1-10-F06 — Direct edits to source-linked planner fields are not captured as overlays

- **Consequence:** planner artifacts declare `taskTitle`, `description`, `dueAt`, and `source` locked/source-owned fields (`convex/managebac.ts:1886-1909`; `src/features/spectra/artifacts/schema/planner-task.ts:99-116`), but the sync conflict detector only consults an `externalRecordOverlays` row (`managebac.ts:2459-2490`). `setOverlay` exists (`managebac.ts:2998-3050`), but no ManageBac UI call was found. A direct artifact edit can therefore be overwritten by the next source hash refresh without a recorded personal overlay.
- **Severity:** important; **confidence:** high source / live user-edit reproduction untested.
- **Affected neighbors:** planner status, reminders, links, calendar task scheduling, and the UI copy promising that source updates do not replace personal notes.
- **Remedy:** choose one explicit contract: make source-owned fields read-only and expose a typed “personal adjustment” editor, or capture direct field divergence before refresh and create an account-scoped conflict/overlay. Do not silently rely on `lockedFields` metadata.

#### W1-10-F07 — Source-to-local task/calendar split is mostly sound but not full attachment parity

Assignments/deadlines intentionally create an immutable official deadline plus a distinct movable task (`convex/calendarShared.ts:164-251`), and planner projections preserve non-source content fields. `calendar.scheduleTask` only creates a local scheduled work block and does not mutate provider truth. However, source refresh resets the source task’s title/notes/status to active; whether completion is meant to survive must be decided and tested against the source-task UI. ManageBac resources normalize a URL and create only an `externalProjections` resource record (`managebac.ts:2000-2075`); no download, asset, or artifact attachment is materialized. This is a functionality gap, not an unproven provider claim.
- **Severity:** attachment parity is future/important for launch scope; **confidence:** high source.

### Reconciliation, filtering, and scheduling

#### W1-10-F08 — Current-vs-historical class filtering depends only on provider `archived`

- **Consequence:** `listMyClassCandidates` deduplicates by provider class ID and filters only `normalized.archived` (`managebac.ts:3465-3520`). It does not require a current academic period, date window, or active roster period. A historical class with no reliable `archived` field can be offered and materialized; the later related-record filter only compares `academicPeriodKey` when present.
- **Severity:** important; **confidence:** high code / provider-field behavior untested.
- **Remedy:** define the current-class contract using a verified provider field/route and academic-period metadata, expose the period in candidate data, and test same-ID current/historical payloads. Do not infer currentness from a title or last fetched time.

#### W1-10-F09 — Semantic retry idempotency is absent

- **Consequence:** bridge HMAC nonces prevent exact request replay, but a retried page with a fresh nonce is accepted again. `commitNormalizedPage` increments fetched/count/page totals and repeats projection work; rows dedupe only by provider key. A retry after a partial response can therefore inflate run metrics and produce repeated conflicts/projection writes. `completeSync` also has no settled-run idempotency guard.
- **Severity:** important; **confidence:** high.
- **Remedy:** add a bounded page receipt keyed by sync run + capability + route binding/page/cursor/payload digest, and reject or return the prior result for duplicate pages; make completion/failure terminal-state aware. This crosses the sync schema/worker seam, so it is report-only here.

#### W1-10-F10 — Scheduled refresh has a recovery/coverage dependency that is not visible enough

- **Consequence:** `configure` creates/updates the integration but does not set an initial `nextSyncAt`; `scheduleExisting` exists as an internal mutation but has no caller in the current source, and `convex/crons.ts` has no ManageBac scheduling entry. Normal manual/complete/fail paths schedule future work, but a newly configured integration with no successful manual completion has no scheduled polling. In addition, `claimScheduledSync` intentionally selects only verified non-personal capabilities (`managebac.ts:1155-1303`); a manifest containing only the official personal routes cannot run as a school-wide scheduled sync and is degraded.
- **Severity:** important operational gap; **confidence:** high source. Heavy live timing was deferred.
- **Remedy:** make the initial/repair scheduling path explicit, surface “manual sync required” versus “next scheduled sync,” and test an integration with no non-personal route. Keep scheduled runs non-personal; never solve this by enumerating student records.

## Next-wave tests and implementation implications

Prioritize these exact scenarios, in order:

1. **Two-account same-ID isolation.** In a disposable school, connect an admin read-only token and resolve two student accounts to different provider users whose class/task IDs overlap. Sync A, sync B, then read A/B `myOverview`, `recordsForPurpose`, class candidates, artifact owners, Calendar source keys, and projections. Expected: no cross-account normalized source, workspace, task, timetable, resource, conflict, or AI read. Run the migration/readback path for rows created before `3c905bcc`.
2. **Membership removal.** Sync a class/member/resource set, remove one membership in the provider fixture, resync with a fresh page and completion, and read the external record tombstone, class candidates, `get_school_data(class_resources)`, and materialization response. Expected: removed class-member data is unavailable; decide separately whether an existing user shelf is retained/dissolved and verify the preference does not silently claim a missing shelf.
3. **Current/history matrix.** Supply current and historical classes with combinations of `archived`, `academicPeriodKey`, year dates, and same provider IDs. Verify candidate filtering, selected workspace identity, related assignment filtering, and AI `classes` results. Expected: only the explicit current contract is selectable.
4. **Edit-survival matrix.** Materialize an assignment; edit planner title/description/status/notes/reminder/link, move and complete its Calendar task, then change provider title/due date/description and resync. Read artifact content, overlay/conflict rows, official deadline, movable task, scheduled work block, and visible provenance. Expected behavior must be chosen explicitly and then asserted; no silent overwrite.
5. **Retry/idempotency.** Capture one signed page and submit it twice with a fresh valid nonce, then retry after a simulated timeout and complete twice. Expected: one logical page/record/projection and stable counts; no duplicate conflict or re-tombstone churn.
6. **Scheduler recovery.** Configure an integration, inspect `nextSyncAt` and scheduled jobs before manual sync, then test manual completion, worker lease expiry, credential 401, rate-limit 429, schema drift/quarantine, and no verified non-personal route. Expected: a visible actionable state, bounded retry, and no personal enumeration by a scheduled worker.
7. **Attachment/resource path.** Return a resource with URL, file metadata, and any provider attachment shape available in the tenant reference. Verify resource list, provenance link, download/readback, artifact attachment creation, stale/removal behavior, and account/school isolation. Current source only proves normalized metadata/provenance.
8. **Ordinary AI path.** As student and teacher, from `/chat` and `/school`, request personal classes/deadlines/resources, force a stale refresh, create a planner task, update it, and schedule work. Verify no admin page is required, no provider ID is exposed, stale/not-connected/identity-required states are explicit, and the AI cannot change credentials/mapping. As admin, verify connection/manifest/disconnect remain admin-only; verify platform superadmin context does not widen ordinary school data.
9. **External write safety.** Use a recording proxy/mock around the authorized tenant endpoint and assert every ManageBac request remains GET, no provider POST/PUT/PATCH/DELETE is emitted, auth headers never reach the browser, and raw payloads/tokens are absent from UI, AI context, logs, and quarantine samples.

Cost points to measure per scenario: one identity GET; membership pages; per-selected-class details/tasks/timetable/resources fan-out; per-year-group CAS; the sequential request gap (`ceil(60,000 / requestBudgetPerMinute)`, capped at 180 requests/minute); `/school`’s overview plus class-candidate reads; `recordsForPurpose`’s bounded personal/scoped/membership scans; and page commit fan-out through external records, projections, artifacts, Calendar items, relations, and summaries. The official 200 requests/minute provider ceiling is not a reason to raise the app cap without measuring Convex writes and provider payload latency.

## Decisions for parent/Pablo

- Integrate `3c905bcc` only with a migration/readback plan for existing unscoped ManageBac records/projections. A source-only key change is not enough if stale rows remain visible.
- Treat F05/F06/F07/F08/F10 as separate next-wave packages. The highest-risk sequence is two-account isolation, membership removal, then edit survival and timetable refresh.
- Choose and document “current class” semantics from the tenant reference before launch. If the provider cannot guarantee an active-period field, require explicit school/period configuration rather than guessing.
- Choose a durable edit contract: typed personal overlays with source fields protected, or conflict-on-direct-edit. The current metadata-only `lockedFields` contract is not enforcement.
- Preserve the current read-only/provider-write boundary. Spectra can create/update local schoolwork for the authenticated user, but ManageBac write parity and attachment import should not be implied by the current resource projection.
