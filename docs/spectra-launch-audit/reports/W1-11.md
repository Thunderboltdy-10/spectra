## Executive readout

This is a first prelaunch audit wave, not a release pass. The strongest part of the current build is its shared interaction architecture: Workspace and Library have a common workbench, secondary product routes get a global Live Dock, role-gated admin destinations are derived from the account, and the split-pane allocator has a single budget with hysteresis. Those are good foundations for a school product that must let a student work while a teacher continues to create and share work nearby.

The launch risks are concentrated in discoverability and spatial/focus behavior rather than missing routes:

- important: the shell Search field searches recent/pinned chat titles only. It does not recover an artifact, workspace, or idea from one place.
- important: the mobile bottom navigation exposes nine destinations in one horizontal strip. At 320–390 px, several core routes are hidden behind undiscoverable horizontal scrolling.
- important: ManageBac and Settings section rails use five fixed primary tabs and shrinking/truncating labels. The route-specific overflow is not enough protection at narrow widths.
- important: chat/history/live side panels are visually docked but lack a modal-vs-docked focus contract. There is no role="dialog", modal scrim, focus containment, or reliable focus restoration in the chat browser path.
- important: a plausible student/teacher sequence can still stack shell, organizer/list, studio, live conversation, run status, and composer zones until the task surface is visually overloaded.
- small: secondary-route errors and chat-browser failures do not share one truthful recovery pattern; some paths show raw errors and one load failure is rendered as “No chats found.”

One contained fix is included in the audit worktree: the sidebar shortcut hint now renders Ctrl K on Windows/Linux and ⌘ K on macOS/iOS, matching the existing shortcut handler. The primary runtime was not restarted, so this fix is not present in the running app during this wave.

## Scope and audience

The audit is framed around the requested Windows and macOS bridge launch contract, with students as the primary users. Teachers are treated as peers who create, curate, present, and share quizzes, presentations, agents, and class work; they are not treated as operators who control students. School setup and the ManageBac journey received focused coverage. The landing page, broad platform-administration UX, artifact editor internals, full keyboard-command registry, and native bridge internals were not swept here.

The core task lens was: can a student or teacher start from a school/class context, locate a prior idea or file/chat, open it without losing context, continue an AI run safely, and understand what happened when data or integration state is unavailable?

## Findings

### W1-11-F01 — Unified recovery is missing from the shared shell

Severity: important  
Evidence: S  
Owner: shell/search + Library/Chat navigation

Source anchors: src/components/layout/app-shell.tsx:579-583 and 672-679; Chat’s contextual search is mounted at src/features/spectra/pages/chat-shell.tsx:528.

The sidebar field is labeled simply “Search,” but its result set is only the recent/pinned threads array and its filter is thread.title. Library has its own artifact search and Chat has a contextual GlobalSearch, but a user standing on School, Calendar, Agents, or Workspace has no single lightweight way to recover “the quiz idea from last week,” “the class presentation,” or “the file I opened yesterday.” This is a discoverability break in the exact school workflow where people move between class context, chat, and saved work.

Exact browser scenario for the next authenticated run:

1. Sign in as a student and open /workspace.
2. Use the sidebar Search field and type the exact title of an artifact known to exist in Library, then type the exact title of a known chat.
3. Repeat from /school and /managebac as a teacher/school-admin peer.
4. Compare results and the number of navigation surfaces a first-time user must already know.

Expected: one compact recovery surface should return the matching chat, artifact, and workspace, with a clear scope label and one-click destination. Current source behavior: only matching thread titles appear in the sidebar; the artifact/workspace query produces no result there. The separate surfaces are individually reasonable, but the cross-route recovery task is not.

Recommended fix: add a small route-aware “Search work” result surface to the existing shell search, limited to recent/authorized threads, artifacts, and workspaces. Keep the existing Library and Chat filters as scoped searches. This is not a request to expand the audit into a full enterprise command bar.

### W1-11-F02 — Mobile navigation hides core destinations without an overflow affordance

Severity: important  
Evidence: S; H desktop shell confirms the same destination set  
Owner: src/components/layout/app-shell.tsx

Source anchors: src/components/layout/app-shell.tsx:90-98 and 1016-1068; the desktop rail uses the same ordinary destination set but a different layout.

The mobile shell is a fixed bottom rail with seven core destinations—Chat, Home, Library, Calendar, Agents, School, Analytics—plus Workspaces and Alerts. Each item has min-w-[62px]; the rail uses horizontal scrolling but has no “More” item, visible scroll cue, or alternate menu. At 390 px, the nine-item set is wider than the usable rail; at 320 px, roughly half the set is initially outside the viewport. Calendar, Agents, School, and Analytics are particularly easy for an unfamiliar student or teacher to miss. Role-gated Admin/Super Admin entries are not in the mobile rail at all, which is acceptable only if the role-specific overflow path is explicit.

Exact browser scenario:

1. In a 390×844 viewport, sign in as a student and open /workspace.
2. Inspect the bottom navigation without swiping; then keyboard-tab through it and use a screen reader landmark query.
3. Try to find Calendar, School, and Alerts; repeat at 320×844.
4. Sign in as a teacher/admin peer and confirm where ManageBac and Admin are discoverable.

Expected: the primary mobile rail shows the most important four or five destinations and an explicit, labeled overflow that contains the rest; the active destination is always visible or scrolled into view. Current behavior relies on a user discovering horizontal swipe in a navigation bar that visually reads as a complete set.

Recommended fix: keep four or five primary destinations, add a labeled “More” menu/sheet for Calendar, Agents, School, Analytics, Workspaces, Alerts, and role-gated entries, and preserve aria-current, focus visibility, and selected-item reveal in the overflow path.

### W1-11-F03 — Section rails can degrade into truncated labels at narrow widths

Severity: important  
Evidence: S  
Owner: src/features/spectra/components/product-section-nav.tsx

Source anchors: product-section-nav.tsx:29 and 43-88; ManageBac’s eight-item tab list begins at managebac-integration-shell.tsx:70; Settings’ six-item list begins at settings-application.tsx:24.

ProductSectionNav is shared by School, Admin, Superadmin, ManageBac, and Settings. It defaults to five primary items. Its button class uses min-w-0 shrink, while the label uses truncate; the active tab is swapped into the fifth slot when it would otherwise be in overflow. ManageBac has eight tabs—Overview, Classes, Calendar, Periods, Tasks, History, Conflicts, Provenance—and Settings has six. At narrow widths this protects reachability of the active item, but not the legibility of the surviving labels. The component comment says labels are never deleted, yet CSS can reduce them to an icon plus a clipped label before the overflow menu becomes the clear mental model.

Exact browser scenario:

1. Open /managebac at 390 px while authenticated.
2. Record which tab labels are fully readable, which are truncated, and which are only reachable from More.
3. Use Tab to move through all section buttons; activate Calendar, Conflicts, and Provenance from both the primary rail and overflow.
4. Repeat /settings?section=devices at 320 px and verify that the active Files and devices section remains obvious.

Expected: a stable three- or four-item primary rail with full labels plus a real More menu at narrow widths. Current source behavior is five primary buttons that are allowed to shrink and truncate.

Recommended fix: make primary buttons shrink-0, choose the primary count responsively, and move whole labeled tabs—not partial labels—into an accessible overflow. Ensure active-section swapping also scrolls/reveals the selected item and updates the overflow trigger label.

### W1-11-F04 — Side panels lack a clear docked-versus-modal focus contract

Severity: important  
Evidence: S, H (profile-a-chat-browser-final.png, profile-a-chat-browser-open.png)  
Owner: ChatBrowserPanel, LiveThreadPanel, RouteSidePanelHost

Source anchors: chat-browser-panel.tsx:75-116 and 156-171; route-side-panel-host.tsx:157-181; live-thread-panel.tsx:41-47.

The chat browser is an absolutely positioned right-side aside with a width capped at calc(100vw - 24px). It has an accessible label and an Escape listener, but no dialog role, aria-modal, scrim, inert underlay, focus trap, or focus restoration. The live conversation panel uses the same split-shell family and similarly behaves as a docked side surface. The historical captures show the underlying chat/library composer and content remaining visibly active beside/under the panel, making it ambiguous whether the panel is a secondary workspace or a modal interruption. On mobile, the 24 px underlay is especially likely to remain interactive or visually distracting.

Exact browser scenario:

1. From /library, open the chat browser and set a 390 px viewport.
2. Press Tab repeatedly; note whether focus enters the underlying Library or composer before the panel is closed.
3. Press Escape and verify focus returns to the button that opened the browser.
4. From /chat, open a live conversation/run detail and repeat the same focus and dismissal checks.

Expected: desktop docked panels should announce their relationship and keep keyboard focus coherent; mobile panels should become a full-width sheet/dialog with a scrim, focus containment, and restoration. Current behavior only provides close-by-button and global Escape.

Recommended fix: choose one explicit contract per viewport. For a modal sheet, add dialog semantics, scrim/inert underlay, focus containment, restore target, and a full-width mobile layout. For a true dock, keep it in the workbench pane registry and make the underlying surface intentionally available, with a persistent close/minimize affordance and non-modal announcement.

### W1-11-F05 — The shared panel budget does not yet cover every simultaneous zone

Severity: important  
Evidence: S, H (profile-a-library-artifact.png, profile-a-chat-browser-final.png)  
Owner: workbench/panel orchestration

Source anchors: global-route-workbench.tsx:18-28 and 36-128; route-side-panel-host.tsx:32-49 and 157-181; the single-row allocator is in split-presentation.ts.

The split-presentation allocator is a strong single-row authority for the Library content reserve, open work, live thread, and run detail. However, route-side panels are mounted by RouteSidePanelHost outside the local SpectraShell workbench, and secondary routes also receive the global Live Dock and composer. This means a realistic sequence can still produce shell sidebar + organizer + artifact list + studio + live conversation + run status + bottom composer, or a School/ManageBac page plus a route-side studio/thread panel plus global dock. The historical artifact capture visibly contains several of these zones at once; the browser-panel capture shows a chat/library surface and a substantial right browser side by side.

Exact browser scenario:

1. At 1280×720, open a class workspace, select a folder, open an artifact, then open its related chat.
2. Start or continue an AI run so the Live Dock and composer remain present.
3. Open the artifact in full studio and then inspect the live conversation/run detail.
4. Repeat on /school or /managebac, opening an artifact and a live conversation while the global dock is active.
5. At 390 px, repeat only the mobile equivalent and record the number of simultaneous exit affordances and whether the primary task stays readable.

Expected: one coherent pane registry owns all in-flow surfaces, with explicit priorities and promotion to overlay when the task surface would fall below a readable reserve. Current architecture coordinates the local workbench well but leaves global/route panels able to add another visual layer.

Recommended fix: register route-side studio/thread panels in the same presentation authority, or establish a strict route-panel rule that automatically closes/minimizes a competing dock before opening a new high-cost surface. Make the next action and one obvious exit dominant at every breakpoint.

### W1-11-F06 — Error and empty states are not consistently truthful across panels

Severity: small (promote to important if telemetry shows frequent recoveries)  
Evidence: S  
Owner: shared data-state/copy layer

Source anchors: route-side-panel-host.tsx:64-84; chat-browser-panel.tsx:75-76 and 171; settings-application.tsx:220 and 238; calendar action handlers were also reviewed for direct error-toasts.

Several shells use good ProductErrorState / describeFailure patterns, but the shared route-side host sends error.message directly to a toast when an artifact or conversation fails to open. Calendar also has raw error-toasts on action failures. Separately, ChatBrowserPanel catches a failed thread load by setting threads=[] and then renders “No chats found / Try a different search or filter.” A transport/auth/server failure is therefore indistinguishable from a successful empty result and offers no Retry action. This undermines trust during ManageBac or school-data setup, where “not connected,” “not authorized,” “no records,” and “request failed” mean different next actions.

Exact browser scenario:

1. In an authenticated fixture, open /managebac or /school with the API unavailable or unauthorized.
2. Open a related artifact or chat from the route-side panel while the request fails.
3. Open the Chat browser with its list request failing, and compare it with a genuinely empty account/search.
4. Trigger a Calendar action failure and inspect the toast wording.

Expected: a human-safe error with a retry path, a stable diagnostic reference where appropriate, and a distinct empty state. Raw server phrases should remain diagnostic data, not the primary user copy.

Recommended fix: use the shared truthful-state formatter and ProductErrorState/retry pattern in panel hosts; keep empty and failed states separate in ChatBrowserPanel; add a retry button to the browser and safe fallback copy to Calendar/route-side toasts.

### W1-11-F07 — Sidebar shortcut hint was wrong for Windows

Severity: small  
Evidence: S; fixed in audit worktree  
Owner: src/components/layout/app-shell.tsx

Source anchors: app-shell.tsx:151, 206-214, and 583; keyboard-shortcuts.tsx:61 and the existing modifier handler.

The sidebar search hint displayed ⌘ K unconditionally even though the existing keyboard shortcut registrar accepts the platform modifier (metaKey || ctrlKey) and the shared ShortcutKey component already renders Ctrl on non-Apple platforms. On the Windows launch path this creates a small but concrete trust break: the visible instruction contradicts the action that works.

Contained fix applied in commit 1af35262126266617bb781ac98a932c560439673:

- ShellNavigation detects Apple platforms in a client-side effect.
- The hint renders ⌘ K on macOS/iOS and Ctrl K elsewhere.
- The actual key handling remains unchanged and continues to accept the platform modifier.

Exact verification for the next live run: sign in on Windows, verify the sidebar says Ctrl K and that it focuses Search; repeat on macOS, verify ⌘ K; resize to mobile and confirm the same instruction does not collide with the field.

## What is working well

These are positive launch signals, not a claim that the end-to-end journeys have passed:

- The app shell has a skip link to #main-content, named navigation landmarks, visible account/settings/notification controls, and selected-route semantics. The ordinary navigation list is intentionally distinct from school-admin and platform-operator destinations.
- The route tree has canonical redirects for legacy /artifacts*, /timetable, and /memory paths, and the artifact redirects preserve query parameters. This reduces link rot when teachers share saved work.
- Workbench ownership is explicit. /chat, /workspace, /library, and /agents own local workbenches, while Calendar, School, ManageBac, Settings, Analytics, Admin, and Superadmin receive the global route workbench. This avoids mounting a second Yjs-backed studio on pages that already own one.
- The split allocator subtracts the Library content reserve before allocating panels, gives open work priority, supports overlay promotion, and uses hysteresis to avoid resize flapping. That is the right foundation for the F05 fix.
- Live Dock controls are labeled for status, retry, stop, opening a conversation, and required input. Polling is shared, visibility-aware, and spaced at three minutes rather than every component independently polling.
- Core and secondary shells contain deliberate loading, error, and empty states. ManageBac distinguishes not-connected, validating, identity matching, conflicts, quarantine, and provenance concepts instead of presenting all school data as one opaque table.
- The public-share route is intentionally outside the signed-in shell and has explicit loading, expiry, invalid-token, and read-only states. It does not accidentally expose the account chrome.

## Decisions and handoff

- Do not call the first prelaunch wave a pass. Authenticated coverage is still required, and F01–F05 should be addressed or explicitly accepted before launch.
- Keep the current patch isolated. Integrate the shortcut fix only after the next Windows/macOS authenticated smoke confirms no hydration, focus, or narrow-layout regression.
- Prioritize retrieval and mobile navigation before visual polish. They affect whether a new student can find the work the product already stores.
- Use the existing pane allocator as the extension point. Do not add per-panel width heuristics that compete with split-presentation.
- Treat ManageBac setup as a stateful school workflow. The next wave must cover capability, identity, permissions, and failure semantics—not just the happy-path connected screen.
- No primary runtime restart or bridge control was performed. The next operator can use the existing W1-13 runtime/baseline and authenticated fixtures without assuming this worktree patch is live.
