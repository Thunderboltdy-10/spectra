## Scope and current architecture

| Path | Current flow | Authority/durability boundary |
| --- | --- | --- |
| Human edit | Studio → `NativeArtifactYjsModel`/type adapter → Y.Doc → Hocuspocus or opt-in Cloudflare provider | Human edits are optimistic in `region-controller.ts`; gateway/Convex performs the durable authorization check. |
| AI/native materialization | AI region claim → Yjs update → gateway append → projection/checkpoint | AI writes require durable claims; native projection is eventually materialized into `spectraArtifacts`. |
| Presence/coordination | Awareness, structural claims, interaction leases | Presence is ephemeral; claims/leases are server-side and expire. |
| Connected embeds | `artifactEmbeds` → `artifactEmbeds.projection` → source snapshot/runtime | Source read/use capability is checked against the current authority policy. |
| Schoolwork/calendar | ManageBac `externalRecords` → `externalProjections` → source calendar item/task; personal scheduled blocks are separate | Provider truth is source-locked; task overlays and scheduled work blocks are user-owned. |

`provider-factory.ts:7-23` makes Hocuspocus the default and selects Cloudflare
only with the explicit deployment flag. The token route signs the artifact,
account, client, room, policy epoch, access level, and expiry
(`src/app/api/spectra/collaboration/token/route.ts:75-95`).

## Findings grouped by root cause

### W1-12-F01 — Cloudflare connected-session authorization does not track policy revocation

- Severity: launch blocker for an enabled Cloudflare provider; important for
  the default Hocuspocus deployment. Confidence: high.
- User consequence: after a teacher/owner revokes a collaborator, an already
  connected Cloudflare socket can still apply and broadcast edits until its
  room learns a newer permission epoch or the signed session expires. The
  Cloudflare room has no Convex policy reauthorization or periodic policy
  sweep; `canMutate()` exists in `workers/collaboration/src/auth.ts:43-49` but
  is not used by the room message path. `RealtimeRoomCore.applyUpdate()` only
  checks the claims held by the room (`room-core.ts:116-153`).
- The current bounded fix adds expiry checks, initial epoch adoption, stale
  epoch rejection, and socket identity guards (`room-core.ts:67-176`,
  `room.ts:151-225`). It does not provide an immediate policy feed/sweep for
  an otherwise idle connected socket. A new connection can update the epoch,
  but that is not a revocation mechanism.
- Neighbor: Hocuspocus has the desired comparison behavior: reauthorization
  before messages/awareness and the active policy sweep closes stale sockets
  (`scripts/collaboration-gateway.mjs:823-864`, `:1233-1287`). Convex append
  checks policy later, but Cloudflare has already broadcast before its local
  durable append (`room-core.ts:129-139`), so a stale edit can be visible as a
  live/temporary change even if later projection authorization fails.
- Bounded remedy: add an authorized policy-version/expiry check to the
  Cloudflare message boundary and a low-frequency alarm sweep, closing the
  socket before broadcast. Keep the existing token/epoch and stale-socket
  protections. Do not rely on a new collaborator connecting.

### W1-12-F02 — Durable Yjs head can advance before native projection checkpoint

- Severity: important. Confidence: high.
- User consequence: a human edit can be durably appended to the gateway Yjs
  log and update `liveStateVectorHash`, while the Convex artifact projection
  remains old if the gateway dies before its debounced checkpoint. On restart,
  `onLoadDocument()` replays the Yjs updates and only invokes recovery when the
  observed vector differs from the stored vector (`scripts/collaboration-gateway.mjs:1141-1184`).
  The crash case has equal vectors, so the editor can show the new text while
  Library/detail/embed consumers continue reading the old projection until a
  later checkpoint-triggering edit.
- Root chain: ordinary human messages omit `projectionJson` in
  `persistAcceptedMessages()` (`scripts/collaboration-gateway.mjs:372-475`);
  append updates the room/artifact live vector (`collaborationGatewayStore.ts:673-779`);
  checkpoint is delayed by a 2-second idle/15-second maximum scheduler
  (`scripts/collaboration-checkpoint.mjs:12-70`). Graceful shutdown flushes,
  but a hard process kill, host crash, or prolonged failure leaves the window.
- Bounded remedy: on room load/restart, compare `lastProjectionSequence` with
  the durable room head and enqueue an authorization-checked checkpoint (or a
  repair outbox item) even when the state vector matches. Add a crash-window
  test that appends a human update without checkpoint, reloads, and reads back
  both artifact content and projection sequence.

### W1-12-F03 — “Restore selected” is whole-content for native non-sheet regions

- Severity: important. Confidence: high.
- User consequence: a user selecting one historical content region can replace
  unrelated current content. `artifact-studio.tsx:5031-5035` calls
  `restoreRegions()`, but `NativeArtifactYjsModel.replaceRegionsFromSnapshot()`
  only patches metadata surgically; any selected content falls through to
  `replaceSnapshot()` (`native-artifact-model.ts:475-501`). For non-sheets,
  `replaceSnapshot()` applies the complete content projection and claims
  `artifact:structure` (`:340-463`). Sheets have a cell plan, but document,
  code, presentation, flashcard, quiz, whiteboard, and timetable content do
  not get a per-region restore patch here.
- Human `ArtifactRegionController.editMany()` is intentionally optimistic and
  does not acquire a region claim (`collaboration/region-controller.ts:50-78`).
  Thus two human sessions can silently last-write: A restores an old paragraph
  or slide while B edits a different region, and A's full projection can erase
  B's change without the restore conflict banner.
- Bounded remedy: add adapter-specific restore plans that mutate only selected
  Yjs regions; make restore a structural operation with an explicit base-vector
  or conflict result. Preserve the current metadata-only and sheets behavior.

### W1-12-F04 — Scheduling a task is not retry-idempotent

- Severity: small-to-important trust issue. Confidence: high.
- User consequence: a double click, timeout retry, or offline replay of
  `calendar.scheduleTask` inserts another `scheduled_work_block`; the mutation
  always calls `ctx.db.insert()` and accepts no operation/idempotency key
  (`convex/calendar.ts:308-364`). `moveWorkBlock` and `resizeWorkBlock` do have
  revision checks (`:367-405`), but those protect later edits, not duplicate
  creation.
- Neighbor: ManageBac source records are better behaved. The source calendar
  item and deadline task reuse `ownerAccountId + sourceKey` indexes
  (`convex/calendarShared.ts:164-228`), and legacy migration checks
  `legacyArtifactId + legacyEventId` (`convex/calendar.ts:476-483`). Intentional
  repeated work blocks must remain possible, so deduping by task alone would be
  wrong.
- Bounded remedy: add a caller-generated operation ID to scheduled-block
  creation and a unique server-side replay check; leave intentional separate
  blocks available through new operation IDs. Coordinate with W1-02/W1-10
  before changing shared calendar schema.

### W1-12-F05 — ManageBac timetable projection IDs disagree with refresh logic

- Severity: important. Confidence: high.
- User consequence: a changed ManageBac timetable source can be treated as a
  customization conflict even when the source calendar row is refreshed. New
  and existing timetable projections store `projectionId = String(calendar.itemId)`
  (`convex/managebac.ts:1953-2001`), but `safelyRefreshProjection()` expects
  `artifactId#eventId` and returns false when that split cannot produce both
  values (`:2149-2163`). `commitNormalizedPage()` then inserts an open conflict
  and marks projections conflicted (`:2429-2477`). The subsequent ensure path
  can set the projection active again while leaving the false open conflict.
- Source removal happens to use the calendar-item ID contract
  (`managebac.ts:2235-2245`), so deletion is a different path and should not be
  conflated with update refresh.
- Bounded remedy: choose one projection identity contract. Recommended:
  persist the calendar item ID for timetable projections and refresh that
  calendar item directly, or store the actual timetable artifact/event identity
  consistently. Add repeated-page, changed-source, overlay, and removal tests.
  This belongs to W1-10; no ManageBac production mutation was made here.

### Product choice / unverified integration boundary — secondary studios and embed rows

The registry and embed switch cover document, flashcards, quiz, planner,
sheets, code/visualisations, presentation, whiteboard, timetable, and agent.
Flashcard/quiz attempt state is local interaction state; source content is the
collaborative artifact. Code runtime mounting is visibility-gated and cleaned
up (`artifact-embed.tsx:576-597`). Whiteboard viewport is deliberately personal
(`whiteboard-studio.tsx:681-683`), while nodes and embed rows are shared.

One medium-confidence next-wave race remains unverified: whiteboard reference
creation inserts the `artifactEmbeds` row before adding the Yjs node
(`whiteboard-studio.tsx:894-937`). A tab crash or failed subsequent local
transaction can leave an active row without a node; undo/redo reconciliation
only repairs rows when those actions run (`:1613-1677`). Treat this as a
future cleanup test, not a confirmed launch blocker. The hard-delete fix below
also prevents deleted source/container rows from remaining live.

## Next-wave tests and implementation implications

1. Use two different accounts (teacher/owner and student) with distinct
   `clientId`s. Share an editable artifact, type in both sessions, revoke the
   student, and verify Hocuspocus and Cloudflare separately: the revoked
   session must stop before another edit is broadcast or durably projected.
2. With two human sessions, edit region B in session 2, then restore only
   region A from history in session 1. Read back both regions, Yjs state, the
   history entry, and the conflict UI. Repeat for document, code, presentation,
   whiteboard, flashcard, quiz, timetable, and sheets.
3. Disconnect session 1, make an offline edit, edit the same artifact in session
   2, reconnect session 1, and verify merged content, no duplicate structured
   items, durable acknowledgement, bounded local cache state, and correct
   presence/lease cleanup.
4. Kill the gateway after a human append but before checkpoint, restart it, and
   verify artifact detail, Library listing, and embed projection all converge
   without requiring a new edit.
5. Submit the same ManageBac page twice, then a changed page and a removed page.
   Read back external-record count, calendar item/task count, projection state,
   conflict count, and source-locked/user-overlay behavior. Coordinate setup
   and provider payloads with W1-10.
6. Create, move, undo, redo, delete, and restore a whiteboard embed while
   intentionally interrupting the client between the Convex mutation and Yjs
   node transaction; verify row/node reconciliation and deleted-source state.

Same-account testers are not a reason to prohibit parallel testing, but they
must use separate accounts and client IDs for these scenarios. Same-account
sessions can look like self-collaboration and can exercise account-level
ownership/overlay behavior rather than the intended teacher/student boundary.

## Decisions for parent/Pablo

- Treat Cloudflare as not ready for an enabled production provider until the
  connected-session policy sweep/recheck is implemented or Cloudflare is kept
  explicitly disabled. Hocuspocus is the stronger current authorization path.
- Prioritize the native restore fix before advertising “restore selected”; the
  current label overpromises granularity outside sheets.
- Send the timetable projection-ID mismatch to W1-10 as a concrete integration
  fix, and send scheduled-block idempotency to the calendar/storage owners.
- Do not broaden this patch into a shared protocol rewrite. The existing Yjs,
  gateway append, local persistence, and capability model are usable seams for
  the next wave once the listed boundaries are tested.
