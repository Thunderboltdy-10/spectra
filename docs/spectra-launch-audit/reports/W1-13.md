# W1-13 — Shared local runtime and browser baseline

## Result

The shared local instance-1 runtime reached a known-good state and supported a first Playwright CLI smoke tour of Workspace, Library, an existing Office/DOCX artifact, Settings, Files and devices, and Chat. A current-checkout release bridge was rebuilt and verified against a disposable fixture mount; the UI paired it successfully and showed the mount as `Ready` after one explicit retry.

The later task interruption caused a slow local Convex restart, but the existing instance recovered without reset or data deletion. At handoff, the local Convex endpoint, collaboration gateway, and web health endpoint all returned ready responses. No product source fix or commit was made in this wave.

## Findings grouped by root cause

### W1-13-F01 — Local Convex restart can create a long visible startup gap

- Consequence: after an interrupted task, the supervisor can leave the app unavailable while the existing local Convex database reopens and prepares functions. This delayed the handoff and can be mistaken for a dead runtime.
- Severity: important. Confidence: high.
- Repro/code chain: `scripts/local/stack.mjs` waits for the local backend before starting or declaring the dependent services ready; the configured startup timeout is 900 seconds. The instance-1 local database is large, so the recovered backend took materially longer than the normal launch.
- Evidence: the post-interruption backend process remained responsive and later logged “Convex functions ready”; the stack log then reported gateway/web readiness and `/api/health` returned 200 with both dependencies ready.
- Affected neighbors: every browser scenario, bridge sync, and any test that starts during the startup gate.
- Bounded remedy: add a small operator-facing readiness/wait helper or a timestamped startup-duration line to the audit harness. Do not reset or delete the local database as a workaround. Product launch impact is unproven because the delay was in the local development restart path.

### W1-13-F02 — Bridge state can require one retry after a bridge/runtime rebuild

- Consequence: the Files and devices UI briefly showed the disposable mount as needing attention after the bridge was stopped, rebuilt, and restarted; the visible Retry action recovered it to Ready.
- Severity: small. Confidence: medium-high.
- Repro/code chain: bridge settings use the client status/connect/retry paths in `src/features/spectra/bridge/client.ts` and `bridge-settings.tsx`; bridge health/status are served by `bridge/bridge-core/src/server.rs`.
- Evidence: `settings-after-rebuild.yaml` and `settings-bridge-retry.yaml` captured the transient failure; `settings-bridge-ready.png` showed the same mount as Ready with one available file after Retry. Direct bridge health was paired before the UI retry.
- Affected neighbors: local-file mount recovery and any test that restarts the bridge while the app remains open.
- Bounded remedy: add a restart/reconnect smoke assertion that waits for Convex readiness, reloads status, and records whether automatic recovery occurs before treating Retry as required. No source change is justified from this single recovery event.

### W1-13-F03 — Office/DOCX lens errors are not isolated from bridge/runtime readiness

- Consequence: an existing read-only Office artifact showed a recoverable failure alert and 400/404 lens/media requests during the first open. The first attempt happened before the bridge was connected, so it does not establish a DOCX parser or media regression.
- Severity: future / unverified. Confidence: high that the observation is real; low for root cause.
- Repro/code chain: the artifact surface uses the DOCX lens API and media routes (`src/app/api/spectra/lenses/docx/route.ts`, `src/features/spectra/lenses/docx-lens.ts`, and `src/features/spectra/bridge/resource-surface.tsx`). The UI correctly remained read-only and offered a recovery/open-from-library path.
- Evidence: `office-artifact.yaml`, `office-artifact.png`, and the Playwright console record captured the lens/media failures. No equivalent post-pairing, fully Ready DOCX retest was completed in this wave.
- Affected neighbors: Office preview/read-only collaboration, embedded media loading, and bridge-backed local file resources.
- Bounded remedy: rerun the same existing artifact only after Convex, gateway, and bridge are Ready; capture response status, request path, and rendered body/media. Classify as product defect only if the connected-runtime retest reproduces the error.

### W1-13-F04 — Role and integration parity remain unverified

- Consequence: the smoke tour demonstrates one student account and local runtime behavior, not teacher authorization, second-student collaboration, ManageBac, invitations, or Mac packaging behavior.
- Severity: future. Confidence: high.
- Evidence: only the student account was available; no invitation or external integration mutation was performed.
- Affected neighbors: School, calendar/roster, admin surfaces, authorization boundaries, and desktop packaging.
- Bounded remedy: schedule a two-role browser matrix and a Mac-host bridge run before making parity or launch claims.
