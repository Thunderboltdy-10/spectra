# W1-16 — Spectra launch audit: AI targeting, Bridge, and school setup

## Result

The assigned recordings cover useful UI surfaces, but they do not yet establish a trustworthy launch path for AI mutation, native-file roundtrip, or school synchronization. The strongest issue is a truth boundary: AI content and target changes appear in the studio as a live/optimistic state, then the shell can return to the earlier canonical content while the dock/result card still reads as successful or active. Capture 12 does show a good ambiguity gate, but the run remains waiting for input for the rest of the 123-second recording and its displayed candidate choices do not stay aligned with the artifact opened beside them.

Windows browser-side Bridge states are legible (`Not connected` → `Connecting` → `Connected`, plus `Offline` and `Not running`), but no native Bridge confirmation window, OS folder picker, reboot/autostart, or native Office read/write proof appears. The current architecture explicitly calls Windows the initial platform and macOS packaging later work, so macOS launch readiness is not established.

ManageBac, Agents, Planner, and School administration are route/surface smoke tests only. They do not prove the school setup journey, teacher/student parity, class/workspace creation, ordinary-user authorization, or a real sync.

- The web app owns Library, studios, Live Dock, settings, ManageBac, Agents, Planner, School, and admin surfaces. Bridge is a separate Tauri/Rust helper with a localhost protocol and native filesystem authority.
- The architecture contract says ordinary students and teachers retain the same ordinary product capabilities; admin pages add operational tools. A school launch therefore needs both admin setup and ordinary teacher/student tests, not just an admin page screenshot.

## Findings grouped by root cause

### Live optimistic state is not the same thing as committed work

#### W1-16-F01 — AI body and target changes can revert after appearing successful (High, confidence: high)

Capture 10 is the clearest reproduction. Around f-047 (`t≈46s`) the open `QA10 AI Edit 691552` body reads `QA10-PARAGRAPH-BETA-691552: The new wording after AI edit.` while the dock says `Update QA10 AI Edit` and `Changing only the reque...`. Around f-056 (`t≈55s`) the body has returned to `QA10-PARAGRAPH-ALPHA-691552: The old wording stays until AI changes it.`, the studio says `Reconnecting`, and the dock still contains completed-looking task cards. F-068 still shows ALPHA with `Saving...` and a Bridge-related recovery sentence. This is an observable contradiction, not a claim about the hidden backend result.

Capture 11 gives the same shape across artifacts. At f-041 (`t≈40s`) the URL/title is `QA11 Report Final 692014` and the body is the original FINAL body; by f-045 (`t≈44s`) the route/title/body have returned to `QA11 Report Draft 692014` and the original Draft body. The explicit prompt asked for Final and explicitly prohibited editing Draft. The recording therefore does not show a silent Draft mutation, but the visible final state is still not a trustworthy readback of the claimed result.

Current-HEAD correlation: `src/features/spectra/pages/spectra-shell.tsx:2308-2355` intentionally reads the overview and focused artifact independently, and its own comment notes that those reads can be one revision apart. `mergeLiveAiArtifact` at `:297-351` preserves live AI chrome over a lagging snapshot; `applyLiveArtifactPatch` at `:2357-2570` applies live preview content and AI state to the shell. `use-spectra-run.ts:622-631` and `:937-941` invoke the terminal callback, while `spectra-shell.tsx:2701-2707` reloads the overview before opening a result. These are plausible boundaries for the recorded divergence, but the recording build is unknown, so this is a current-HEAD risk correlation rather than a source-proven regression verdict.

Required behavior: keep a stable `(runId, artifactId, server revision)` through preview, commit, open, and readback. The UI should label a live body as preview/working until a canonical artifact read confirms the expected revision/content; only then should the card say completed. If the final read differs, expose a recovery state with the affected artifact and retry/inspect actions.

#### W1-16-F02 — Result/open completion is claimed before identity and durability are visually closed (Medium, confidence: high)

Capture 13 reports `Created “QA13 Created Doc 692586” ... opened it in the Document studio` at f-001 (`t≈0s`) while the main surface is still Library. By f-056 (`t≈55s`) the conversation/card instead names `QA13 Created Doc 692835`; f-058 (`t≈57s`) finally opens that document and shows the exact `QA13-CREATED-BODY-692835` paragraph. The eventual open is positive, but the ID change and the near-end readback leave no evidence that the first reported object and the opened object are one durable identity.

Current-HEAD correlation: result-card `open` is handled by `use-spectra-run.ts:1223-1225`; the shell callback at `spectra-shell.tsx:2701-2707` performs a fresh overview lookup and then opens the panel. The callback is a sound place to enforce identity, but a result card's prose is not itself proof that the panel has opened. The card should distinguish `Created`, `Opening`, `Opened and verified`, and `Could not open`.

### Target resolution and user input need a closed-loop contract

#### W1-16-F03 — The ambiguity gate is intelligible but its run can remain unresolved and its context can drift (High, confidence: high)

Capture 12 correctly stops instead of silently choosing. At f-001 the centered card asks `Which Spectra work should I change?` and offers exactly two choices; `Skip for now` is visible. No choice is made in the recording. Through f-123 (`t≈122s`) the card remains, the dock still says `Needs input`, and the Library remains visibly unorganized. The run does not surface a clear timeout/cancel/completed-with-no-op outcome in the captured interval. At f-020, `QA12 Beta Notes 692439` is open even though the pending choices are `QA12 Beta Notes 692280` and `QA12 Alpha Notes 692280`; this is an identity/context mismatch in the visible experience, regardless of whether the extra object came from an earlier run.

Current-HEAD correlation: `src/app/api/spectra/run/loop/resolve.ts:620-657` constructs the choice card, and `:811-817` returns clarification for an ambiguous target rather than applying operations. `resolveArtifactTarget` at `:301-450` scores title, selection, focused-work, summary, and recency evidence. `src/features/spectra/runs/live-dock/live-dock-model.ts:165-178` maps clarification to `needs_input`. The source supports the safety intent; the recording exposes the missing completion/reconciliation contract around that intent.

Required behavior: freeze mutations while a choice is pending, bind the choice card to the exact candidate IDs/revision snapshot, show the selected ID after selection, and provide explicit `Cancel`/`Skip` semantics. A no-choice timeout should end as a no-op or paused run, not a changing stream of progress cards. After a choice, verify that only the selected artifact changed and that the selected object is the one opened.

#### W1-16-F04 — Current source has target safeguards, but the wrong-target recording must be rerun on current HEAD (Medium, confidence: medium)

Capture 11 is not evidence that Draft was edited: the Draft body remains unchanged at the end, and the Final object is briefly opened at f-041. It is evidence that the user can be returned to the prohibited/open Draft after the correct target is touched, which makes a correct run look wrong and makes a failed commit look successful. Do not diagnose this as the historical “open artifact always wins” behavior without a fresh run against the current baseline.

Current-HEAD already has a positive safeguard: `resolvePlanArtifactTargets` returns a clarification plan for an ambiguous target and throws for an unresolved permissioned candidate (`resolve.ts:811-817`), while `resolveArtifactTarget` only resolves above explicit confidence thresholds (`resolve.ts:427-450`). The next live test must capture the same prompt with current source, record run/artifact IDs, and inspect both Final and Draft after reload. The test must verify both “correct target changed” and “open Draft unchanged,” not rely on the transient studio view.

### Bridge/platform evidence is browser-side and Windows-only

#### W1-16-F05 — Pair/mount state is legible, but the required native handshake and filesystem path are not proven (High, confidence: high)

Capture 17 shows the browser settings page at f-001 as `Not connected`, f-007 as `Connecting this device. Keep Spectra Bridge open`, and f-013 as `Connected`. Capture 20 shows the storage policy cards, including `Both Recommended`. This is good product copy and a useful browser state transition. It is not proof of the architecture's required Bridge-side code confirmation, token binding, native folder selection, mount scan, or reconnect after browser restart. The Library's `__bridge-sacrificial` folder and four visible items establish that some file-shaped state is present, not that the end-to-end mount is safe.

Current-HEAD correlation: `src/features/spectra/bridge/bridge-settings.tsx:241-335` maps reachability to the visible status/button and says pairing remains active while the Bridge is open. `src/features/spectra/bridge/client.ts:114-158` supplies honest `Offline`, `Not running`, `Not connected`, and `Connected` copy. The architecture contract requires both browser↔Bridge pairing and Bridge↔cloud sync, so the browser screenshots cover only one side.

#### W1-16-F06 — macOS launch/readback is not release-ready or evidenced (Launch blocker for a two-platform requirement, confidence: high)

All Bridge captures are Windows Chrome screen recordings. Current source/docs explicitly say Windows is the initial platform and macOS/Linux are later packaging work (`docs/spectra-nova/ARCHITECTURE-BRIDGE.md:9-10`). `bridge/bridge-core/src/platform.rs:37-151` contains full Windows-specific file identity, share-lock, credential, and atomic-replace behavior; the `#[cfg(not(windows))]` implementation at `:153-208` uses a fallback metadata identity, reports no lock, and makes autostart a no-op. `bridge/bridge-app/src/main.rs:117-145` has a Windows-only autostart repair and a no-op non-Windows branch; `bridge/bridge-app/Cargo.toml` has a Windows-only `winreg` dependency.

This is not a claim that the Rust core cannot compile on macOS. It is a direct gap against the requested Windows-and-macOS launch requirement: there is no macOS packaging/login-item/Keychain/native-dialog/readback evidence in the assigned captures or the current architecture. macOS needs a dedicated signed bundle, login-item/autostart path, Keychain behavior, security-scoped folder access, file identity/lock/readback semantics, update path, and real Office roundtrip tests before parity can be claimed.

#### W1-16-F07 — DOCX/XLSX/PPTX roundtrip and conflict recovery are not demonstrated (High, confidence: high)

Capture 18's strongest file evidence is a folder list containing `complex-structure.docx` with `3 conflicts`; later frames show an imported `qa-resource-citizen` as `Format BIN`, `Location Spectra`, `Profile Strict native`, and `Download native copy`. Capture 19 shows no spreadsheet or presentation editor after the ignored landing frame. No native Office app edit/save/reopen, preserved OPC parts, formula/chart preservation, conflict-resolution action, or before/after hash is shown. Treat these as file listing/import metadata, not roundtrip proof.

The fidelity contract is appropriately conservative (`docs/spectra-nova/workbar-artifact-capability/WORKBAR-ARTIFACT-CAPABILITY-CONTRACT.md:63-69`), but the launch bar still requires a per-format evidence matrix. Until it exists, expose unsupported/preserved-only states explicitly and avoid success language that implies an editable native roundtrip.

#### W1-16-F08 — Offline and storage copy is honest, but queue/replay persistence is unproven (Medium, confidence: high)

Capture 24 communicates offline state well: the banner says work can continue and changes will be sent after reconnect; the Files tab shows `Offline` and then `Not running`. Captures 17/20 make the storage choices easy to parse. None shows a mutation queued while offline, a reconnect, replay, conflict, or persisted choice after reload. At 1280×800 the persistent dock also covers the lower selected-folder/toggle area, adding manual setup friction.

The next test should create one disposable local fixture, record pre/post hashes, toggle each policy, disconnect Bridge/browser independently, perform an edit, restart both processes, reconnect, and verify journal replay and final state. Originals must remain untouched.

### School launch surfaces are only smoke coverage

#### W1-16-F09 — ManageBac is stuck at validation/empty data in the capture (High, confidence: high)

Capture 21 shows `Validating ManageBac capabilities`, The Global College as a read-only operational connection, automatic import settings, `Review` conflict resolution, and zero current classes/tasks. The capture never reaches verified identity, class choice, workspace materialization, or synced task/calendar data. This is a useful surface and a clear “paused until validation finishes” message, but it is not a school setup pass.

Current-HEAD correlation: `src/features/spectra/pages/managebac-integration-shell.tsx:644-760` exposes the connection page, identity-resolution action, sync action, and validation gating. The next run needs to exercise those actions with a safe read-only fixture and then repeat as a teacher and student, verifying privacy and capability parity.

#### W1-16-F10 — Agents prove list/draft visibility, not creation, release, or sharing (Medium, confidence: high)

Capture 22 loads `Agent library` with empty Discover/Installed collections and a Yours collection. The `Agent draft created` toast and count change show a draft-side action, but no editor fields, saved instructions, publication/release, install, share, or consumer use are shown. Current route source is `src/features/spectra/pages/agent-library-shell.tsx:789+`; this needs a complete teacher-create → share/publish → student-use test.

#### W1-16-F11 — Planner form is not a reminder proof (Medium, confidence: high)

Capture 23 opens `New Planner task` and exposes useful fields, but the due date/reminder values are not set or visible and nothing fires. The dock's `Create QA13 Document` thought popup is unrelated evidence. The next test needs a disposable task with due date, reminder, timezone, recurrence (if supported), reload, and actual notification delivery.

#### W1-16-F12 — Admin smoke does not establish school authorization or class setup (High, confidence: high)

Capture 26 shows a coherent admin route: one active member/admin, zero invitations, accepted invitation state, usage, People, and School tabs. The School view simultaneously says ManageBac last success `Not yet`, `Overview: Not supported`, and zero classes/upcoming/resources. No invite, role transition, class creation, governance, sync, ordinary teacher, or ordinary student test occurs.

Current product guidance says admin pages add operational tools without narrowing ordinary capabilities (`docs/spectra-rebuild/next-generation-plans/05_ADMIN_AND_SUPERADMIN.md:5-7`). The next wave must prove that separation with two ordinary identities plus one school admin, including attempts to access only the intended admin surfaces.

### Surface quality and intelligibility

#### W1-16-F13 — Persistent dock collisions and duplicate-looking cards obscure the evidence (Medium, confidence: high for the recording; current-HEAD status: medium)

At 1280×800 the bottom dock repeatedly covers content: Planner's `Reminders` area, Bridge's selected-folder section, and lower Library rows are partly hidden. Captures 10, 11, 12, and 13 also show several same-looking cards for the same task family at once. Capture 13 has three `Create QA13 Document` cards; capture 12 has several `Organize QA12 Library` cards. This makes it difficult to know which run owns the result and whether a green check is durable or merely an older card.

Current HEAD contains same-thread/run filtering in `src/features/spectra/components/live-dock.tsx:549-568` and renders the optimistic `Starting run` surface at `:767-775`, so the recording may predate or exercise separate run IDs rather than a current dedupe failure. Regardless, the visual acceptance test should use one unique run card per runId, stable card ownership, a collapsible/scroll-safe dock, and a 1280×800 collision pass.

#### W1-16-F14 — Loading/skeleton transitions need a bounded, attributable state (Low/Medium, confidence: high)

Several short captures show full-page skeletons or blank transitions (`11`, `13`, `18`, `19`, `23`, `26`). A brief load is acceptable, but in combination with the returning Draft/ALPHA content and changing run IDs it becomes hard to distinguish loading, stale data, reconnect, and no-op. Each transition should name the surface being loaded, preserve the last stable artifact identity, and expose a retry/failure result instead of silently swapping context.

## Next-wave tests and implementation implications

1. **Current-HEAD AI edit/create harness.** Run unique QA markers on `43c45cc5`, capture runId/artifactId/result-card IDs from the network or server logs, wait through terminal state, reload the page, and reread both the changed object and a control object. Assert that the displayed body, URL/title, card target, and server revision agree. Include a reconnect during the run.
2. **Target safety matrix.** Use two same-type, similar-title artifacts. Test exact title, explicit “not the open one,” no target, ambiguous choice, choice acceptance, skip, and cancel. Verify no mutation before choice; after choice, verify only the selected artifact changed and the open artifact is unchanged.
3. **Create/open contract.** Create one unique document, require the same server-generated ID in the result card, URL, opened studio, and post-reload readback. Do not say “opened” until the studio confirms that ID; surface `created but not opened` separately.
4. **Windows Bridge E2E.** Show the Bridge native window and matching code, use the native folder picker, confirm the selected mount, reboot/autostart, disconnect/reconnect, and perform DOCX/XLSX/PPTX read/edit/save/reopen tests with hashes and conflict recovery. Use disposable fixtures only.
5. **macOS Bridge release gate.** Produce a signed/notarized app and run login-item, Keychain, security-scoped folder, native dialog, Office lock/readback, updater, disconnect/reconnect, and crash/restart tests. Do not mark macOS supported based on the portable Rust core alone.
6. **ManageBac school journey.** Configure a read-only fixture, complete capability validation and authenticated school identity, select classes, materialize workspaces, sync tasks/calendar/resources, exercise review conflicts, then repeat the relevant surfaces as teacher and student. Verify that admin data does not expose private ordinary content.
7. **Agents, Planner, admin.** Complete teacher agent create/publish/share → student discovery/use; Planner due/reminder/reload/notification; admin invite/role/class/governance flows. Record denial and privacy behavior for ordinary identities.
8. **1280×800 visual pass.** Keep the dock from occluding required controls, show only one card per runId, label stale/reconnecting/preview states, and use bounded skeletons that retain artifact identity.
