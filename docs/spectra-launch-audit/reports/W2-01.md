# W2-01 — Measured costs and hosting options

## Result

This report gives a measured local-production workload baseline and a bounded hosting/cost comparison. It is not a whole-product launch verdict.

The primary production-mode build (`8a04e039`, served from the primary checkout) was usable for Library and Workspace navigation. The browser observer measured about 23.5 KB on warm client navigation and about 64.6–65.9 KB on cold reloads in the captured windows. Those are browser delivery measurements, not Convex database I/O or a cloud egress bill. The measurement window included a deliberate settle wait, so its 9.5–15.1 second elapsed values are not page TTFB or an interaction SLO.

The server-side usage helper saw 1.79–20.17 MB of local Convex database I/O per 60-second window and 201–650 non-cron executions per minute. These samples are deployment-wide and overlapped with other Wave-2 sessions, active AI runs, Bridge activity, and self-collaboration. They are useful signals about amplification and dominant functions, but cannot be attributed to one browser or extrapolated to a school-wide bill. Local Convex storage and egress meters were zero in these logs; local development is not a production invoice.

The existing local SQLite database is 7,561,375,744 bytes (7.56 GB decimal, 7.04 GiB). A read-only inspection found 433,615 physical document rows, 53,247 tombstone/deleted rows, 380,368 non-deleted rows, 5,303,656,483 bytes of non-null JSON, and 454,440 index rows. Only 13 SQLite pages were on the free list. The shape is therefore consistent with retained document history, indexes, and SQLite overhead—not a large free-list vacuum opportunity. No reset, delete, vacuum, export, migration, or private-content dump was performed.

The two consequential live workflows did not pass their intended contracts. A cloud-only DOCX opened into the user-visible read-only fallback after `/api/spectra/lenses/docx` returned 400 (`DOCX_LENS_FAILED`) and a media request returned 404. A disposable mounted DOCX did show an editable editor; after a typed marker, the editor remained `Syncing…` for roughly 20 seconds and the native file size/hash did not change. Reopen/readback was not completed because the shared Convex backend subsequently went offline. The AI edit similarly failed before mutation: the UI reported a one-second `orgTree:liveIdentities` timeout, recovery exhausted, and the fixture remained unchanged.

Recommendation: keep managed Convex as the default launch evaluation target until an isolated production usage window proves the real plan/region/traffic cost. Do not select self-hosted Convex on price alone: it trades vendor meters for persistent-volume, backup/restore, failover, upgrade, observability, and incident ownership. Keep small metadata, summaries, hashes, permissions, and hot semantic projections in Convex; evaluate a separate object-storage boundary for large immutable native payloads, import originals, assets, and cold version/snapshot bodies only after the hash/refcount/ACL/GC/backup contract is explicit.

The roughly 2.26 GB difference between physical file size and non-null JSON bytes is not itself a billable category. It includes SQLite pages, indexes, metadata, tombstones, and retained persistence rows. The schema confirms separate `documents`, `indexes`, and `persistence_globals` persistence tables. The source audit also identifies intentionally duplicated representations across canonical artifact content, summaries, protected bases, replicas, payload metadata, versions/snapshots, collaboration updates/snapshots, and Bridge write bases. A table-aware inventory is still required before deciding which bytes are safely retainable or movable.

`RUNTIME.md` records that the backend startup working set reached roughly 19.5 GB before falling below 0.5 GB. That is process-memory/startup behavior, not stored database size, a Convex cloud meter, or a per-user forecast. This task did not reproduce or attribute the peak.

### Exact room projection seam

The W1 response projection change is present in the current primary source:

- `convex/collaborationGatewayStore.ts:271-346` defines `load`. It first queries the room, then unconditionally executes `ctx.db.get(args.artifactId)` at lines 289–290. This reads the full `spectraArtifacts` document even when the normal returned response does not include content.
- The response includes `initialProjection` only when `afterSequence === 0 && includeInitialProjection === true` (`:334-345`). The normal gateway load omits it; the legacy/non-native bootstrap branch explicitly requests it in `scripts/collaboration-gateway.mjs:1195-1225`.
- `convex/collaborationGatewayBridge.ts:151-205` forwards the optional flag and returns the bounded room/snapshot/update envelope.

Therefore W1 reduced response serialization and browser/gateway bandwidth for native reloads, but it did not remove the full artifact database read. The exact per-call DB-I/O bytes were not isolated in this task: the usage windows overlapped several clients and the backend later stopped, and no clean `collaborationGatewayStore:load` sample could be joined to one artifact size. The safe conclusion is one full-artifact read per `load` invocation; the byte amount remains unknown until a clean named deployment window or bounded harness records it.

- [Fly Volumes overview](https://fly.io/docs/volumes/overview/) says a volume exists on one server in one region and attaches to one Machine; daily block-level snapshots default to five days, but Fly explicitly says important data needs its own backup plan. ## Findings grouped by root cause

### W2-01-F01 — Cost identity and per-journey attribution are not launch-ready

Severity: important. Confidence: high for the evidence gap.

User consequence: the team cannot turn the current measurements into a defensible monthly bill or a school-size capacity budget. Browser bytes, WebSocket bytes, Convex DB I/O, file storage, egress, Fly compute, and model charges are different meters.

Repro/code chain: the browser observer is per-session, while `convex-window.mjs` reads deployment-wide completion usage. Four labelled windows overlapped other Wave-2 browser sessions, active run retries, Bridge polling, and self-collaboration. The current handoff proves a local instance and a build, not a production Convex deployment/plan/region/account or Fly app usage identity.

Evidence: the four copied usage windows above; browser navigation table; current `RUNTIME.md` explicitly says the local startup/working-set observation is not a cloud or per-user forecast.

Affected neighbors: W2-02 data reads, W2-03/04/06 AI lifecycle, W2-07/08/09 Office, W2-12 Bridge, and the parent’s final deployment checklist.

Bounded remedy: run one isolated 15-minute window per scenario on a named production-like deployment with no other sessions; record exact build, Convex deployment/region/plan, Fly app/machine/region, active users, and scheduler state. Add sanitized journey/run correlation in usage logs or a test-only account/deployment so function chains can be joined without recording content.

### W2-01-F02 — The local database is persistence/history/index heavy, with no free-list shortcut

Severity: important. Confidence: high for current file statistics; medium for the exact named-table attribution.

User consequence: slow startup, high working-set risk, longer backup/restore, and future volume pressure are plausible. A simple vacuum or reset is not an evidence-backed fix and would destroy audit state.

Repro/code chain: read-only SQLite totals show 7.56 GB physical size, 433,615 persistence document rows, 53,247 tombstones, 380,368 non-deleted rows, 5.30 GB non-null JSON, and 454,440 index rows, with only 13 free-list pages. `persistence_globals.table_summary_v2` contains 185 opaque table entries, but the backend outage prevented a safe named mapping. W1-01 documents intentional duplicate content representations across artifacts, replicas, payloads, versions/snapshots, and collaboration state; W1-02 separately documents unbounded history/orphan lifecycle paths.

Evidence: the read-only SQLite table above; `RUNTIME.md` startup working-set note; no mutation or content dump.

Affected neighbors: artifact/version retention, replicas/payloads, collaboration snapshots/updates, Bridge write requests, backup/export, and self-hosted volume sizing.

## Decisions for parent/Pablo

- **Managed Convex is the recommended default for launch evaluation.** The current official Professional price and included meters make a small pilot plausible, and the hosted product retains the operational features the current design needs. This recommendation is conditional on an isolated production usage window and a proven deployment identity; it is not derived from the noisy local MB/min samples.
- **Do not self-host Convex solely to escape DB-I/O cost.** The official self-hosting material calls out a multi-service setup, persistent storage, and hands-on operation. Fly’s volume is local to one server/Machine and daily snapshots are not a complete backup plan. Self-hosting becomes reasonable only if data residency/control or a measured usage profile justifies owning RPO/RTO, backup/restore, failover, observability, upgrades, and incident response.
- **Keep the hot semantic/collaboration path in Convex.** Summaries, permissions, hashes, refcounts, room metadata, bounded update tails, and active projections need reactive query semantics. Moving them to an object store would not fix subscription/query amplification and would make collaboration correctness harder.
- **Consider object storage for large immutable binary boundaries.** Native payloads, import originals, large assets, and cold version/snapshot bodies are the strongest candidates. Convex’s own self-hosting materials document S3-compatible storage options; external storage can lower database/file pressure but introduces request/egress cost, signed URLs, hash verification, refcounts, GC, retry, ACL, export, and restore obligations. No migration should begin until those invariants and an offline Bridge fallback are tested.
- **Treat the current native and AI failures as capability evidence, not cost-only tuning items.** A smaller bill does not compensate for read-only Office fallback, pending native writes, or an AI edit that never commits. Reliability/readback acceptance must precede scale or storage migration.
- **Do not use the 7.56 GB SQLite size as a production cloud-storage quote.** It is a valuable retention/index/startup signal. It needs named-table accounting and a retention policy before pricing or cleanup decisions.
