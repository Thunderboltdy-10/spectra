# W2-03 — Vague AI requests and correct targeting

## Verdict

The live baseline does not silently mutate the open Draft when the user asks to update the Final. The clarification UI names the Final artifact and exposes a bounded choice, and both synthetic sibling artifacts remained unchanged after fresh readback.

There is, however, a high-severity continuity defect after the choice is accepted: the selected artifact identity is lost before the follow-up run. The UI reports a success-like update, but the canonical Final readback is still the original content and the chat transcript then reports `0 context objects selected` followed by a permissioned-work mismatch. This is a durable choice-identity/protocol problem, so it is report-only for W2-03.

A separate contained defect was fixed in the source worktree: permissioned search/read failures no longer become indistinguishable from empty or not-found results. The patch is committed as `c245a204f8f545cdd62c76cc3628746bac55db95` (`fix(spectra): preserve permission read failures`). The running launch-audit service was not restarted, so the source patch was not claimed as a live-runtime result.

## Live scenario results

### `make this clearer` with Draft open

The Draft was open and its composer was used for the ordinary prompt `make this clearer`. The run paused with the bounded request: `I could not match that request to permissioned Spectra work. Name or select the work you want to change.` It did not guess the focused Draft as a mutation target.

I selected `Skip` to terminate the ambiguity safely. The resulting response explicitly left the selected Draft unchanged because it was marked as an untouched sibling. A fresh Draft view and reload still showed the original Draft marker.

Result: safe non-mutation, but no useful recovery path for the vague request.

### `update the final version` with Draft open

With the Draft still open, the ordinary prompt `update the final version` produced a target clarification for the named Final artifact:

`What should be changed in “LA-W2-03 Revision Final”?`

The bounded choices included `Make the wording clearer`, `Replace the text`, `Copy the draft`, and `Skip for now`. This is the correct safety posture for a different named artifact being requested while a sibling is open.

I selected `Make the wording clearer`. The Live Dock then displayed a success-like response saying it had updated the Final introductory sentence and preserved the separate Draft. The open Draft remained unchanged. A fresh open and a full reload of the Final both still showed `LA-W2-03 FINAL ORIGINAL. Keep this sibling untouched.` The Draft also still showed `LA-W2-03 DRAFT ORIGINAL. Keep this sibling untouched.`

The associated chat readback makes the continuity failure explicit. After the choice, the transcript contains:

- user: `Make the wording clearer`
- assistant: `I could not match that request to permissioned Spectra work. Name or select the work you want to change.`
- context status: `0 context objects selected.`

Result: sibling preservation passed, but the accepted clarification did not carry the selected Final identity into the follow-up run; the success-like Dock message is contradicted by canonical artifact readback.

## Source trace for the targeting defect

The relevant path is split across the client, durable choice storage, and continuation gatherer:

1. `src/features/spectra/components/live-dock.tsx` sends the selected choice title to `onInput` together with the thread ID, but no selected candidate ID.
2. `src/features/spectra/pages/spectra-shell.tsx` forwards only `{ threadId }` to `runEngine.run`; the follow-up therefore reuses the current UI closure rather than the candidate that was selected in the clarification.
3. `src/app/api/spectra/run/loop/plan.ts` sanitizes choice options to title and description. Candidate IDs from `request_context_target` are not retained in the persisted choice options.
4. `convex/spectraThreads.ts` persists `choiceSelection` as only a key/title pair.
5. `src/app/api/spectra/run/loop/gather.ts` recovers a selected clarification by finding an assistant message whose selected title is a substring of the new prompt. It can recover the unresolved question text, but not a durable selected candidate identity.

This explains the live sequence without relying on the historical rollback recording: the Final candidate is correctly offered, the title is accepted, but the follow-up has no canonical `(runId, artifactId, revision)` target identity. Adding that identity and carrying it through the choice protocol would be a larger durable redesign and was intentionally not implemented in this audit.

## Source fix implemented

`src/app/api/spectra/run/loop/io.ts` now exports `readQuery`, which converts a backend read exception into a sanitized, retryable `context_read_unavailable` result. `executeAgentReadTool` uses it for:

- `search_objects`
- `read_artifact`
- `read_workspace`
- `read_thread`

Legitimate empty results and `*_not_found` results remain distinct. The bounded agent loop can now see that a discovery/read attempt failed and either use existing context, make one changed/bounded attempt, or stop with an honest limitation instead of treating the failure as absence.

No change was made to choice identity, dispatcher ownership, attachment retry behavior, or service state.
