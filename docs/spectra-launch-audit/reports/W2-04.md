# W2-04 — AI attachments, steering, retry, and run lifecycle audit

## Result

**CONDITIONAL — attachment reading is useful in a first run, but attachment retry is not launch-safe.**

The live run could correctly read the DOCX/XLSX fixture and answer the control markers, average (`2.02 s`), and equation. A chart/image run timed out, exposed Retry, then completed a second attempt that explicitly said it could not access the image. The retry payload drops all attachments. This was fixed fail-closed in the audit worktree: attachment-backed stopped/failed runs no longer advertise or accept Retry and instead tell the user to reattach the files. The durable-source option remains a planned follow-up; attachment bytes were not added to run rows.

The broader attachment claim remains blocked until the worktree commits are integrated into the primary runtime and a live failure/retry test passes. Steering was exercised only as a late, no-op attempt after the DOCX/XLSX run had already completed; true mid-flight steering and stale-event behavior remain unverified because the shared Convex runtime became unavailable during the final probe.

## Scope and current architecture

| Stage | Current path | Lifecycle implication |
| --- | --- | --- |
| Input | `command-bar.tsx` reads local files into `CommandAttachment` objects containing metadata and data; `POST /api/spectra/run` prepares them | Original bytes exist in the request and initial execution only. |
| Durable start | `runtime.ts` calls `spectraRuns:beginRun` with attachment metadata, then schedules/executes `runAttempt` with prepared attachments | `spectraMessages.metadata.attachments` records names/type/size/handling, not bytes or a reusable source ref. |
| First execution | `runtime.ts:runAttempt` builds context/provenance and passes prepared attachments to the model/visual path | First-run DOCX/XLSX parsing worked live; image path hit a 1-second Convex timeout in the shared build. |
| Retry | `spectraRuns:resetForRetry` resets the same run/execution; `runtime.ts` reconstructs the payload | Before this audit, scheduled and inline retry both explicitly used `attachments: []` (`runtime.ts` retry path). |
| Client | `use-spectra-run.ts` owns live NDJSON, durable polling, stop, retry, and stop-plus-new-run steering; `run-ledger.ts` projects events by `runId` | Events have no execution/supersession identity in the client contract. |

The authority boundary is still the durable Convex run/card/message/operation state. The browser’s optimistic card is presentation only; it must not claim that a retry is safe when the source envelope cannot be reconstructed.

## Findings grouped by root cause

### A. Attachment source is request-scoped, but retry is run-scoped

#### W2-04-F01 — Attachment retry silently loses the original source

- **User consequence:** A retry after an image/PDF/DOCX/XLSX/PPTX failure can look like a normal resume while the model no longer has the source bytes. It may answer “cannot access,” guess, or act from incomplete context.
- **Severity / confidence:** **Launch blocker for attachment retry; high confidence.**
- **Code chain:** The first request prepares full attachments and passes them to `runAttempt`; `beginRun` persists only `{name,mimeType,size,handling}`. The retry reset returns prompt/context only, and both retry execution branches reconstruct `attachments: []`.
- **Live evidence:** Image run failed with a timeout, Retry was shown, second attempt completed with “I can’t access the attached image.” The thread still displayed the attachment name, which makes the missing bytes especially easy to miss.
- **Bounded remedy completed:** `convex/spectraRuns.ts` and `runtime.ts` now detect attachment metadata and make stop/failure recovery non-retryable with “Attached files are not retained for retry. Reattach them and start a new run.” `resetForRetry` rejects direct callers too. The client’s optimistic Stop card no longer fabricates Retry before the durable response.
- **Remaining limit:** The fix is in worktree commits `46fb93ad` and `0ad7aa04`, not in the live build. A durable, permission-bound, expiring source reference or an explicit reattach flow is still required for true retry semantics.

### B. Read intent and creation intent are not isolated for attachment responses

#### W2-04-F02 — “Do not edit anything” still produced sheet-building progress and a derived artifact

- **User consequence:** A user asking only to inspect attached files can see creation/edit activity and receive an Attachment Report artifact with workspace actions. Even when the source files are not mutated, this creates unrequested work and makes it hard to tell whether “read-only” was honored.
- **Severity / confidence:** **Important; high confidence in the observed UI, medium confidence about whether the derived artifact was durable because Convex became unavailable before a second readback.**
- **Evidence:** `doc-xlsx-running.yaml` shows the sheet canvas/new-sheet/build progress; `doc-xlsx-after-steer-attempt.yaml` shows the correct answer plus `LA-W2-04 Attachment Report` and `1 actioncompleted`.
- **Bounded remedy:** Keep attachment read/answer mode separate from artifact creation. Treat explicit no-edit/no-create language as a hard plan constraint; only create a report when requested or after confirmation. If a derived preview is unavoidable, label it as ephemeral and omit “Add to workspace.”

### C. Run attempts and client presentation do not share a durable supersession identity

#### W2-04-F03 — Steering and retry lack an execution/supersession contract

- **User consequence:** Steering is implemented as stop the old run, then start a new run in the same thread. A late old event, a replayed terminal event, or a retry attempt sharing the same durable `runId` can race the new presentation. The server’s operation execution IDs reduce mutation risk, but the client event schema does not make “which attempt is authoritative” explicit.
- **Severity / confidence:** **Important; medium-high confidence from source, live mid-flight steering unverified.**
- **Code chain:** `use-spectra-run.ts:1147-1172` stops then calls `run(..., {threadId})`; durable event cursors and `run-ledger.ts` entries are keyed by `runId`; `parseSpectraStreamEvent` carries no execution/supersession ID. The observer silently skips parse failures and swallows outer polling failures.
- **Affected neighbors:** Live progress, final card selection, `onFinal`, thread refresh, and artifact patch queues. This extends W1-03-F08/F09 rather than replacing those findings.
- **Bounded fix completed:** Request begin-timeout/Stop cleanup is now keyed by the request exchange (`0ad7aa04`), preventing one pending run from aborting another and preventing an optimistic Retry claim before durable safety is known.
- **Recommended remedy:** Add `executionId` plus `supersedesRunId`/`supersededByRunId` to durable event envelopes and client ledger entries. Ignore old-attempt events after the new authority is known, preserve old history in cards, and expose a bounded observer-resync state instead of silently dropping malformed/poll-failed events.

#### W2-04-F04 — Duplicate submission protection is present but not live-proven in this pass

- **Severity / confidence:** **Small current gap; medium confidence.**
- **Evidence/code:** `beginRun` queries owner plus `submissionKey` before creation (`convex/spectraRuns.ts:298-317`); the client sends a stable exchange key (`use-spectra-run.ts:1045`) and serializes steering per run (`:1117-1130`). The direct live duplicate probe could not reach Convex after the backend refused connections.
- **Remedy:** Add a Convex lifecycle regression that calls `beginRun` twice with the same owner/submission key and asserts one run/message/card. Add a browser test that double-submits the same UI event and reads back one user message and one effect. Do not rely only on the disabled Send button.

## Next-wave tests and implementation implications

1. Integrate the two commits, then repeat image/PDF/DOCX/XLSX/PPTX failures, Stop, Retry, and reload. Expected interim behavior is an explicit reattach message and no Retry action; after source-envelope work, expected behavior is byte/hash-verified rehydration with the same permission scope.
2. Add attachment-aware route tests for worker failure, worker stop, stale-run reconciliation, and direct retry reset. Assert no `retry` action and the reattach copy whenever the input metadata contains attachments.
3. Add a read-only attachment contract test: “read/report only; do not edit or create” must produce an answer-only card with no created sheet/document and no Add to workspace action. Separately test an explicit “create a report from these files” request.
4. Run true steering during image visual preprocessing, a long document read, and a pending operation. Read back both runs’ terminal events, execution IDs, thread messages, cards, and operation state; assert the new run alone can update live UI and no old run can create/patch work after stop.
5. Inject malformed durable events and force one observer poll failure. Expect a visible reconnect/resync state, cursor repair, and convergence to the durable terminal card; no silent missing final.
6. Double-submit the same command at the network boundary and via two browser contexts. Assert one durable run, one user message, and one set of effects; separately submit two distinct commands and assert their independent run IDs are not cross-aborted.
7. Verify the final NDJSON event with and without a trailing newline, including an attachment failure card, and compare live UI with `runDetail`, thread messages, and run events.

Recommended coherent packages:

- **Attachment source envelope:** short-lived, permission-bound reference/hash/expiry plus explicit reattach UX; keep bytes out of `spectraAiRuns`.
- **Read-only attachment mode:** intent gate and answer-only result contract, separate from artifact creation.
- **Attempt authority:** execution/supersession fields, durable event filtering, observer resync, and lifecycle tests.
- **Duplicate/concurrency harness:** idempotency tests plus two independent pending runs to verify scoped abort/cleanup.

## Decisions for parent/Pablo

- Keep attachment retry out of any broad launch claim until `46fb93ad` and `0ad7aa04` are integrated and the reattach or durable-source design is selected.
- Treat the current DOCX/XLSX result as evidence that first-run extraction is viable, not as evidence that retry or read-only behavior is complete.
- Prefer the fail-closed reattach behavior as the interim product choice. It is honest and schema-neutral; the alternative—placing base64 bytes in durable run records—is not recommended.
- Do not classify steering as passed from the late click. Require a mid-flight test with readback of old/new run events and operation effects.
- The shared runtime was not restarted or reset. The duplicate live probe and any final live rechecks are blocked by Convex connection refusal, not by a new source conclusion.
