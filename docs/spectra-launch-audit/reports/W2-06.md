## Source trace and findings

### W2-06-F01 — No universal K-bar or search/action blend

**Severity: high. Confidence: high.**

The current sidebar Search control is implemented as recent-thread filtering. The local `Open actions` menu is a composer affordance, not a global action palette. The application registry and command types are strong enough to feed a palette, but the UI has no shared index or ranking layer that merges actions, artifacts, workspaces, and threads.

The requested palette should not be inferred from the presence of the `kbar` dependency. The live behavior and source trace show no active universal K-bar mount. This is a product-surface gap, not a missing keyboard shortcut.

### W2-06-F02 — Route-side run-only opens were a real no-op

**Severity: high. Confidence: high; fixed in source.**

Before the patch, `RouteSidePanelHost` handled `run.openConversation` only when `threadId` was already present. A run card carrying only `runId` therefore dispatched successfully to the bus but did nothing on eligible routes. `/chat` already resolved `runId -> getSpectraRunDetail(runId).run.threadId`.

The patched route-side handler now follows the same resolution rule, trims explicit thread IDs, fails with `RUN_THREAD_NOT_FOUND` when no thread can be resolved, and awaits the actual thread fetch. This preserves the `/chat` prohibition on mounting a second route-side chat panel.

### W2-06-F03 — Shared application dispatcher was absent from Chat and route-side ArtifactStudio

**Severity: high. Confidence: high; fixed in source.**

The main Spectra shell passed `executeApplicationCommand` into ArtifactStudio and tiles, but the local ChatShell and the eligible route-side ArtifactStudio did not. That left artifact workbars on those surfaces without the same application action path used by the main shell.

The patch creates the shared dispatcher in both hosts, supplies the existing preference store, maps route navigation through the existing router, and keeps full-artifact opens on the established Library handoff. Route-side open callbacks use throwing fetchers for honest completion; passive restore/bus paths retain their user-facing toast handling.

### W2-06-F04 — `executeCommand` returned before async completion

**Severity: medium. Confidence: high; fixed additively in source.**

The legacy `executeCommand` checks availability, starts `command.execute` with `void`, and returns `true` immediately. That behavior is relied on by existing synchronous workbars and was not changed. It is unsuitable for a future palette, bridge, or AI action surface that needs to show completion, failure, or cancellation.

The patch adds `executeCommandAsync`, which shares the same availability gate, awaits `command.execute`, and returns a completion boolean. Two focused tests cover delayed completion and disabled-command non-execution.

### W2-06-F05 — `insert_reference` is declared but has no safe server handler

**Severity: high for AI reference insertion. Confidence: high; not changed.**

`insert_reference` is registered with `hostWorkId`, `targetWorkId`, and optional label, and the client application dispatcher already forwards `app.reference.insert` through the typed `reference.insert` bus path. The server application executor maps tool IDs and ends in `APP_COMMAND_NOT_REGISTERED` for the missing server case.

This was intentionally not papered over with an orphan `artifactEmbeds.create` write. The existing document handler creates the embed and the editor reference node together, requires an open editable host, and cleans up if insertion fails. A safe AI path needs an explicit client acknowledgment or a server-side operation that can atomically resolve the target anchor, host region, embed, and editor node. The precise next step is to add that protocol and its result event, not to claim completion from an unverified UI event.

### W2-06-F06 — Shared runtime and role state limit launch proof

**Severity: high for authorization/evidence; confidence: high.**

The live account combines a student identity with a visible Super Admin route. School overview returned Access denied for the current school role while ManageBac admin setup remained visible. A later Library overview request returned 500. These facts make this run suitable for route/chrome behavior and integration-state observations, not ordinary-user permission proof or stable artifact-open proof.

## Typed action contract

The existing `Command` and application-command records provide useful identity, params, availability, risk, undo, and AI-authority fields. The next shared action record should make target resolution, completion, cancellation, and viewport explicit rather than relying on caller convention:

```ts
type ActionResult =
  | { state: "completed"; target?: ResolvedTarget; revision?: string }
  | { state: "cancelled"; reason: "user" | "navigation" | "superseded"; partial?: boolean }
  | { state: "failed"; code: string; message: string; retryable: boolean };

type SpectraAction<P> = {
  id: string;
  title: string;
  params: z.ZodType<P>;
  availability: (ctx: ActionContext) =>
    | { state: "enabled" }
    | { state: "disabled"; reason: string }
    | { state: "hidden" };
  target: {
    kind: "route" | "artifact" | "workspace" | "thread" | "library-selection" | "settings";
    resolve: (params: P, ctx: ActionContext) => Promise<ResolvedTarget>;
  };
  completion: {
    mode: "awaitable";
    success: "target-reached" | "server-committed" | "ui-acknowledged";
    evidence: string[];
  };
  cancellation: {
    supported: boolean;
    preservesPartial: boolean;
    stopsFollow: boolean;
  };
  authority: {
    human: "allowed" | "confirm" | "prohibited";
    ai: "allowed" | "confirm" | "prohibited";
    capability?: string;
    risk: "safe" | "confirm" | "always-confirm" | "destructive";
  };
  viewport: {
    surfaces: Array<"sidebar" | "kbar" | "composer" | "library" | "workspace" | "chat" | "route-side-panel" | "live-dock">;
    minWidth?: number;
    presentation: "inline" | "panel" | "full-route" | "modal";
  };
  execute: (ctx: ActionContext, params: P) => Promise<ActionResult>;
};
```

Rules implied by this contract:

- `enabled`, `disabled`, and `hidden` are shared by human and AI consumers.
- Target resolution happens before mutation and is part of completion evidence.
- `completed` means the declared completion condition, not merely that a promise was started.
- A route or panel open can complete on target-mounted/target-loaded; a server mutation must complete on server commit; a client bridge operation must complete only on UI acknowledgment or a verified native result.
- Cancellation is a result, not a boolean side effect. Stop preserves partial work only when the action declares that behavior; user navigation may cancel the visual follow without cancelling a server run.
- Prohibited AI actions stay hidden or disabled with a human-readable reason; they never become palette results through fuzzy search.

## K-bar/search design

### Ranking

Rank one blended result stream with deterministic tiers:

1. exact action ID, exact target title, or exact route name;
2. exact action title plus current viewport/context;
3. prefix match on action/target title;
4. token match across action title, target title, workspace, thread, and route;
5. recency/pinned/frequency tie-breakers;
6. risk and availability tie-breakers only after relevance, never to promote a destructive action.

Hidden/prohibited actions do not appear. Disabled actions may appear when the query is exact and must show their reason. A result row should carry `kind`, `actionId`, `target`, `availability`, `risk`, `sourceSurface`, and a direct execution affordance.

### Search + action blend

The current sidebar Search can become the global index while retaining a dedicated “Search” mode. Search results should include:

- artifacts, workspaces, folders, threads, runs, and routes;
- action suggestions scoped to the current result or current viewport;
- a visible distinction between “open this object” and “run an action on this object”;
- stable result identity and target freshness checks before execution.

### Param/direct toggles

Every action with required params should support two explicit modes:

- `direct`: execute the selected target using defaults only when all required params are resolved;
- `configure`: open a compact parameter stepper/form, validate with the action schema, show risk and target, then execute.

Do not treat a free-text query as a successful parameter resolution. `organize_library`, `delete_library_items`, `insert_reference`, and `continue_run` need explicit target/param confirmation states.

### Continue / stop / follow

Stop is a run cancellation action; Stop following is a viewport subscription action. They must remain separate in the contract and UI. Continue is available only for `Needs input`, while Retry is available for typed retryable failures or Cancelled runs. A partial response must stay inspectable after user interruption.

### Settings context

Palette availability should include hydrated preference scope (`account`, `device`, `workspace`, or `work-type`), current role/capability, compatibility profile, and whether a remote write is pending. Settings actions should show the scope they will change and report persistence completion, not just local optimistic state.
