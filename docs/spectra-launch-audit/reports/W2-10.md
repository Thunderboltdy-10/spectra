# W2-10 — Office protocol architecture and operation coverage

## Result

**Result: not launch-ready for broad native Office editing.** The current path is credible for a narrow, preservation-first subset: ordinary DOCX paragraph/table text, bounded paragraph/run formatting, XLSX cells/formulas/basic formats/merges/freeze panes, and bounded PPTX slide/text/notes/geometry operations. It is not a closed protocol for broad native editing across Word, Excel, and PowerPoint.

The architecture currently has four partially overlapping vocabularies:

1. human/AI command capabilities and manifests;
2. the collaborative editor/Yjs projection;
3. format-specific native delta schemas/materializers;
4. package/Bridge revision and preservation records.

The gate checks capability/fidelity declarations, but does not require that the current projection change can produce a concrete native delta, target a stable native subregion, and pass semantic readback. This permits successful-looking projection changes that produce no native operation and unchanged bytes.

The recommended direction is a versioned lossless Office package base plus typed semantic operations and stable subregion identities. Keep the existing lenses, Yjs, capability matrix, preservation guard, Convex queue, and Bridge boundary as compatibility surfaces, but make them implementations of one operation/result contract rather than independent declarations.

## Scope and current architecture

Audited the detached W2-10 worktree at `43c45cc5`, against the primary audit documents and runtime contract. The source trace covered:

- command and AI capability registration, manifests, fidelity regions, operation gating;
- `LensPreservedCarry`, DOCX/XLSX/PPTX projection contracts, lens materializers, native editor intent;
- editor-content projection/update adapters and Yjs native artifact replacement/undo paths;
- Office API routes for open/materialize/reconcile, package comparison, preservation checks, payload upload, and Bridge queueing;
- Convex replica ownership, lens activation, materialization, Bridge claim/complete, revision and conflict paths;
- the live Library and mounted native artifact paths through the named Playwright session `launch-w2-10`.

The existing design is preservation-first: a lens opens a native payload into a reduced semantic projection and retains the original bytes in `LensPreservedCarry`. Materialization diffs the reduced projection into a narrow format-specific operation list, applies the operation to the retained payload, compares package parts, and queues the resulting payload for Bridge write. The Yjs model is the collaborative editor state, not the native package model; non-sheet replacement is still structural/full-content projection while Sheets has a cell plan.

This is a reasonable compatibility lane. It is not yet a broad Office protocol because the reduced projection and operation schema are not lossless enough to be the shared base for human editing, AI editing, merge, undo, native write, and native readback.

## Findings

### W2-10-F01 — Capability, editor, native delta, and Bridge contracts are not closed

**Severity: launch blocker for broad native editing. Confidence: high.**

The capability inventory exposes 60 document, 75 Sheets, and 34 presentation AI capabilities. The native delta schemas contain only 8, 7, and 10 operation kinds respectively. In the exposed set, 21 document, 33 Sheets, and 18 presentation capabilities have no native delta. Some are intentionally preserve-only or export actions, but others are ordinary offered operations such as Word lists/tables/equations, Excel charts/rows/columns/tables/filters, and PowerPoint style/chart/layout changes.

The declarations are often truthful for strict-native files, but the architecture has no machine-checkable invariant of the form:

`offered operation + current target + current projection -> typed native delta -> verified intended semantic change`.

The current gate can return allowed for a semantic operation whose projection update later yields an empty operation list, or whose delta lacks the identity/field needed to target the intended native object.

**Implication:** broad editing cannot be accepted on capability names alone. Each capability instance needs a native operation family, supported target shape, precondition, and verification contract. “Preserved” and “no native delta” must remain explicit, but a declared delta must also be proven applicable to the current artifact.

### W2-10-F02 — Projection diff drops rich and structural edits as successful no-ops

**Severity: launch blocker for lossless editing. Confidence: high; reproduced by harness.**

DOCX diff ignores rich inline content and equations when block text is unchanged. XLSX update has no native op for defined names or broad workbook topology. PPTX diff does not cover source bindings and can omit text edits when the editor object has no native shape binding. The focused harness produced unchanged package hashes in all three cases.

This is more serious than a visible disabled control: a human/AI projection can look changed, the request can travel through a successful path, and the native package can remain unchanged. The same shape also risks a wrong-target mutation when a flattened text projection maps several native paragraphs/runs to one `paragraphIndex: 0`.

**Implication:** materialization must reject an unrepresentable change with a typed “unsupported target/delta” result. Empty operations are only valid when the semantic projection is proven equal to the native readback, not merely when the current diff function found nothing.

### W2-10-F03 — Native identity is too coarse for rich ranges, embeds, and cross-artifact links

**Severity: high. Confidence: high.**

DOCX IDs identify broad paragraphs/tables, but not stable run/span/equation/drawing targets. XLSX cell IDs are useful for cells but do not extend to names, tables, chart series, validation, filters, or sheet lifecycle. PPTX objects retain a native shape ID in some content, but text is flattened, paragraph identity is not retained, and `sourceBinding` has no corresponding native operation. A new text box operation carries text and slide ID but no durable new-object ID, geometry, style, or binding identity.

**Implication:** merges and undo cannot be reliable at the intended granularity until each editable semantic region has a stable native anchor, source path, identity version, and conflict key. Stable IDs alone are insufficient without a target schema and native precondition.

### W2-10-F04 — Preserved carry is a fallback payload, not a shared lossless package base

**Severity: high. Confidence: high.**

`LensPreservedCarry` keeps a payload alive for one lens call, while Convex activation stores a reduced/possibly compacted projection. The editor and AI operate on that projection; native writes reconstruct only the subset represented by typed deltas and reuse the original payload for everything else. This is adequate for “touch a safe cell while preserving unknown parts,” but not for broad mixed editing where a changed semantic region must coexist with unknown package content, links, calculations, macros, media, and format-specific relationships.

The absence of a versioned package manifest/part graph/relationship graph and per-region fingerprints makes the retained payload a hidden side channel rather than the common base shared by editor, AI, merge, undo, and Bridge.

**Implication:** introduce an immutable `OfficePackageBase`/manifest identity and semantic index. Treat the current carry as a version-1 compatibility wrapper around that base during migration.

### W2-10-F05 — Bridge verification confirms revision, not semantic readback

**Severity: high. Confidence: high.**

The server verifies upload bytes before queueing and the Bridge completes with `actualRevision === targetRevision`. This is valuable race protection, but the completion contract does not include the re-opened native projection, intended operation IDs, changed native target fingerprints, or preserved-region fingerprints. The server therefore knows that the Bridge file reached a target hash, not that the intended Word range/cell/chart/text object was changed and unrelated semantic regions were preserved.

**Implication:** Bridge write must return a verified native readback envelope: resulting package hash, native application/file revision, semantic projection digest, applied operation IDs, changed region fingerprints, and preservation proof. Hash-only remains a prerequisite, not the complete semantic success condition.

### W2-10-F06 — Owner-scoped replica authority blocks shared Office editing

**Severity: high for collaboration. Confidence: high; inherited W1-17 finding.**

`payloadForWork`, `activateLens`, and related replica/materialization functions require the authenticated actor to own the artifact. Yjs collaboration can share editor state, but a peer who is allowed to edit the artifact is not automatically allowed to open/materialize the native package or queue the local Bridge write. The two-account/shared-Office case therefore cannot be treated as a normal extension of the single-owner path.

**Implication:** separate artifact edit authority, package-base read authority, native write authority, and device/Bridge authority. Resolve the writer through an explicit lease or account/device policy and record it in the operation envelope.

### W2-10-F07 — Merge and undo operate at different granularities than native package writes

**Severity: high. Confidence: high.**

Yjs origins distinguish human, AI, import, source update, undo, and redo, but non-sheet native projection changes can still be applied as a whole semantic snapshot. Sheets has a cell plan; DOCX/PPTX do not have equivalent typed inverse/native transaction records. Office merge helpers operate on reduced projections and region IDs, while preserved package parts and rich subregions remain outside the merge key. A Yjs undo can therefore revert the collaborative projection without an equivalent native inverse, or a three-way merge can declare a region conflict without enough package-level information to produce a safe native result.

**Implication:** one typed operation journal must drive editor/Yjs, AI, native materialization, merge, undo, and Bridge. Every operation needs an inverse or compensating operation, base vector/hash, target identity, and verification result. Snapshot replacement remains a migration/bootstrap operation, not the normal edit protocol.

## Recommended architecture

### Decision

Adopt **Option A: versioned lossless package base plus typed semantic adapter**. Do not rewrite the application around a new schema in this wave; define the contract and migrate one feature family at a time. Keep the current narrow preservation-first lane as a compatibility profile while broad families are implemented and verified.

### Core objects

```text
OfficePackageBase
  packageBaseId, format, packageHash, nativeRevision
  parts + relationships + content types + external refs/macros quarantine
  semanticIndex: stable region/object/span anchors -> part/path/fingerprint

OfficeSemanticProjection
  packageBaseId, projectionVersion, fidelity profile
  regions with stable identities, source bindings, merge keys
  native capabilities: delta kinds, target shapes, verification level

OfficeOperation
  operationId, actor, actorKind, baseVector/basePackageHash
  target { regionId, subrange/object/span identity }
  precondition fingerprint
  typed semantic intent + format-native delta
  inverse/compensating op + expected readback

OfficeOperationResult
  applied/rejected/unsupported/conflicted
  resulting package hash/native revision
  applied operation IDs and native target fingerprints
  readback projection/digest and preserved-part proof
```

The package base is immutable and content-addressed. A native edit creates a new package base after applying a typed operation stream; unknown parts remain attached to the base and are carried forward by package-level copy/relationship logic. The semantic projection is a queryable/indexed view of that base, not a replacement for it.

### Shared interfaces to retain and evolve

- Retain `SpectraLens.open`, `mutate`, `materialize`, `diffExternal`, and `capabilities`, but return `PackageBase` plus semantic index and typed operation results.
- Retain `LensFidelityMap`, evolving it to carry capability/target/verification metadata and explicit `UNEDITABLE`/`PRESERVE_ONLY` semantics without overloading `PRESERVED`.
- Retain `NativeEditorIntent` and command IR, but require operation IDs, target anchors, preconditions, and the native delta family in the intent.
- Retain Yjs adapters, actor origins, and undo manager. Store the canonical semantic operation journal and stable identity map in Yjs; do not store a hollow projection that cannot reconstruct the package base.
- Retain Convex payload storage, replica revisions, materialization queue, and Bridge ownership boundary. Extend queue/complete contracts with package-base ID, operation IDs, target fingerprints, readback projection/digest, and semantic preservation proof.
- Retain package preservation comparison as a lower-level guard. Add target-change and semantic readback checks above it.

### Required contract changes

1. `LensPreservedCarry` version 2 wraps an immutable package base and manifest, not only raw bytes/projection.
2. Each projection region has a native anchor: package part/path, object/run/span identity, base fingerprint, and merge key.
3. Each capability declares native delta kinds, target shape, unsupported reasons, and verification level. The gate rejects unavailable target shapes before mutation.
4. Lens materialization returns a typed result. `operations: []` is valid only with semantic equality/readback evidence; otherwise return `UNSUPPORTED_CHANGE` or `STALE_TARGET`.
5. Native writers return readback projection plus changed-region and preserved-region fingerprints.
6. Merge is three-way over package-base IDs and stable semantic anchors; conflicts are per target/subrange where possible, not only broad artifact regions.
7. Undo/redo records inverse/compensating native operations and the package base they apply to.
8. Replica functions distinguish artifact authority, package read authority, native write authority, and Bridge/device authority; peer editing is not implicitly owner-only.

### Feature-family migration order

1. **Text/rich inline:** DOCX runs/spans, lists, hyperlinks, fields, comments, equations, tables; PPTX paragraphs/runs and text styles.
2. **Structure/layout:** DOCX sections, headers/footers, numbering, table topology; XLSX sheets/dimensions/views; PPTX slide/layout/master/z-order/geometry.
3. **Data and visuals:** XLSX formulas/calc chain, number formats, charts, tables, validation, filters, pivots; PPTX charts/tables/media.
4. **Review and metadata:** comments, tracked changes, notes, alt text, speaker notes, accessibility/reading order.
5. **Embeds and bindings:** typed artifact/source references with static/live/cache policy; native OOXML relationship support where possible and explicit Spectra-extension fallback where not.
6. **Lifecycle:** import/create/export, native GUI verification on Windows/macOS, Bridge readback, merge, undo, recovery, and idempotent replay.

### Cross-artifact embeds

Model a binding as `{sourceArtifactId, sourceVersion, sourceRange/object, targetObjectId, mode: native-link | cached-preview | spectra-link, refreshPolicy}`. If the target format cannot represent the link natively, do not silently drop it: either emit a clearly labeled cached preview/Spectra extension or reject the native mutation. A Sheets range embedded in PPTX must not be considered complete because the projection contains a `sourceBinding` field.

### Failure points to design explicitly

- macros, ActiveX/OLE, external links, dynamic formulas, calculation engines, unsupported fonts/scripts, and package extensions;
- relationship and part renumbering, package signatures, encryption/password protection, and native application repair;
- Office GUI differences on Windows versus macOS and readback timing while files are locked;
- large workbook/deck projection budgets and compaction without semantic loss;
- concurrent native edits during queued writes and idempotent retries;
- unsupported rich target changes, stale anchors, deleted objects, and conflicting source bindings;
- account/device authorization and multiple Bridge mounts;
- exports that are intentionally copies versus writes to the linked original.

## Alternatives considered

### Option B — Expand the current carry and format-specific deltas

Lowest migration cost and preserves the current operational path. It can improve one format at a time, but leaves three divergent semantic systems, has no common rich-range/embed/merge contract, and keeps projection content as a lossy side channel. It is acceptable only as a short compatibility lane, not as the broad-editing architecture.

### Option C — Delegate complex edits to an Office-compatible engine

An optional Windows/macOS native Office or compatible document engine could improve fidelity and GUI verification. It introduces licensing, availability, latency, server/device dependence, deterministic collaboration, and security constraints. Use it as a verification/escape hatch for selected feature families, not as the sole source of truth.

## Next-wave tests and implications

Before claiming broad native editing, add a matrix that executes each offered operation against each relevant artifact fixture and records:

- command/AI operation ID;
- projection target and stable anchor;
- emitted native operation(s), or typed unsupported result;
- package hash/part preservation result;
- native readback projection and changed target fingerprint;
- Yjs operation/origin and inverse/undo result;
- Bridge queue/claim/retry/readback result;
- Windows and macOS native GUI readback where the feature is claimed native.

Minimum targeted probes are the three reproduced no-ops in `office-mismatch-harness.json`, then rich DOCX mixed ranges, lists/table topology, Excel charts/tables/validation/names/sheet lifecycle, PPTX text runs/styles/charts/media/source links, two-account collaboration, native edit during queued write, and undo after Bridge verification.

The launch matrix should distinguish `NATIVE`, `EQUIVALENT`, `SPECTRA_EXTENSION`, `PRESERVE_ONLY`, and `UNSUPPORTED` per feature family and artifact instance. “Broad native editing” should not mean every Office feature; it should mean every claimed family has a typed native operation, stable target, preservation rule, and readback proof.
