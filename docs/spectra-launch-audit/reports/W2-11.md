# W2-11 — Office-compatible editing / rendering engine comparison

**Date:** 2026-09-08  
**Mode:** report-only; no dependency adoption, server install, license purchase, or CI change  
**Scope:** `@ariadng/office` as installed by Spectra, the current Spectra document lenses/adapters, and viable editing/rendering engine families for DOCX/XLSX/PPTX  
**Recommendation:** keep the installed package as the lossless/offline package layer and deepen the existing lens seam; add a separately hosted or native engine only behind an explicit engine-session adapter for rendering, calculation, high-fidelity editing, and collaboration. Do not replace the action/AI/Yjs/bridge architecture with an opaque editor iframe.

## Executive result

The installed `@ariadng/office@0.3.0` is materially more capable than a ZIP-only helper. It has public document/workbook/presentation APIs, typed declarations, a raw OPC/XML escape hatch, formula parsing, and preservation-oriented save behavior. The local probe opened and reopened representative Word, Excel, and PowerPoint fixtures; every untouched save was byte-equal to its input. Small semantic mutations changed only the expected XML parts while unrelated media/chart parts stayed unchanged.

That is a strong foundation for Spectra's current lossless package lane. It is not a full Office editing/rendering engine. The package explicitly leaves layout/rendering, PDF/page calculation, formula evaluation, VBA source editing/execution, and several high-value feature families outside its modeled API. Spectra's current lenses expose an even narrower safe subset. Consequently:

- Extending `@ariadng/office` can improve offline/local edits and preserve unsupported OOXML, but cannot by itself deliver Word/Excel/PowerPoint visual equivalence, formula results, or Office collaboration.
- ONLYOFFICE Docs and Collabora Online are the credible mature self-hosted engine families for browser editing and collaboration, but both introduce a server/session/storage/callback boundary, font inventory and hosting cost, and a second authority that must be reconciled with Spectra actions, AI actions, Yjs, and the bridge.
- Microsoft Office web/desktop remains the highest-fidelity reference for Office behavior, but Office web is online and feature-limited, while desktop automation requires the installed licensed applications and platform-specific integration. It is a handoff/reference lane, not a drop-in browser engine.
- “Full Office equivalence” is not a single package target. Macros, OLE/ActiveX, embedded workbooks, SmartArt, themes/masters, advanced charts, equations, fields, tracked changes, and layout depend on either preservation, a specialized model, or the actual Office/LibreOffice-derived engine.

The recommended architecture is a three-lane model:

```text
Spectra actions / AI actions / Yjs / bridge authority
                 |
       format-neutral EngineAdapter
          /          |             \
 package lens     server engine     native Office handoff
 @ariadng/office  ONLYOFFICE or      Windows/macOS Office
 offline/local    Collabora          fidelity/reference lane
```

Each lane must report capabilities and fidelity explicitly. The package lens remains the deterministic preservation path; a server/native engine is an optional session with explicit open, mutate, save, callback, conflict, and readback semantics.

### Stable findings

- **W2-11-F01 — Strong preservation base, incomplete editor:** `@ariadng/office@0.3.0` is a credible lossless OOXML/package layer, but it is not a layout renderer, formula calculator, macro runtime, or complete Word/Excel/PowerPoint object model.
- **W2-11-F02 — Adapter omissions are real:** the installed package exposes more semantic operations than the current Spectra lenses surface, especially Word lists/tables/headers, Excel tables/defined names/dimensions, and PowerPoint slide/layout lifecycle. These are safe opportunities for incremental adapter work.
- **W2-11-F03 — Dependency limits remain material:** equations, charts, embedded objects, themes/masters, revisions/comments, advanced spreadsheet semantics, font metrics, pagination, and formula results need additional modeling or an external engine; raw XML preservation does not supply those semantics.
- **W2-11-F04 — Mature engines are service or native sessions:** ONLYOFFICE, Collabora, and Microsoft Office introduce a server/WOPI/callback/native-process boundary, with hosting, licensing, fonts, platform, and conflict-authority consequences.
- **W2-11-F05 — Protocol preservation is mandatory:** any engine must sit behind a format-neutral session adapter that preserves action/AI/Yjs provenance, bridge authority, capability/fidelity reporting, idempotency, save/readback, and conflict handling.
- **W2-11-F06 — Full Office equivalence is not a single acceptance claim:** macros/OLE/ActiveX, formula calculation, visual layout, fonts, collaboration, and native application behavior require separate tests and explicit product promises. Notion remains a deferred provider connector, not an Office engine.

## 1. Current package and architecture

### 1.1 Installed dependency

The worktree declares `@ariadng/office: ^0.3.0`; the lockfile resolves exactly `0.3.0` from npm, with MIT license and Node `>=20`. The installed package is ESM, has zero runtime dependencies, and exports root and focused subpaths for ZIP/XML/OPC/preservation/schema/document/DOCX/XLSX/PPTX work.

The package README describes these important boundaries:

- modern OOXML package open/edit/save for DOCX/DOCM/DOTX/DOTM, XLSX/XLSM/XLTX/XLTM/XLAM, and PPTX/PPTM/POTX/POTM/PPSX/PPSM/PPAM;
- untouched-part preservation and a fidelity ladder from semantic equivalence through Office-clean files to byte-stable untouched parts;
- a live XML/DOM lens with a raw DOM escape hatch;
- no legacy binary DOC/XLS/PPT, XLSB, layout/rendering/PDF/page-counting engine, formula evaluation, or VBA source editing;
- opaque macro-part preservation rather than macro execution or source-level editing.

The package's claims are consistent with the local API and fixture probe below, but the README's mention of a real Office COM conformance harness was not independently run in this audit. The probe therefore treats package-level round-trip evidence as package evidence, not as proof of native Office visual equivalence.

### 1.2 Public API observed

| Area | Installed public surface | Practical implication |
|---|---|---|
| Common package | `OfficeDocument`, `OpcPackage`, relationships, parts, XML elements, package comparison | Good preservation/inspection seam; unknown parts can remain opaque or be edited through raw XML, with dirty-state responsibility on the caller. |
| Word | `Document.open/create`, paragraphs/runs, text/bold/italic, effective formatting, lists, tables/rows/cells, inline PNG/JPEG, headers/footers, save | Useful semantic subset for ordinary body content; not a page-layout or complete Word object model. |
| Excel | `Workbook.open/create`, sheets, typed cell access, cached formula values, styles, row/column dimensions, formulas, merges, tables, defined names, streaming rows, A1/R1C1 parsing | Useful workbook model; no calculation engine and several advanced feature families remain preservation-only. |
| PowerPoint | `Presentation.open/create`, slides, title/text access, layouts, add/remove slide, raw DOM, save | Useful slide/title lane; not a complete shape/theme/media/chart/animation editor or renderer. |
| Preservation | per-part compare and XML comparison utilities | Enables package-level readback checks and meaningful “changed only these parts” assertions. |

### 1.3 Current Spectra seam

Spectra already has the right architectural insertion point. `SpectraLens` exposes open, mutate, external diff, materialization, capabilities, and fidelity; the fidelity vocabulary distinguishes `NATIVE`, `EQUIVALENT`, `PRESERVED`, and `EXTENSION`. The source-update/Yjs seam can keep the canonical content and action history separate from a native file adapter. The bridge remains a signed transport/sync boundary, and the provider-neutral source contracts avoid coupling the work model to a particular file format.

The implication is important: an engine should implement an adapter at the lens/engine boundary, not become the new owner of Spectra's action, AI, undo, provenance, or bridge protocol. The engine can be a projection target, a calculation/rendering service, or a temporary native-edit session. It should not silently turn the file bytes into an untracked second source of truth.

## 3. Why package extension alone cannot be the full answer

OOXML is an OPC package made of interrelated parts, not one self-contained document string. Microsoft describes Word files as many parts such as document content, properties, styles, theme, settings, and fonts, with relationships connecting those parts; PresentationML similarly composes presentations, masters, layouts, slides, and relationships. See [Microsoft's Word Open XML package overview](https://learn.microsoft.com/en-us/office/dev/add-ins/word/create-better-add-ins-for-word-with-office-open-xml), [PresentationML structure](https://learn.microsoft.com/en-us/office/open-xml/presentation/working-with-presentations), and the [OPC package model](https://learn.microsoft.com/ja-jp/previous-versions/windows/desktop/opc/packages-overview).

The package can preserve and selectively mutate those parts, but preservation is not the same as semantics:

- A preserved OMML equation is not an equation editor or a layout engine.
- A preserved chart and embedded workbook are not chart data/series/axis semantics.
- A preserved theme/master is not a resolved visual style model.
- A preserved tracked-change or comment part is not a collaboration/review model.
- A preserved VBA project or OLE object is not executable or editable.
- A formula string and cached value are not a recalculation engine.
- A font name in XML is not proof that the same font metrics, fallback, hinting, and pagination are available on a browser, Windows, macOS, or a server.

The package's zero-dependency, browser-capable design is valuable for deterministic local work, but the same design intentionally excludes the native layout/calculation/application runtimes needed to make those claims.

## 4. Candidate engine families

### 4.1 Extend `@ariadng/office` plus existing Spectra adapters

**Fit:** recommended foundation and offline lane.

**Advantages:** MIT, already installed, no runtime service, works with the existing lens/Yjs/bridge seams, can operate locally or in a browser-capable runtime, preserves unknown parts, and allows incremental capability mapping. It is the only option here that naturally retains Spectra's current deterministic package workflow and does not introduce a new remote authority.

**Limits:** substantial implementation remains for rich Word ranges, OMML authoring, comments/revisions, page sections, drawing anchoring, Excel formula evaluation, charts/validation/conditional formatting/pivots, PowerPoint shape/theme/master/chart/table/animation semantics, and all visual/layout verification. A raw DOM escape hatch must not be promoted to a user-facing semantic operation without a fidelity and readback contract.

**Use it for:** safe structured edits, source preservation, package inspection, import/export, action replay, offline mode, and as the fallback when a richer engine is unavailable.

**Do not claim:** native Office rendering, full formula parity, macro execution, full embedded-object editing, or collaboration solely from this layer.

### 4.2 ONLYOFFICE Docs

ONLYOFFICE is a mature browser-based document/spreadsheet/presentation editor that can be self-hosted. Its official Docker distribution describes online editing and real-time collaboration for OOXML document formats and expects a separately running Document Server with persistent service resources; the published requirements include 4 GB RAM, swap, disk, and mounted data/log/cache/database/message-broker volumes. See the [official Docker Document Server repository](https://github.com/ONLYOFFICE/Docker-DocumentServer).

The integration shape is not a library call. The editor calls the integrator's callback endpoint with save/action/history events; the integrator owns document storage when not using Workspace. See [ONLYOFFICE callback handling](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler/). Requests are protected with JWTs in the documented security model; see [ONLYOFFICE security](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/security/). The official integration surface also supports WOPI as an alternative integration route.

**Advantages:** mature browser editing/rendering/coauthoring experience, a broad user-facing Office model, server-side font/layout/runtime control, and a path to Word/Excel/PowerPoint sessions without implementing every OOXML semantic ourselves.

**Costs and risks:** a Linux/Docker service or equivalent deployment, CPU/RAM/storage/upgrade/observability cost, callback and storage reconciliation, JWT/WOPI integration, server font inventory, and a second live document authority. The Community edition is GNU AGPLv3 with a recommended user limit in the official integration documentation; Enterprise is proprietary. Confirm current licensing and deployment terms with legal before adoption; no license was purchased in this audit.

**Spectra integration requirement:** the editor session must be an explicit engine projection. Spectra needs an engine session ID, document version/hash, actor, capability manifest, open/save/readback state, callback event IDs, conflict policy, and fidelity result. AI or user operations sent into the engine need stable action IDs and provenance. Callback saves need to re-enter the bridge/Yjs source-update path, not silently overwrite canonical content.

**Assessment:** strongest candidate for an optional hosted collaboration/rendering lane; not a replacement for the package lens or the Spectra protocol.

### 4.3 Collabora Online

Collabora Online is a browser collaboration layer built around the LibreOffice ecosystem and integrates into host products through browser/WOPI-style boundaries. Its public project is primarily MPLv2 and is intended for browser collaboration without a plugin; see the [Collabora Online source repository](https://github.com/CollaboraOnline/online) and [integration overview](https://www.collaboraonline.com/integrations/collabora-online-and-sharepoint/).

CODE is the free development edition, suitable for testing/home/small teams but explicitly not recommended for production; its FAQ distinguishes the supported paid Collabora Online subscription with SLA, maintenance, and security updates. See [CODE](https://www.collaboraonline.com/code/) and the [Collabora FAQ](https://www.collaboraonline.com/faqs/). The production deployment model still requires a server, font inventory, lifecycle management, and a document/storage integration boundary.

**Advantages:** broad LibreOffice-derived editing/rendering behavior, on-premise/self-hosted options, open-source components, browser collaboration, and a plausible WOPI integration lane.

**Costs and risks:** server/runtime/upgrade cost, licensing/support choices, LibreOffice-versus-Microsoft-Office compatibility differences, font and pagination drift, and the same second-authority/callback/conflict problem as any hosted editor. CODE is not a production-SLA answer.

**Assessment:** credible alternative to ONLYOFFICE where LibreOffice compatibility, on-premise operation, or licensing posture is preferred. It still cannot be treated as an in-process JS package or as a free browser-only offline engine.

### 4.4 Microsoft Office web and native Office

Microsoft's own web feature matrix is useful as a reality check: Office for the web requires a browser and internet connection, has documented limits versus desktop Office, and does not provide offline authoring. The matrix calls out gaps in advanced layout, themes/document parts, SmartArt, citations/bibliography and other features; VBA/scripts do not run in the web environment. See the [Office for the web service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/office-online-service-description/office-online-service-description).

PowerPoint web has additional explicit limitations: ActiveX and embedded OLE objects cannot be inserted/edited, and shapes, charts, and equations have restricted editing behavior; macros do not run. See [How features behave in web-based PowerPoint](https://support.microsoft.com/en-us/powerpoint/how-certain-features-behave-in-web-based-powerpoint). This is direct evidence that “use Office web” is not the same as full Office equivalence.

For an integrated web session, Microsoft's WOPI model requires a host implementing file operations such as CheckFileInfo, GetFile, PutFile, locks, and unlock/refresh flows; see the [WOPI REST endpoints](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/rest/endpoints) and [WOPI protocol file operations](https://learn.microsoft.com/en-us/openspecs/office_protocols/ms-wopi/f52e753e-fa08-4ba4-a68b-2f8801992cf0).

Native Word/Excel/PowerPoint on Windows or macOS remains the strongest reference for application fidelity, but it is a platform-specific installed-app bridge with licensing, process lifetime, file locking, user profile, font, and automation concerns. It is appropriate for an explicit “open in Office / verify in Office” lane, not as a browser renderer or as the authority for every Spectra action. No native Office instance was launched in this wave.

**Assessment:** highest reference fidelity, highest integration/platform cost. Use as an optional native handoff and validation target unless product requirements explicitly fund a desktop bridge.

### 4.5 Low-level Open XML SDK and conversion libraries

Microsoft's Open XML SDK is a useful comparison point: the official repository describes a MIT-licensed .NET SDK for generating/modifying Word, Excel, and PowerPoint documents with strongly typed low-level parts and markup. It is not a browser editor, layout renderer, collaboration server, or formula calculation engine. See the [Open XML SDK repository](https://github.com/dotnet/Open-XML-SDK).

It validates the package-layer direction but does not change the decision. A commercial conversion/rendering library could fill some server-side gaps, but would require a separate legal, platform, feature, performance, and fixture-based evaluation. It should not be adopted as an unnamed “full Office” dependency.

## 5. Cross-cutting capability risks

### Fonts and visual fidelity

No candidate can promise identical pagination from file format support alone. Font files, versions, fallback, shaping, East Asian font names, equation fonts, printer metrics, and platform text stacks affect layout. `@ariadng/office` can preserve font declarations and resolve limited style metadata, but does not render or package a controlled font environment. Server engines need an explicitly managed font image; native Office needs the target OS/application font environment. Spectra should surface a font/runtime fingerprint in any visual-fidelity result and treat “same XML” and “same screenshot/PDF” as separate assertions.

### Equations

OMML preservation is safe evidence of lossless storage, not equation editing or rendering. The current DOCX lens marks equation content as preserved/read-only, matching the package's preserve-only support for richer Word structures. A future engine adapter must declare whether it can parse, author, recalculate/layout, and round-trip equations; a raw OMML write should not be presented as equivalent to Word's equation UI.

### Charts and embedded workbooks

The XLSX/PPTX probes deliberately included chart/media-rich preservation fixtures. Unrelated chart/media parts remained unchanged after the targeted edits, which is good preservation evidence. It is not chart editing evidence. A chart-capable engine must define chart data source ownership, embedded workbook updates, cached image refresh, relationship updates, and readback. The current Spectra lenses preserve these families rather than exposing them as broad native operations.

### Macros, OLE, ActiveX, and embedded objects

Macro-enabled files can be preserved as opaque package parts, but execution and source editing are different capabilities. Microsoft also documents macro blocking/security behavior, and Office web has explicit macro/OLE limitations. See [Microsoft's macro security guidance](https://learn.microsoft.com/en-us/microsoft-365-apps/security/internet-macros-blocked) and the [Office web feature matrix](https://learn.microsoft.com/en-us/office365/servicedescriptions/office-online-service-description/office-online-service-description).

The product contract must distinguish:

1. untouched macro/embedded bytes preserved;
2. surrounding document edited without destroying those bytes;
3. embedded object data edited;
4. VBA/ActiveX source edited;
5. macro/object executed.

The package currently supports the first two only where the fixture and operation preserve the opaque parts; none of the package probe is evidence for the last three.

### Collaboration and conflict authority

Yjs gives Spectra a canonical collaborative model for supported content. A hosted Office engine has its own session, locks, revisions, callbacks, and conflict rules. The bridge has its own signed transport/session authority. These must be composed, not conflated. An engine adapter needs an explicit rule for whether the engine is:

- a projection fed by Spectra operations;
- a temporary interactive authority whose save is imported as a source update; or
- the source of truth for an artifact family during an engine session.

The default recommendation is projection plus explicit save/import. Silent bidirectional merging of arbitrary engine XML into Yjs is unsafe.

## 6. Adapter and protocol design recommendation

Add a format-neutral `EngineAdapter`/`EngineSession` capability at the same conceptual seam as `SpectraLens`, without changing the existing action/AI/Yjs/bridge contracts. The exact interface can be designed in a later implementation wave, but it should include:

```text
open(source, requestedCapabilities) -> session
capabilities(session) -> fidelity + feature matrix + runtime/font fingerprint
applySpectraAction(session, actionId, actor, operation) -> acknowledged result
applyExternalChange(session, version/event) -> source update or conflict
save(session) -> package/artifact + engine version + changed parts/history
close/cancel(session)
```

For a WOPI or callback-backed engine, the session additionally carries CheckFileInfo/GetFile/PutFile/lock state, callback URL/authentication, document version, idempotency keys, and conflict handling. For a native Office bridge it carries process/application identity, platform, installed version, file-lock state, and safe-copy/reopen rules. For `@ariadng/office`, the session is in-process and can use package compare/reopen checks.

Required invariants:

- Every user/AI operation retains actor, action ID, origin, undo/cancel behavior, and bridge authorization.
- Every engine result declares `NATIVE`, `EQUIVALENT`, `PRESERVED`, or unsupported status per feature family.
- Engine saves are never accepted as canonical merely because they returned HTTP 200 or produced a valid OOXML ZIP; Spectra must compare/reopen and record a source update.
- Unsupported content is preserved and visibly marked; a lossy conversion must be explicit.
- Engine callbacks and retries are idempotent and version-checked.
- The browser/editor lane and native package lane can be compared through the same artifact/fidelity reporting, even though they do not share all semantics.

## 7. Notion boundary (deferred)

Notion is not an Office engine and should remain a future connector/adapter concern, not a W2-11 dependency decision. The existing `import-notion.ts` is a local markdown/HTML import helper, not a Notion API integration. The generic source contracts and context-source registry are the correct seam for a future provider.

The official Notion API reinforces why it should be separate: connection capabilities distinguish read/update/insert/comment; page content is a paginated block tree; unsupported blocks can be returned as `unsupported`; large content requires recursive fetches and rate-limit handling; and webhooks are change signals whose payloads do not include full content, so the connector must fetch the current blocks. See [Notion capabilities](https://developers.notion.com/reference/capabilities), [working with page content](https://developers.notion.com/guides/data-apis/working-with-page-content), [block children pagination](https://developers.notion.com/reference/get-block-children), and [webhook delivery](https://developers.notion.com/reference/webhooks-events-delivery).

The future Notion adapter should map page/block semantics to a provider-neutral source record, expose permissions/freshness/cursor/capability state, and never be presented as a DOCX/PPTX/XLSX fidelity engine.

## 9. Recommended next actions

No source code or dependency changes are proposed in W2-11. The next implementation/evaluation wave should:

1. Keep `@ariadng/office` as the default preservation/offline adapter and add only capability-gated operations with package compare/reopen tests.
2. Build an isolated engine-session proof of concept for one hosted engine (ONLYOFFICE or Collabora) using disposable files and a minimal WOPI/callback/storage boundary. Do not wire it into production authority until action IDs, actor/provenance, conflict, save/readback, and font/runtime reporting are defined.
3. Add a fixture matrix for OMML inline/display equations, East Asian/custom fonts, comments/revisions, headers/sections, chart-linked workbooks, conditional formatting/validation, pivot tables, themes/masters, animations, OLE/ActiveX, macros, and embedded objects.
4. Run native Windows Office and macOS Office/LibreOffice open/edit/save tests on safe fixture copies, including screenshot/PDF and package comparisons. This is required before claiming visual or cross-platform parity; it was not run in this wave.
5. Add formula recalculation tests against the selected calculation engine, including cached values, volatile functions, date systems, external links, errors, and shared/array/dynamic formulas.
6. Add a protocol integration test that sends a human action and an AI action through Yjs/bridge into each adapter, reopens the resulting artifact, checks package diffs, and verifies undo/cancel/provenance.
7. Keep Notion deferred to the provider-neutral connector wave; test OAuth/capabilities, block pagination, unsupported blocks, webhook-triggered refetch, and source freshness there.
