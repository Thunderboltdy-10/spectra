# W2-15 — ManageBac student sync and useful tasks

## Result

The required live student journey did not reach ManageBac. The shared local Convex deployment at `127.0.0.1:3002` refused connections throughout the isolated run, so identity resolution, provider reads, manual sync, class materialization, and durable planner/Calendar readback are unverified. The app and bridge shells remained reachable and reported the dependency failure honestly.

Source tracing confirms a coherent intended path: a school administrator supplies a server-side read-only token and verified route manifest; an ordinary member can view personal school data, manually refresh it, choose class shelves, and use local planner/Calendar work without ManageBac writes. The source also has consequential gaps: current-period semantics are not present in the built-in class manifest, source updates can create a false Calendar conflict, personal overlays are not connected to ordinary planner editing, and the integration-wide freshness/scheduler state is mixed with student-scoped runs.

One bounded fix is committed in this worktree: the shared ManageBac page no longer labels ordinary users as “Admin setup.” It now uses role-aware personal-data copy. This is not in the running primary build.

## Findings grouped by root cause

### Provider contract and temporal identity

#### W2-15-F01 — Built-in personal class sync cannot establish current academic period (important; confidence: high)

**Consequence:** A student can be offered an old or duplicate class when the provider returns multiple non-archived academic periods, and tasks/resources can be associated with the wrong period. The code cannot safely distinguish “current” from “historical” using the built-in manifest.

**Code chain:** `officialPersonalCapabilities()` in `src/app/api/spectra/managebac/route.ts:108-385` defines class memberships, class details, tasks, timetable, resources, and CAS routes. None of the class/task/resource capability normalizations specifies `academicPeriodPath`; the timetable transform carries `academic_year_id` into its raw row, but the capability still does not map it into the normalized record. `normalizeProviderPage()` only stores `academicPeriodKey` when the capability configuration supplies that path (`route.ts:705-860`). `listMyClassCandidates()` then deduplicates eligible classes by `providerClassId` and filters only `normalized.archived` (`convex/managebac.ts:3331-3460`). Its workspace key falls back to `current` when no period exists.

**Remedy:** Require a tenant-verified current-period contract: an explicit active academic-year/term field or a school-configured period rule with provider evidence. Store and display the period in candidate rows; dedupe by provider class + period; filter assignments/resources/timetable to the selected period. Test current, historical, archived, same-ID, missing-period, and provider-date combinations. Never infer currentness from title, fetch time, or the absence of an `archived` flag.

### Projection refresh and local work preservation

#### W2-15-F02 — Calendar projection refresh uses the old timetable-artifact identity (important; confidence: high)

**Consequence:** A changed ManageBac assignment/deadline can produce a false `customization_overlap` conflict even without a user edit. The planner artifact may refresh while the official/movable Calendar source is handled through a different path, leaving inconsistent status or a conflict that the student cannot explain.

**Code chain:** `ensureTimetableProjection()` (`convex/managebac.ts:1953-2038`) calls `upsertSourceCalendarItem()` and stores a `timetable_event` projection whose `projectionId` is the `calendarItems` ID. On an existing external record, `commitNormalizedPage()` (`managebac.ts:2307-2495`) calls `safelyRefreshProjection()` for every projection. Its timetable branch (`managebac.ts:2096-2210`) splits `projection.projectionId` on `#`, normalizes the first segment as a `spectraArtifacts` ID, and requires a legacy `timetable` artifact. A new Calendar item ID therefore returns `false`, causing a conflict and setting projections conflicted. Later `projectRecord()` calls `ensureTimetableProjection()` again and may update the Calendar item, but it does not remove the already-open conflict or clear the planner projection’s conflicted state.

**Remedy:** Branch refresh by representation. For `timetable_event` projections backed by `calendarItems`, refresh the source-owned Calendar item directly and preserve the movable task’s local scheduling fields. Keep an explicit legacy-artifact fallback for old records. Make refresh and projection state updates idempotent; do not create a conflict for a source-only Calendar refresh, and add a migration/readback test for both legacy and new projection IDs.

#### W2-15-F03 — Planner overlays are modeled but not connected to ordinary editing (important; confidence: high)

**Consequence:** A student’s edited title/description/due date can be replaced by the next provider refresh without an overlay or explanation. Notes, reminders, alternative planned times, tags, and links have server support but no discovered ManageBac UI caller, so the page’s “personal overlays remain separate” guarantee is not an end-to-end behavior.

**Code chain:** `ensurePlannerProjection()` creates `source.lockedFields` for `taskTitle`, `description`, `dueAt`, and `source`, plus an empty `personalOverlay` (`managebac.ts:1845-1951`). `setOverlay()` supports notes, completion, reminders, alternative times, tags, placement, and linked artifacts (`managebac.ts:2952-3015`), but `rg` found no UI caller. `commitNormalizedPage()` detects only an `externalRecordOverlays` row (`managebac.ts:2416-2468`). When none exists, `safelyRefreshProjection()` overwrites planner source fields. Planner status survives because the refresh spreads existing content, but `calendarShared.ts:229-268` patches the separate source task with `status: "active"`, so a completed planner task and its Calendar task can diverge after a source update.

**Remedy:** Define source-owned versus personal overlay fields once and route human/AI edits through that contract. Preserve completion intentionally across both planner and movable Calendar representations, or show a visible reactivation decision. Add UI for notes, planned times, reminders, completion, detach/rebase, and provenance. Test edit → resync → reload, including completed tasks, moved work blocks, and source removal.

### Scope, freshness, and recovery

#### W2-15-F04 — Account/integration scope is incomplete on ordinary reads (important; confidence: high)

**Consequence:** If another integration or stale unscoped row exists for the same account/school, the ManageBac page or AI school-data path can read records, runs, or class memberships that were not produced by the current ManageBac integration. A related provider class ID can incorrectly make a class appear selectable.

**Code chain:** `myOverview()` queries `externalSyncRuns` by account and `externalRecords` by mapped account without filtering `integrationId` (`convex/managebac.ts:1053-1130`). `recordsForPurpose()` similarly reads personal rows and membership rows by account/type, while scoped rows are integration-filtered (`managebac.ts:3123-3330`). `listMyClassCandidates()` reads all school records and account memberships without an integration/tombstone filter on the membership derivation (`managebac.ts:3331-3460`), and `materializeClassWorkspaces()` repeats the account-only membership scan (`managebac.ts:3487-3550`). Existing `externalProjections` use account-wide indexes and are filtered by integration only in some callers.

**Remedy:** Apply `(integrationId, schoolId, accountId)` to every ManageBac personal query and membership derivation; exclude tombstones before building accessible class IDs; verify source, projection, and relation integration IDs together. Add two-account/two-integration overlap tests and a migration/readback plan for unscoped rows. This belongs with W2-16’s isolation work, not a local UI patch.

#### W2-15-F05 — Integration-wide freshness and scheduler state cannot represent student retry semantics (important; confidence: high)

**Consequence:** A student’s personal manual sync can update the integration-wide `lastSyncAt` and `nextSyncAt`, making the school page/admin view look freshly synchronized even though school-wide routes were not refreshed. A failed personal run schedules an integration-level retry, but `claimScheduledSync()` intentionally accepts only verified non-personal routes, so the scheduler cannot replay that student’s personal data. Newly configured integrations can remain unscheduled until a manual or AI-triggered path sets `nextSyncAt`.

**Code chain:** `configure()` creates/updates the integration without setting `nextSyncAt` (`convex/managebac.ts:478-650`). `completeSync()` updates integration `lastSyncAt` and schedules the next run for every run kind (`managebac.ts:2754-2948`). `failSync()` also sets integration `nextSyncAt` and schedules retry, except credential rejection (`managebac.ts:2630-2753`). `claimScheduledSync()` filters to non-personal verified capabilities and degrades when none exist (`managebac.ts:1145-1300`). `convex/crons.ts` contains no ManageBac interval calling `scheduleExisting`; the internal helper is only useful once some path has scheduled a run.

**Remedy:** Separate school-wide freshness from account-scoped personal freshness and expose both. Define whether scheduled sync is catalog-only and make the student’s refresh manual/queued with an account-bound retry state, or add a safe per-account scheduler without enumerating unrelated students. Set initial scheduling explicitly after validation, show next-attempt/error state, and test manual success, 401, 429, schema quarantine, lease expiry, restart, and no non-personal capability.

#### W2-15-F06 — Sync status stores actionable errors but the student/admin UI hides them (important; confidence: high)

**Consequence:** After a loaded run fails, the user sees a status pill but not whether the cause was rejected credentials, a rate limit, schema drift, a tombstoned source, skipped scope, or a retry time. The UI cannot support a reliable “sync progress/errors” workflow or tell the student whether cached data is safe to use.

**Code chain:** `externalSyncRuns` stores `stage`, counts, `errorCode`, and `errorSummary`; `failSync()` and `commitQuarantine()` populate them. `SyncTable` (`managebac-integration-shell.tsx:1110-1160`) displays only date/time, status, created, updated, conflicts, and kind. The right-rail activity view (`managebac-integration-shell.tsx:1040-1070`) shows added/updated and relative time only. The School `SyncStatus` view shows capability last success and a short run count, but not per-run error details. Quarantine has a provenance view and retry button, but it is only one error family.

**Remedy:** Keep raw provider details server-side, but expose sanitized `stage`, `errorSummary`, retry eligibility/next attempt, fetched/unchanged/tombstoned/skipped/quarantined/projected/error counts, and current capability. Make failed/partial/awaiting-review rows link to the exact recovery action. Test 401, 403, 429, timeout, redirect rejection, oversized response, invalid schema, partial completion, and reconnect.

### User-facing discovery and projection completeness

#### W2-15-F07 — Ordinary ManageBac controls are not discoverable from the sidebar (small/important discovery; confidence: high)

**Consequence:** A student can use `/school` for classes, tasks, Calendar, resources, and sync status, but cannot discover the dedicated ManageBac page from the sidebar or School overflow. The dedicated link is only shown to admins, while the direct page contains useful peer views and class shelf controls.

**Evidence/code chain:** The live `/school` snapshot showed the peer sections and `More School sections` (`Discussions & news`, `Feedback & results`, `CAS`, `Sync status`) but no ManageBac link. `school-data-shell.tsx:419-424` conditionally renders the ManageBac link only for `payload.admin`; `managebac/page.tsx` itself has no server-side admin gate, and `managebac-integration-shell.tsx` gates settings/actions by `overview.admin`.

**Remedy:** Add a clear ordinary-member route affordance from School—either a ManageBac item in the overflow or a “Manage school data”/“View source and sync history” link—without exposing admin connection settings. Keep the peer role model; the link should land in the ordinary read/sync view and explain when identity or admin configuration is required.

#### W2-15-F08 — Resource projections do not create useful local work (future/important; confidence: high)

**Consequence:** A synced ManageBac resource/file appears as a normalized source row and provenance URL, but it is not downloaded, attached, or materialized as a Spectra artifact. A student cannot reliably use the source resource in a local document/task offline or link it into study work from the source list.

**Code chain:** `ensureResourceProjection()` stores an `externalProjections` row with `projectionType: "resource"` and a synthetic `managebac:${source._id}` projection ID (`convex/managebac.ts:2018-2068`). It does not create a tree node, artifact, asset, or download operation. `RecordsList` exposes only the optional `provenanceUrl` external link (`managebac-integration-shell.tsx:294-349`).

**Remedy:** Define a read-only resource materialization contract: provider capability must expose a safe URL/asset route, server fetch must remain bounded and read-only, stored assets need account/school authorization and provenance, and the UI must distinguish linked source from downloaded copy. This crosses upload/storage ownership and should be a parent package, not an incidental sync fix.

#### W2-15-F09 — Source-removed conflicts have no matching ordinary UI action (important; confidence: high)

**Consequence:** `completeSync()` creates `source_removed` conflicts with suggested `detach`/`archive_projection`, but the visible conflict list only offers `Keep mine` and `Rebase`. A deleted class/task or removed source event can remain blocked with no safe action available to the user.

**Code chain:** Source removal is tombstoned in `completeSync()` and projected through `markProjectionSourceRemoved()` (`managebac.ts:2754-2948,2212-2240`). The backend accepts `rebase`, `keep_overlay`, `detach`, `archive_projection`, and `link_existing` (`managebac.ts:3017-3120`), while `ConflictList`’s callback/buttons (`managebac-integration-shell.tsx:1165-1220`) expose only the first two relevant ordinary actions.

**Remedy:** Render only capability-safe actions for each conflict kind, including detach/archive for source removal, and show exactly what remains locally. Verify that source tombstones hide the class candidate, preserve personal work according to policy, and settle the conflict/readback state.

## Decisions for parent/Pablo

- Do not call ManageBac launch-ready from the current run: the real dependency was unavailable, and no provider read or durable materialization was proven.
- Integrate the source changes from W2-16 only with the account/integration scope and unscoped-row migration/readback plan. The current page has strong authorization intentions, but several queries still use account/school indexes without integration filtering.
- Make current academic period a hard contract. The provider’s public API supports administrator-managed read-only permissions and documented versioned routes, but the tenant reference must identify how “current” is represented. A title/fetch-time heuristic is not acceptable.
- Fix the new Calendar projection refresh seam before relying on source updates. The safer design is representation-aware refresh for `calendarItems`, preserving separate local scheduled-work fields, with a legacy fallback and explicit regression tests.
- Separate student-scoped freshness/retry from integration-wide scheduler state. A school-level “last sync” should not be advanced by a personal-only run unless the UI labels the scope precisely.
- Expose actionable but sanitized sync errors and source-removal actions. The current backend records enough metadata to support this without exposing provider tokens or raw payloads.
- Add ordinary-user discovery for the dedicated page, but keep connection/manifest/period-map/disconnect authorities admin-only. The small header fix is safe and committed; the broader route affordance should be coordinated with navigation ownership.
