## Findings grouped by root cause

### W2-16-F01 — Personal and reconciliation reads were not consistently integration-scoped

- **Status:** fixed in `9e5d2fd9`; not integrated into the primary runtime.
- **Severity:** important; **confidence:** high from source and passing tests.
- **Consequence:** account-indexed `myOverview` sync runs, conflicts and records could include another ManageBac integration/school belonging to the same account. `completeSync` could reconcile personal records from another integration and let a personal run’s conflict count be affected by another integration’s open conflicts. Broad school reads could also select another integration before filtering.
- **Fix:** filter `myOverview` sync runs/conflicts/records by current integration and school; filter admin identity queues/previews by the selected integration; use integration-first queries for personal/membership/class reads; filter personal reconciliation and projection side effects by integration, school and run account.
- **Neighboring impact:** no role policy changed; teachers and students remain peers, and school administrators remain the only authority for school-wide actions.

### W2-16-F02 — Tombstoned memberships could retain class access

- **Status:** fixed in `9e5d2fd9`.
- **Severity:** important; **confidence:** high from source and the passing membership test.
- **Consequence:** removed provider membership rows could continue to populate `accessibleClassIds`, exposing old class-member resources and offering a removed class for materialization.
- **Fix:** current integration/school membership derivation excludes `tombstone` in `recordsForPurpose`, `listMyClassCandidates` and `materializeClassWorkspaces`. Selected class sources still require current school/integration ownership and non-tombstone state.
- **Limit:** this does not decide whether an already-created personal shelf should be retained, dissolved or marked unavailable after provider removal. That is a product/data-lifecycle decision.

### W2-16-F03 — Conflict scope allowed peer resolution and unsafe link targets

- **Status:** fixed in `9e5d2fd9`.
- **Severity:** important / launch-relevant for conflict review; **confidence:** high from source and passing authority tests.
- **Consequence:** an accountless conflict, which denotes school/integration scope, could previously be resolved by any active school member. Resolution iterated every projection for the source record, and `link_existing` did not sufficiently bind the target to the same integration/account scope.
- **Fix:** accountless conflicts now require `school_admin`; account conflicts still require the conflict account or a school administrator; affected projections are filtered to the conflict’s integration/school/account; `link_existing` requires an active target of the same projection type and same integration/school, and account-scoped conflicts additionally require the same account.
- **Limit:** the UI/live admin review path was unavailable because Convex was down. The Convex mutation path is covered.

### W2-16-F04 — Personal provider keys remain globally shaped before the held migration

- **Status:** not fixed; precise migration proposal below.
- **Severity:** launch blocker for real two-account ingestion when provider IDs overlap; **confidence:** high from source.
- **Consequence:** `commitNormalizedPage` upserts `externalRecords` by `(integrationId, providerRecordKey)`. The current route’s personal `recordKeyTemplate` is provider-defined and does not add account identity. Two students whose ManageBac task/resource/class IDs overlap can overwrite the same source row, change its mapped account, and reuse the wrong source/projection identity. The isolated two-account test intentionally uses scoped keys to prove the safe downstream projection behavior; it does not hide this production gap.
- **Held evidence:** `3c905bcc` adds `account:<accountId>:` to mapped-user keys and scopes projection keys, but it also changes the durable identity model without migration/reconciliation. It must not be cherry-picked wholesale.
- **Remedy:** add a versioned canonical source identity and a staged backfill/reconciliation before enabling account-scoped keys in production (see below).

### W2-16-F05 — Duplicate pages are row-deduplicated but not receipt-idempotent

- **Status:** not fixed; report-only because it needs a schema/worker contract.
- **Severity:** important operational correctness/cost issue; **confidence:** high from the passing characterization test.
- **Consequence:** a fresh-nonce retry does not duplicate the source row or resource projection when the provider key/hash is unchanged, but it increments fetched/page counters and repeats downstream checks. Timetable/calendar refreshes can also bump revisions on a duplicate delivery. `completeSync` has no terminal-state receipt check for a fresh-nonce repeated completion.
- **Remedy:** add a durable page receipt keyed by sync run, capability, route binding, page/cursor and payload digest; return the stored result on duplicate; make page counters and completion transitions terminal-state aware. Preserve signed nonce replay protection as transport anti-replay, but do not treat it as semantic delivery idempotency.

### W2-16-F06 — Stable source IDs and personal overlays are not yet one explicit contract

- **Status:** open; report-only.
- **Severity:** important for edit survival and calendar correctness; **confidence:** high from source, live edit untested.
- **Consequence:** planner and calendar identity currently derives from provider record keys (`managebac.ts:1917-1970`, `calendarShared.ts:153-255`). Calendar adds `:official_deadline` and `:task`, which is directionally correct, but a provider key/template change can create a new logical item. The source-owned planner fields are marked locked in artifact content, while `externalRecordOverlays` stores notes/completion/reminders/tags/timing; no complete path was found that captures every direct planner edit into an overlay before refresh. Source refresh also updates the source-derived task title/notes/status even though that task is intended to be personally schedulable.
- **Remedy:** define an immutable canonical source identity independent of display fields; keep official deadline and personal task as explicit derived children with stable references; route personal status/notes/reminder/move/complete changes through an account overlay or typed personal task mutation; on refresh update only source-owned fields and preserve personal fields. Add readback for source change + local edit + resync + calendar scheduling.

### W2-16-F07 — Current/history and attachment/scheduled coverage remain incomplete

- **Status:** open; report-only.
- **Severity:** important for launch workflows; **confidence:** high source / provider behavior untested.
- **Consequence:** class candidates visibly filter `archived` but do not establish a current academic-period/date contract. Resource projection stores provenance metadata but does not materialize provider attachments for download/readback. `configure` leaves `nextSyncAt` unset; `scheduleExisting` has no current caller, and the scheduler only accepts verified non-personal routes. A tenant with only verified personal routes cannot be safely polled school-wide, but the UI/operational state needs to say this explicitly.
- **Remedy:** verify provider period fields and define currentness; test same-ID current/history payloads; add attachment capability-specific materialization; initialize/surface schedule state based on actual verified capability coverage, keeping personal sync user-triggered and never enumerating student credentials.

## Migration and reconciliation design for parent/Pablo

### Existing unscoped keys

Use a versioned canonical identity rather than silently changing the existing string:

`v2:<integrationId>:<audienceScope>:<mappedAccountId-or-shared>:<recordType>:<providerCanonicalId>:<academicPeriodKey-or-current>`

Keep the old provider key as a temporary alias for readback/reconciliation. Backfill in bounded batches per integration:

- unscoped shared/class rows can be re-keyed when `(integration, provider ID, period)` is unique;
- mapped-user rows with one unambiguous account mapping can be re-keyed to that account;
- collisions across accounts must be quarantined and re-fetched from each mapped provider identity, never assigned by latest-write order;
- re-key related projections, relations, overlays, conflicts, planner source references and calendar source references transactionally per row/batch;
- dual-read during rollout, dual-write only after the backfill checkpoint, then remove the alias after collision and retry metrics are zero for a defined window.

The migration must preserve source hashes and provider provenance, record an audit count of re-keyed/quarantined rows, and provide a dry-run/readback report before any deletion of the old alias.

### Stable task/calendar IDs

Store an immutable source identity separate from the provider’s route/template key and display title. Use the canonical provider ID plus integration/audience/account/period, with a semantic child kind for `official_deadline`, `personal_task`, `timetable_event` and `resource`. Keep `calendarItems.sourceRecordId` as the durable source row and link official deadline → personal task with `officialDeadlineItemId`/`taskItemId`; do not derive identity from mutable title, due date or route parameters. Reconcile old rows by source record ID first, then by a uniquely provable legacy key, otherwise create a review conflict.

### Source-owned versus personal overlay

Declare source-owned fields (provider title, description, provider due date, provider teacher/location and source status) and personal fields (notes, completion preference, reminders, alternative timing, placement, links and personal task schedule) in one shared contract. Direct editing of a source-owned artifact field must either be blocked with a clear personal-adjustment affordance or atomically create/update an account overlay before the next sync. A sync may refresh source-owned fields only; it must not reset personal completion, notes or schedule. Add a provenance/readback view showing source value, personal overlay and effective value.

### Receipts and scheduling

Add a page-receipt table with sync run, capability, route binding, page/cursor, payload digest, first-seen time, result/counts and terminal status. Exact duplicate delivery returns the recorded result; a same page/cursor with a different digest is a provider/replay anomaly and is quarantined. Completion/failure mutations must reject or return the existing terminal result when the run is already settled. Scheduling should be driven by the set of verified readable capabilities: non-personal class/school routes can be claimed by the school worker; personal-only routes remain manual/AI/account-triggered. Configure/repair should set `nextSyncAt` only when a runnable non-personal route exists, otherwise expose an actionable degraded/manual state. Honor provider rate limits, credential rejection, schema quarantine and lease expiry without enumerating student credentials.

## Decisions for parent/Pablo

- Integrate `9e5d2fd9` as a narrow guard patch after review; do not integrate `3c905bcc` wholesale.
- Treat same-provider-ID personal key collisions as a release gate until the versioned migration/reconciliation is designed, tested with two accounts and read back without data loss.
- Keep school-wide ManageBac conflict access administrator-only; do not broaden student/teacher roles to make conflict UI convenient.
- Do not claim duplicate-delivery idempotency until durable receipts cover page delivery and terminal completion.
- Keep scheduled polling capability-driven and non-personal; a personal-only tenant should be visibly manual/identity-scoped rather than solved by credential enumeration.
- The current live browser failure is an environment/readiness limitation, not evidence that the patched source passed or failed in the primary runtime. Repeat the browser matrix only after the parent restores the existing shared Convex instance without reset/redeploy.
