## Findings grouped by root cause

### W2-20-F01 — Scheduling a task could duplicate a block on retry

Severity: important before the fix; confidence high; source-confirmed and fixed in the source worktree.

`calendar.scheduleTask` previously validated the task and unconditionally inserted a new `calendarItems` row. A lost response, browser retry, or AI replay could therefore create two active scheduled blocks for one user gesture. This was inconsistent with the existing `mutationDefaults` idempotent declaration and with the stable planner/task references already present in the action contract.

The fix adds an optional caller-owned key to `calendarItems`, indexed by owner/key. Human Calendar drops generate `human:${uniqueToken()}` once per gesture. AI scheduling forwards an explicit tool key or derives one from the actor and OpenRouter tool-call ID, falling back to a hash of arguments. A matching active row is returned, changed data under the same key is rejected, and a removed row cannot be silently resurrected. The key is deliberately separate from `sourceKey`: repeated intentional blocks for the same task remain possible with new keys.

Affected neighbors checked: task-item scheduling, planner/task scheduling, AI tool registry/route forwarding, Calendar optimistic pending IDs, revision-based move/resize, official deadline separation, and focused Calendar/plan tests. Remaining limit: direct callers that omit a key retain legacy insert-only behavior; making the key mandatory is a follow-up migration/contract decision.

### W2-20-F02 — Planner task completion does not update scheduled work state

Severity: important if “complete” means a linked Calendar transition; confidence high from source; live behavior unverified.

Planner tasks have a durable `status: "done"`, and `calendar.planTasks()` omits done tasks from the unscheduled list. However, `calendar.scheduleTask` only stores the foreign references (`planArtifactId`, `planTaskId`, `linkedArtifactIds`) and never writes the returned block ID into the plan task’s `calendarBlockIds`. Conversely, Calendar overview selects active `scheduled_work_block` rows without checking the linked task’s current status. Calendar’s item panel exposes resize and “Open linked work”, but no complete action.

Consequences are a split readback: the planner may show a task completed while its scheduled work block remains active in Calendar, and Plan Studio’s canonical `planScheduleEntries()` cannot include a newly created block because `calendarBlockIds` is still empty. This is partly a product choice—some calendars intentionally retain completed work as history—but the current UI does not make the choice explicit.

Recommended bounded design: make the plan task the completion authority, keep the block as a visible historical row with an explicit `completed`/derived status, and add a server-side reconciliation query or mutation that updates the block when the plan task transitions to `done`. If the intended rule is instead that blocks remain active until manually removed, expose that state clearly and add a “mark work complete” action. Do not patch this by blindly overwriting collaborative plan content from Calendar; the collaboration writer and ownership/revision contract need to be selected first.

### W2-20-F03 — Ordinary embed creation is not retry-idempotent

Severity: important for duplicate UI rows/nodes; confidence high from source; live unverified.

`artifactEmbeds.create` inserts a row for every call and has no caller mutation ID or `(container, region, source)` uniqueness contract. The legacy document migration separately searches for the same historical region/source and converges, but normal document and whiteboard flows call `create` before inserting or updating their local reference node. A request retry or crash between the row insert and local node transaction can leave duplicate active rows or an orphaned active row.

Remedy proposal: add a caller-owned `idempotencyKey` or deterministic placement operation ID to the embed schema and all ordinary document/whiteboard/panel/dock callers; return the existing row only when the full placement/source/version tuple matches, and reject mismatched reuse. Add an orphan reconciliation query for row-without-node cases. This should be coordinated with the collaboration durability/retention work rather than folded into the calendar patch.

## Decisions for parent/Pablo

- Integrate the calendar idempotency commit if the optional-key compatibility policy is acceptable. Recommended: keep keys optional for one migration window, instrument missing-key callers, then make them required for new schedule mutations once all callers are forwarded.

- Treat ordinary embed retry safety as a separate migration, not as a second incidental schema extension in the calendar patch. It requires row/node reconciliation and should align with collaboration durability and deletion retention.
- Do not expand `/admin` navigation or introduce teacher-supervision semantics to solve educational workflows. Source authority already models peers via owner/read/modify/use capabilities; verify that with an ordinary second identity after runtime recovery.
