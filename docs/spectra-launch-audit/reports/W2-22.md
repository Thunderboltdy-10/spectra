# W2-22 — Deletion retention and large-history lifecycle

## Result

The deletion lifecycle is only partially launch-ready. The existing direct hard-delete path removes the primary artifact, tree placements, versions, known import originals, assets, links, runtime builds, some AI rows, and selected memory projections. W1 embed tombstones were already present for direct source/container deletion; this task extended the same contract to permanent Trash/tree purge and verified both paths in Convex tests.

The larger lifecycle remains open: artifact deletion does not yet own a resumable cascade for native replicas, content-addressed payloads, bridge operations, sync conflicts, storage-strategy transitions, collaboration rooms/logs, region claims, or every AI descendant. Abandoned import uploads also have no reliable job-owned storage cleanup. Those changes require a precise retention/ownership design and are handed to the parent rather than being guessed in this wave.

This task also added a bounded race guard. A Bridge byte or structure operation whose work disappeared before claim or completion is now terminalized as `work-no-longer-exists`; the associated operation and target replica are failed/unavailable, replica payload references are cleared, and a pending storage-strategy transition is failed/restored. The guard prevents a late native write from logically resurrecting a deleted work, but it is not a substitute for the full cross-domain cascade.

## Findings grouped by root cause

### W2-22-F01 — Permanent delete is still not one cross-domain cascade

Severity: important. Confidence: high. Proven source defect.

`convex/spectraArtifacts.ts:3192-3440` removes the artifact, work placements, user states, versions and snapshot references, runtime builds and their storage, finalized import originals, assets and their storage, links, `spectraAiRuns` plus `spectraOperations` and `spectraResultCards`, and selected memory evidence/claims. It does not retire or delete the artifact-keyed rows in `workReplicas`, `payloadObjects`, `bridgeWriteRequests`, `bridgeFsRequests`, `syncOperations`, `syncConflicts`, `storageStrategyTransitions`, `collaborationRooms`, `collaborationUpdates`, `collaborationSnapshots`, or `regionClaims`. It also does not cover all AI descendants such as run jobs, run attachments, events, or tabs.

Permanent Trash purge is a separate implementation. `convex/orgTreeShared.ts:1596-1660` removes owner placements, user states, links, and the artifact row. `convex/orgTree.ts:656-689` drains collaboration rooms for the selected work before calling it. That path used to bypass W1 embed tombstones; the new shared helper closes that specific gap, but the broader cascade remains different from direct delete. For a non-owner/shared placement, the tree path intentionally removes only the account’s placement, which is correct ownership behavior but means the owner’s eventual delete still has to handle the global graph.

User consequence: “delete forever” can leave cloud metadata, native replica state, payload objects, room data, pending operations, and operational rows that continue to be found by indexes or maintenance jobs. A local source file may intentionally remain on disk, but the cloud-side lifecycle must be explicit rather than incidental.

Bounded remedy: define one deletion coordinator used by direct hard delete and permanent Trash purge. It should record a deletion generation/job, enumerate every owned row family by indexed pages, terminalize in-flight work, drain collaboration data, release only verified-unshared payload objects, and finish with an auditable completion marker. Keep account-placement removal separate from owner-object deletion.

### W2-22-F02 — Orphan replicas can pin payloads and confuse offline/migration state

Severity: important. Confidence: high. Proven source defect.

`convex/replicas.ts:1664-1743` implements `payloadHasRemainingRefs` by probing `workReplicas` payload/projection fields, artifact pending refs, pending/claimed bridge writes, and open/resolving conflicts. The probes treat any matching row as live; they do not first verify that the referenced `workId` still exists. Thus an orphan local/cloud replica or request can prevent a payload from being released indefinitely.

The sweeper at `convex/replicas.ts:1764-2020` repairs stale claimed writes, pending replicas without live requests, pending operations, strategy transitions, resolving conflicts, and open conflicts whose work is missing. It does not scan all replicas with missing work, clear their payload/projection references, or terminalize every bridge request/structure request/transition keyed to missing work. `claimPendingPayloadUpload` at `convex/bridgeSync.ts:993-1040` also scans local replicas before checking that the artifact still exists.

The new guard addresses the highest-risk write race: `bridgeSync.claimWrite` and `completeWrite` now check work existence/status before native byte mutation, fail the associated request/operation/strategy transition, mark the target replica unavailable, and clear its payload/projection refs. `bridgeStructure.claim` and `complete` apply the equivalent terminal state. The tests prove missing work returns no claim and that late completion cannot return the request to pending/verified. This is intentionally not a full payload GC implementation: shared account-level payload ownership is ambiguous until all references are classified.

Native consequence: `kind: local` replicas and physical files are not the same object. Direct artifact deletion currently does not prove whether the local Office file should be deleted, moved to Recycle Bin, retained as an offline copy, or offered for local-to-cloud migration. Clearing the cloud replica ref without an explicit local-file policy could either leak source bytes or destroy a user’s only offline copy.

Bounded remedy: add a missing-work repair phase to the deletion coordinator and sweeper that pages every replica/request/transition/conflict by work, clears only references proven to be owned by the deleted work, and leaves the physical file decision to an explicit Bridge policy. Add a migration rule: after cloud work deletion, an offline local replica must become terminal and non-uploadable, never silently recreate the cloud artifact on reconnect.

### W2-22-F03 — Abandoned import uploads have no job-owned storage cleanup

Severity: important for retention/cost. Confidence: high. Proven source gap.

`convex/artifactImports.ts:24-135` creates an `artifactImportJobs` row in `uploading`, then stores `originalStorageId` only during successful finalization. `abortUpload` at `:215-238` accepts only `jobId` and `reason`; it marks the job failed but cannot delete a storage object that was accepted before the client disconnected. The HTTP route uploads the request body before finalizing, so a disconnect between those steps leaves no durable storage reference available to the abort mutation. `convex/crons.ts` has no stale uploading-import janitor.

Known finalized originals are deleted by direct hard delete, but that cannot recover an upload whose ID was never persisted. This is separate from asset uploads, where `artifactAssets.failUpload` accepts an optional storage ID and the HTTP wrapper can clean it up.

Bounded remedy: persist the generated upload/storage ID against the owned import job before or as part of upload finalization, accept it on abort with account/job validation, and add a bounded expiry sweep for `uploading` jobs. The retention window, meter reversal, quarantine reason, and retry/idempotency behavior need to be specified before implementation.

### W2-22-F04 — Collaboration room and claim retention is inconsistent by deletion entry point

Severity: important. Confidence: medium-high. Direct-delete gap proven; retention policy is a decision.

Tree purge explicitly calls `drainArtifactCollaboration` (`convex/orgTree.ts:656-689`), paging updates and snapshots before deleting each room. Direct `spectraArtifacts.permanentlyDelete` has no equivalent room drain. Therefore the same user-visible permanent deletion can either remove collaboration history or leave artifact-keyed rooms/logs behind depending on which entry point is used.

Room rotation has a different deliberate contract: `convex/collaboration.ts:236-280` deletes retired updates/snapshots in batches of 128, resets counters when done, and keeps the closed `__retired__` room row. Keeping that row may preserve generation identity/auditability, but it is not the same as deleting a work’s collaboration data. `regionClaims` can retain an optional `roomId` and is released through account/run/lease paths, not through artifact deletion. Deleting rooms without deciding claim handling could orphan active leases or make late editor messages ambiguous.

Bounded remedy: choose separate retention classes for active-room history, retired-room identity, and deleted-work history. The delete coordinator should close/revoke artifact claims first, drain updates/snapshots by cursor, then either delete or tombstone rooms according to that policy. Direct hard delete and Trash purge must call the same coordinator.

### W2-22-F05 — AI run cleanup stops at a partial descendant set

Severity: important if run history or attachments are user-visible. Confidence: high. Proven source defect.

The direct delete path queries `spectraAiRuns` by artifact and deletes each run’s `spectraOperations` and `spectraResultCards` (`convex/spectraArtifacts.ts:3414-3440`). The schema also contains run-keyed `spectraRunJobs`, `spectraRunAttachments`, result/event/tab-style rows, and other `runId` references (`convex/schema.ts:3195-3479`). The delete path does not enumerate those families. Some may be operational history that should be retained under a redacted/tombstoned retention class, but there is no visible artifact-delete decision or cleanup marker.

Bounded remedy: inventory every `artifactId`/`runId`/`workId` edge, classify it as delete, tombstone, or retain-with-redaction, and implement an indexed page worker. A retry must be idempotent and must not rerun metering or delete a newly reused storage ID.

### W2-22-F06 — Large deletes are transaction-sized and mostly unbounded

Severity: important at large history/asset counts. Confidence: high. Proven source defect.

Direct hard delete uses `.collect()` for versions, runtime builds, import jobs, assets, links, runs, and multiple memory families. The existing W1 report already identified the same shape for version history and exceptional collaboration reads. Tree purge has bounded drains for some owner rows, but the new embed helper and the direct path still collect all matching source/container embeds and requests in one transaction. There is no deletion cursor, phase marker, or resumable continuation for the broad cascade.

User consequence: an artifact with long version history, many assets, native replicas, or room updates can exceed transaction/read budgets; a failure either rolls back the atomic direct mutation or leaves the separate tree path partially divergent. Retrying a partially designed cascade risks double metering and ambiguous storage ownership.

Bounded remedy: make the user-facing action create a deletion job after capability/protection checks. Store phase, cursor, counts, deletion generation, and idempotency key. Use fixed page sizes per table, enforce a maximum wall-clock/read budget, and expose progress/retry status. The parent should choose whether the final artifact row is marked `deleted` until all required phases finish or removed only after the coordinator records a durable tombstone.

### W2-22-F07 — Stale Bridge structure requests can be re-driven forever

Severity: important for native safety. Confidence: high. Proven source behavior.

`convex/bridgeSync.ts:282-305` re-drives claimed `bridgeFsRequests` older than two minutes by returning them to `pending`; there is no expiry or attempt ceiling on the structure request schema. A device that repeatedly claims, moves/renames, fails to report completion, and disconnects can cause the same physical operation to be proposed indefinitely. The new missing-work guard prevents re-driving a deleted work into a new claim, but it does not solve repeated stale claims for a live work or prove what happened on disk after a timeout.

Bounded remedy: add an operation expiry/attempt policy and a reconciliation state that distinguishes “may retry” from “physical effect unknown.” For delete/move/rename, the Bridge should report the observed path and a stable filesystem operation ID; after the cap, stop claiming and require explicit user reconciliation. Preserve the current safe path validation and Recycle Bin wording.

### W2-22-F08 — Payload release and upload integrity are not a single retention contract

Severity: important for storage correctness. Confidence: high.

`payloadObjects` are account/hash-addressed and store a `refCount`, but the sweeper recomputes references through a bounded probe set instead of relying on a fully maintained ownership ledger. `convex/payloads.ts` registers payloads after size checks, while `artifactAssets.finalizeUpload` checks size, digest, and media type; the direct import finalizer still checks only size. The W1-02 report separately records the direct-finalizer integrity gap.

A mismatched or orphaned object can therefore be retained, metered, and considered live by a stale reference even when its source work is gone. Deleting storage from the artifact cascade without a shared-payload ownership check would be unsafe when two works/account replicas intentionally share the same hash.

Bounded remedy: make every object-registration/finalization path enforce declared size, SHA-256, and media type; maintain explicit owner/reference edges or run a bounded, work-aware reference rebuild before release. Keep storage deletion and meter reversal idempotent by object ID plus lifecycle generation.

## Decisions for parent/Pablo

- Treat direct hard delete and permanent Trash purge as two front doors to one resumable, capability-checked deletion coordinator.
- Choose whether the artifact row remains as a deleted tombstone until every required phase completes. Do not use physical row absence as the only signal while bridge, room, migration, or storage cleanup can still be in flight.
- Define the local-file policy explicitly: retain offline copy, send to Recycle Bin, delete, or offer migration. The policy must be platform-specific where Windows/macOS semantics differ and must prevent reconnect from resurrecting cloud work after deletion.
- Define payload ownership and retention separately from artifact ownership. Shared account/hash objects need reference edges or a work-aware release proof; do not blindly delete by artifact ID.
- Decide room/claim retention: whether retired room rows are audit tombstones, when deleted-work room history expires, and how active region claims are revoked before room cleanup.
- Classify AI operational descendants, bridge operation history, conflicts, and audit/meter records as delete, tombstone, retain-with-redaction, or retain-without-source-content.
- Give stale imports, stale structure requests, transitions, and orphan replicas explicit expiry windows, attempt caps, cursors, and retry/idempotency keys.
