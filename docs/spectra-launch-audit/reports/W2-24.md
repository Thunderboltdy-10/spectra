# W2-24 — Full chat and dock experience parity

## Result

Contained chat-shell and side-surface fixes are implemented and committed. `/chat` now preserves a retryable error state when its initial thread/overview reads fail, the chat browser distinguishes a failed list read from a successful empty list, and the chat browser, Live Thread panel, and chat history surface share explicit dialog/focus behavior.

The full live parity matrix could not be completed because the assigned runtime was not ready: Convex on `127.0.0.1:3002` refused connections and `/api/health` reported both Convex and gateway dependencies as `not_ready`. The live evidence therefore verifies the failure behavior and records `/chat`'s pre-fix masking behavior, but does not claim ordinary conversation, reopen, attachment, stop/continue, streaming-card, artifact, or browser-history parity.

## Findings grouped by root cause

### W2-24-F01 — `/chat` converted initial read failure into a false new-chat state

Severity: important. Confidence: high. User consequence: a user can believe they are in a fresh, usable conversation while the thread/workspace data layer is down; a failed reopen can look like an empty/new conversation.

Before the fix, `ChatShell.refresh` swallowed `getSpectraThread` errors as `null`, and the initial `ConversationSurface` always received the welcome empty state after the outer refresh rejected. The live repro is visible in `chat-recheck.png`/`.yml`: the page stayed on `New conversation` despite API 500s and repeated WebSocket refusal. The bounded fix is `chat-shell.tsx:132-165,180-210,709-733`: detail-read failures now propagate to a retryable `ProductErrorState`; the existing missing-thread redirect logic is not used to classify transport/read failures.

Affected neighbors: deep-link/reopen, route navigation, and run-to-conversation. Core run lifecycle and command contracts were left untouched.

### W2-24-F02 — Chat-browser list failure was rendered as “No chats found”

Severity: important. Confidence: high. User consequence: a connectivity or authorization failure looks like a genuinely empty history, which hides whether retrying can recover the list.

Before the fix, the list catch path wrote `threads=[]` and the normal empty branch rendered `No chats found`. The bounded fix at `chat-browser-panel.tsx:82-111,305-326` tracks `loadError`, uses the shared truthful failure copy, exposes `Try again` with `force: true`, and only renders `ProductEmptyState` after a successful empty projection. The distinction is covered by the focused test.

### W2-24-F03 — Temporary side surfaces had no shared focus/close contract

Severity: important. Confidence: high. User consequence: keyboard users could escape into the underlay, Escape behavior differed by surface, and closing a panel did not reliably return focus to its opener.

The bounded fix adds `components/panel-focus.ts:1-77`, with panel-local Escape handling, Tab/Shift+Tab containment, initial focus, and opener restoration. `ChatBrowserPanel` now has a mobile scrim and `role="dialog"`/`aria-modal` (`chat-browser-panel.tsx:214-224`); `LiveThreadPanel` forwards the same semantics through `StudioSplitShell`; chat history receives the same contract. The focused test covers the browser surface directly. A live focus pass remains blocked.

### Verification blocker — runtime unavailable, not a parity verdict

This is an environment limitation rather than a new product finding. The assigned browser session repeatedly received API 500s, Convex WebSocket `ERR_CONNECTION_REFUSED`, and `/api/health` `not_ready`. It prevented a valid readback of durable thread/run/card IDs and status transitions. No claim is made that the untested matrix passes or fails.
