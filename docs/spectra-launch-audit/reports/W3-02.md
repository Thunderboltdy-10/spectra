# W3-02 — repeat Word and linked-file save journeys

## Result

The healthy-window linked DOCX repeat passed the important persistence path: a safe paragraph edit was written through the shared bridge, keyboard undo removed the first edit, a second edit survived an explicit Word/Spectra conflict resolution and a full reload, and native package inspection showed only `word/document.xml` changed while the other 48 package members remained byte-identical. The rich control opened with tables, lists, hyperlinks, images and OMML equations represented in the live DOM. The previous `image3.bin` 404 did not reproduce: the supported PNG-backed `.bin` returned 200.

The ordinary component-level import reached Mammoth conversion but failed durable completion: the completion POST returned HTTP 500, the UI quarantined the import, and a fresh artifact API read still showed the original one-block document while the converted content remained only as a device draft. The generated Word-copy download did pass from the real overflow menu and produced a parseable 8,974-byte DOCX, with the expected clean structural/formatting loss. The W2-10 rich-only UI/AI mismatch remains pending because the live contextual gate was correctly disabled rather than silently writing.

## Findings grouped by root cause

### W3-02-F01 — native save is durable but can surface a same-content conflict

- Severity: small; confidence: high; live baseline.
- Consequence: after the bridge wrote the Spectra marker into the local Word package, a fresh load showed a Word/Spectra conflict even though both previews displayed the same marker. The user had to choose `Keep Word version`; the choice then survived another reload.
- Chain: linked editor change -> bridge native write -> fresh load -> conflict resolver -> Word choice -> durable marker readback.
- Evidence: artifact `wx72d4cm0fwz1a2vny3c1qp3cn8e36zx`; `linked-word-resolved.png`; package hashes above.
- Recommendation: inspect whether the resolver compares serializer/payload revision identity rather than normalized target-region content. Preserve the explicit conflict choice, but avoid a noisy conflict when the competing visible region is identical. No source change was made because the runtime path is shared and the assignment only authorizes a bounded DOCX fix after reproduction.

### W3-02-F02 — supported native media is healthy; unsupported Word media remains preservation-only

- Severity: future fidelity; confidence: high; live plus source.
- Consequence: PNG/JPEG media can render through the verified route. EMF and package parts whose declared type is not PNG/JPEG remain unavailable, although they are preserved in the native package.
- Chain: `nativeImageContent` accepts only PNG/JPEG (`src/features/spectra/lenses/docx-lens.ts:523-576`); the media route repeats that boundary and returns 404 (`src/app/api/spectra/lenses/docx/media/route.ts:64-83`).
- Evidence: live `image3.bin` 200/752,335 bytes; `image1.bin` and `image2.emf` 404; control media lengths recorded in the evidence ledger.
- Recommendation: keep the current truthful non-broken projection. Add an explicit supported/unsupported media fidelity note or a placeholder only if product wants visible non-PNG/EMF placeholders; do not pretend EMF is rendered.

### W3-02-F03 — generated Word download works, but is a clean lossy export

- Severity: future fidelity; confidence: high, live baseline.
- Consequence: the separate Word copy downloads correctly, but drops native tables, hyperlinks, OMML, rich run formatting and media from the rich linked source. This matches the “separate copy” boundary; it is not a native roundtrip.
- Chain: `exportDocument` -> `Packer.toBlob` -> object URL -> anchor download (`document-studio.tsx:1746-1912`).
- Evidence: real browser download and independent ZIP parse in the repeat ledger/evidence file.
- Recommendation: keep the truthful clean-copy boundary. Add a fidelity summary beside the download only if users need to understand what is intentionally omitted; do not silently call this a native export.

### W3-02-F04 — component import conversion is lost at completion failure

- Severity: important; confidence: high, live baseline.
- Consequence: the user sees an explicit quarantine after the client successfully converted the DOCX, and a fresh artifact readback still contains the empty `New Document` rather than the converted copy. The converted content is held in the local draft, not durably imported.
- Chain: `Mammoth.convertToHtml` -> `setContent` -> `onChange(importedContent)` -> `POST /api/spectra/imports {status: imported, importedContent}` -> HTTP 500 -> catch path -> quarantine completion. The saved request body contains `status=imported`, 92 blocks, and no native binding; the response is generic `INTERNAL_ERROR` request `c7a92bd8`.
- Evidence: requests 107/108/110 and 118/119/121/122; `import-complete-request-121.json`; `import-complete-response-121.json`; `ordinary-import-quarantined.png`; post-reload artifact API content remained one default block.
- Recommendation: preserve the converted draft while retrying completion, but do not label it quarantined if the completion failure is transient. Make the completion state distinguish parser quarantine from persistence/network failure and add an idempotent retry/readback path. Library upload/native-open remains a separate product path and should be named distinctly.

### W3-02-F05 — rich-only operation mismatch is currently gated in the live UI

- Severity: future important if a future UI/AI command can target rich-only content; confidence: medium, live gate plus source risk.
- Consequence: `docxOperationsBetween` can emit no operation when only `inlineContent`/equation metadata changes and block text/table rows do not. The native lens separately marks OMML/rich regions read-only, so a live command may be correctly gated; this run did not reach a UI/AI mutation command to distinguish those outcomes.
- Evidence: live selected OMML node exposed disabled `Edit equation`/`Delete equation` buttons with truthful Word-only titles; screenshot `linked-equation-protected.png`. Source at `src/features/spectra/lenses/document-projection.ts:149-205`; W2-10 direct harness still shows a no-op, but this run did not accept a UI/AI mutation proposal.
- Recommendation: next repeat must invoke the reachable equation/rich-region command or AI action and capture either a truthful disabled/protected reason or a durable operation. If a proposal is accepted but yields zero operations, add a DOCX-specific guard/error rather than broadening the shared operation contract.

### W3-02-F06 — Convex/import completion failures need separate recovery messaging

- Severity: important for user recovery; confidence: high runtime observation, not an application defect by itself.
- Consequence: an earlier pass showed the browser’s `orgTree:liveIdentities` one-second timeout while the same batch was active; the later import repeat instead returned a 500 `INTERNAL_ERROR` and then a connection interruption while retrying the held draft. The two failures must not be conflated.
- Evidence: all four health endpoints remained 200 at the checkpoints; W3-01 classified the timeout as batch capacity and later confirmed no restart was warranted. Import request/response bodies identify the separate 500 path.
- Recommendation: keep the linked saved checkpoint, distinguish runtime timeout, import-completion failure and parser quarantine in user-facing state, and rerun only the remaining readback if W3-01 has a quiet window.
