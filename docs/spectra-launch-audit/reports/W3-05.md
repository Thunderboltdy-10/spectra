## Findings grouped by root cause

### W3-05-F01 — Clarification replies were prompt-shaped instead of target-shaped

- Consequence: a legitimate choice such as `Final A` could be matched to an older same-title choice or could continue without the artifact candidate that the asking run resolved. This is an important correctness risk for edits.
- Severity: important. Confidence: high from the live request payload and W2-03 source chain.
- Repro/code chain: Live Dock posted only the selected title in request body `4129`/`4393`; the former server gather path reverse-searched the new prompt through stored choice titles. There was no durable `(asking run, execution, choice key)` continuation contract.
- Evidence: [clarification question](<local-workspace> [update-final timeout](<local-workspace> and W2-03 report/source chain.
- Affected neighbors: artifact targeting, thread memory, operation validation, and retry/stop controls.
- Bounded remedy: commit `62728bec` forwards run/execution/choice identity and binds context to the asking run’s existing resolution snapshot. It is not live-integrated, and durable clarification IDs/schema remain future work.

### W3-05-F02 — Primary runtime timeouts prevented end-to-end AI readback

- Consequence: the first student UI pass showed paused/server-error or only-started cards, preventing a reliable determination of explanation quality, operation list, committed artifact revision, or AI-created follow-up identity. Later quiet-window passes completed explain-only runs and a steered continuation, narrowing this to edit/mutation, AI-created follow-up, and attachment-retry coverage rather than all AI readback.
- Severity: important for launch-audit readiness; not classified here as a newly introduced source defect. Confidence: high for the observed runtime state, low for root cause beyond the displayed one-second timeout.
- Evidence: [update-final timeout](<local-workspace> [healthy durable readbacks](<local-workspace> and the post-health evidence.
- Affected neighbors: broad edit/mutation runs, Calendar scheduling, AI-created follow-up verification, and attachment retry verification.
- Bounded remedy/next step: W3-01/runtime owner should diagnose the existing timeout on the preserved primary stack and rerun the exact pending scenarios. This task did not restart or alter that stack.

### W3-05-F03 — Attachment retry protection is correct but not live-proven in this pass

- Consequence: retrying a failed attachment run without bytes would be unsafe; the current guard instead requires reattachment and suppresses retry. The live degraded run did not reach that retry action, so the user-facing guard still needs one healthy runtime readback.
- Severity: small remaining verification gap. Confidence: high from source and Convex test, not live.
- Evidence: `src/app/api/spectra/run/runtime.ts:144-156` and `convex/ai-run-lifecycle.test.ts:277-293`.
- Bounded remedy: retain the guard; on a healthy runtime, interrupt a unique attachment run, click Retry once, verify the exact reattach copy and no retry POST, then start a new run with the files reattached.

### W3-05-F04 — Calendar key scoping is source/test sound; live postcondition remained unavailable

- Consequence: no issue was found in the scoped key design. Same-intent retry should reuse within the model execution, changed data under the same key should conflict, and a separate later request should be able to create a deliberate second block.
- Severity: no finding / verification gap. Confidence: high for source/test, unavailable for live integration in this session.
- Evidence: `src/app/api/spectra/run/loop/plan.ts:3593-3623`, `convex/calendar.test.ts:97-166`, request body `62`, and the stopped Calendar screenshot.

### W3-05-F05 — Interleaved Calendar and attachment work remained stale-context sensitive

- Consequence: in the existing same-thread live history, a Calendar request and a later three-file attachment request were both present while the Dock still showed the attachment chips, but the visible assistant progress answered the earlier Calendar question. This is evidence of a stale/interleaved context presentation risk; no Calendar mutation was accepted.
- Severity: important verification risk. Confidence: high for the observed same-thread state, not a complete root-cause isolation.
- Evidence: [interleaved thread snapshot](<local-workspace> [interleaved thread screenshot](<local-workspace> and the healthy attachment run above.
- Bounded remedy: preserve exact thread/run/attachment provenance through the visible Dock and ignore late progress or cards whose run identity is not the active continuation. Keep Calendar mutation authority and attachment-byte retry protection unchanged.

## Small fixes completed

### Clarification continuation and exact stop forwarding

Files: `src/app/api/spectra/run/loop/clarification.ts`, `contract.ts`, `gather.ts`, `runtime.ts`, `context-builder.ts`, `use-spectra-run.ts`, `live-dock.tsx`, `conversation-surface.tsx`, `global-route-workbench.tsx`, `spectra-shell.tsx`, and focused tests. Commit: `62728bec`.

Before: a choice response was sent as a fresh prompt/title; server fallback searched recent messages by title and did not reliably rehydrate the asking run’s candidate target. Stop could be associated with the current exchange rather than the selected older Dock tab execution.

After: the UI forwards the asking `runId`, optional `executionId`, and stable displayed choice key; server context binds them to the exact stored choice and target-resolution snapshot; stop includes the tab’s exact execution and omits an unrelated submission key once a durable run id is known. Numeric choice mapping follows the resolver’s displayed confidence slice. Neighboring behavior checked: skipped choices remain target-free, older callers retain the legacy prompt fallback only when no continuation id is supplied, Calendar key scoping was left unchanged, and the existing attachment retry guard was not weakened.

Remaining limit: the primary runtime was not patched or restarted, and this work deliberately does not add durable clarification IDs, attachment-byte storage, or a new orchestration architecture.
