## Delivered

`bridge/bridge-app/src/polling.rs` now owns explicit active, idle, disconnected, unauthenticated, configuration-failure, migration-failure and request-failure timing. Successful work returns to a 250 ms active interval; successful empty calls increase idle backoff; failures retain bounded exponential retry starting at 1 second. Jitter is derived from a per-process UUID seed plus device identity, so equal cycles on separate Bridge processes/devices do not synchronize. All worker sleeps are capped at 15 seconds total, including jitter.

The sync worker in `bridge/bridge-app/src/main.rs` caches deployment configuration instead of rewriting it on every idle pass, preserves migration errors, and gives failure precedence over unrelated work when choosing the next schedule. It does not bypass grants, payload validation, native writes, receipts, or migration invariants. Local pairing/configuration, mount selection/retry/removal, newly journaled filesystem work, and Tauri exit now share a coalescing in-process wake signal. A wake during a busy pass is retained as one permit; it cannot cause a second native side effect because the existing journal/claim/receipt boundaries remain authoritative. Remote work has no push signal in the current protocol: its remaining discovery interval is explicitly bounded to 15 seconds.

## Controlled timing evidence

The `polling::tests` use a virtual clock, deterministic scheduler seeds, and a fake transport; they are not hosted billing measurements.

| Scenario | Observed result |
| --- | --- |
| Idle cost, 60 virtual seconds | 9 fake transport requests; maximum interval 14.183 s |
| Active successful work | next poll after 250 ms |
| Simultaneous local wake, 1 virtual second | duplicate wake signals coalesced; 4 requests total, queued request at 100 ms, added worker latency 0 ms |
| Remote discovery | exact maximum scheduler interval 15 s; transport duration is outside this sleep bound |
| Credential/config/migration/request failure | no 250 ms spin; first retry is at least 1 s and grows exponentially, capped at 15 s |
| Retry recovery | successful work clears failure/idle counters and returns to 250 ms |
| Shutdown | long wait is interrupted immediately by the shutdown signal |

The 0 ms local figure measures the injected queue-to-worker wake in the scheduler fixture. The existing filesystem watcher still samples its nonblocking event queue every 250 ms while active; this is separate from failed-configuration/backoff timing. No claim is made about hosted request billing, production plan usage, real synced files, or remote push behavior.
