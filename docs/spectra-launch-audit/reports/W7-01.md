## Scope completed

This slice hardens clarification continuation and run lifecycle truthfulness across the Convex state layer, route/runtime seam, and Spectra UI surfaces.

- Clarifications are durable and addressable by the original asking message and execution. A selected answer starts exactly one continuation B, consumes the asking execution A, and remains idempotent across repeat submissions or a lost acknowledgement.
- Continuations use the stored clarification targets and selected keys. A changed current focus cannot retarget an older clarification; direct lookup still works after the message falls outside the normal history page.
- Batch questions validate exact question IDs and option keys, including explicit skip, duplicate titles, bounded long keys, and cross-question substitution rejection.
- Stop and steer submit the execution/attempt displayed at click time. Versioned requests do not fall back to an unrelated latest run, and late operation commits are fenced after stop/reset.
- Run outcomes distinguish `answer_only`, `awaiting_input`, `canonical_saved`, `native_pending`, `native_verified`, `cancelled`, and `failed` rather than inferring persistence from generic completion.

## Integrated acceptance steps

1. Ask a clarification, change the visible focus, then select the option from the old question. Confirm the continuation edits the originally selected target, consumes A, creates B, and repeating the same submission does not create another B.
2. Submit a multi-question clarification with duplicate labels, a long key, and an explicit skip. Confirm valid exact keys are accepted and a key from another question is rejected.
3. Start an operation, change the visible run, then stop or steer the run shown at click time. Confirm the request carries that displayed execution/attempt and a late commit from the old execution is rejected.
4. Exercise answer-only, clarification, canonical-save, native, cancellation, and failure paths. Confirm each UI/API outcome reports the corresponding truthful state.
