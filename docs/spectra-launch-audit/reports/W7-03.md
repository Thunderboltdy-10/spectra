## Delivered behavior

1. Bridge write claims now carry an incrementing `claimGeneration` and random `claimToken`. Every current Bridge completion path sends both values. Convex accepts a completion only for the active lease; late acknowledgements return `{ ignored: true, reason: "stale-claim" }` and do not write replica, cloud, operation, or transition state. Terminal requests are immutable, so duplicate A acknowledgements cannot move a verified B back to waiting or failed.
2. SafeWriter now exposes the hash obtained from the durable target read-back. Replaying a verified journal intent re-reads the file and refuses to reuse the result if bytes were externally changed. The Bridge persists a native acknowledgement in a SQLite `native_ack_queue` before its network call, then retries it with bounded backoff after restart or a lost response. Queue identity includes request, generation, and token.
3. Native office receipts are strict at the Convex queue/complete boundaries and are semantically checked against artifact, base revision/payload hash, exact region/part targets, target revision/payload hash, deterministic operation ID, format family, semantic digests, and preserved parts. The stored receipt is the validated receipt, not caller-provided evidence.
4. Storage-transition replay returns the actual transition, materialization request, operation identity, and current `cloud`/`local` location set. Previews retain original/managed-copy identity, local resource/path, availability, revision, and pending write information. A transition does not imply a physical delete; unavailable and conflict states remain recoverable and are presented as such in the storage controls.

## Schema and migration note

`convex/schema.ts` changes are additive: `bridgeWriteRequests.claimGeneration` and `claimToken` are optional, and storage transitions now admit `conflicted` and `cancelled`. No data backfill or destructive migration is required; legacy unbound test/repair rows remain readable, while all new Bridge claims are bound to a lease. No migration file was created.

## Disposable failure cases exercised

1. A verifies, B verifies, then A is acknowledged again as `waiting`, `failed`, and `verified`: B remains verified/current with its target hash on both replicas.
2. A claim is made stale, a second generation reclaims it, and the first worker acknowledges success: the stale acknowledgement is ignored and the second lease remains active/authoritative.
3. A native receipt with a tampered target revision is rejected; valid receipts must also match exact target arrays, base payload hash, format family, and deterministic operation ID.
4. A native acknowledgement is inserted twice for one claim lease: the journal stores one row, supports retry backoff, and removes it only after acknowledgement.
5. A cloud-to-device transition is replayed: the same transition/request/operation identities and current location preview are returned, including the retained local resource and pending write path.

All verification was local (`convex-test`, Vitest, and Rust tests). No shared runtime, deployed Convex, browser, Actions, or macOS environment was used.
